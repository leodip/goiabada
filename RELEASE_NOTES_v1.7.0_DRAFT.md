# Goiabada v1.7.0 — draft release notes

This release strengthens session and two-factor authentication, adds operational controls and metrics, and expands the admin console. **Read the upgrade actions and compatibility changes before changing either image or binary.** These notes compare `v1.6.0` with `main` at `f9bd9bc0`; v1.7.0 has not yet been tagged.

## Upgrade actions

1. **Upgrade through v1.6.x if you are on v1.5.x or earlier.** Start v1.6.x with the correct AES key and let its data conversion finish before starting v1.7.0. A direct jump drops the old plaintext TOTP seed column before its contents are converted and can leave enrolled users unable to sign in. There is no automatic refusal for this unsafe path.
2. **Back up the database and the existing AES encryption key.** Stop the old auth server before the first v1.7.0 start, especially on MySQL with non-strict SQL mode. The auth server runs migrations at startup; the admin console has no database migration of its own. Upgrade the auth server before the console. Keep the old binaries and secrets available until the deployment works. Follow the [upgrade guide](https://goiabada.dev/deploy/upgrade-goiabada/).
3. **Plan for everyone to sign in again.** Migration `000062` ends every stored user session and revokes unredeemed authorization codes because the new password-authentication timestamp cannot be reconstructed from old sessions. Session-bound refresh tokens then fail with `invalid_grant`; offline refresh tokens remain usable. Apps with a pending sign-in must start it again. During a rolling upgrade, an old pod can still complete a sign-in after the new schema arrives; stop old pods first to avoid that window.
4. **For SQLite volumes created by the v1.6.0 images, change file ownership before starting v1.7.0.** The images now run as UID `10001`, while the old images ran as root. With the published Compose volume mounted at `/app/data`, stop the auth server and run `docker compose run --rm --no-deps --user 0:0 --cap-add CHOWN --entrypoint chown goiabada-authserver -R 10001:10001 /app/data`. Other writable bind mounts also need access for UID `10001`. The [readonly database troubleshooting page](https://goiabada.dev/troubleshooting/attempt-to-write-a-readonly-database/) covers this failure.
5. **Resolve email collisions before retrying a refused migration.** Migration `000047` lowercases stored addresses. Its preflight refuses addresses that differ only by case, or ones the database lowercases differently from Goiabada, and identifies the affected `users.id` values. Correct those rows and restart. The refusal happens before migration, leaving the schema clean.
6. **Keep existing secrets when regenerating setup files.** The wizard now writes Compose secrets to `docker-compose.override.yml` and Kubernetes secrets to `goiabada-secrets.yaml`; apply the Kubernetes secrets file before the manifest on a fresh deployment. It prompts before overwriting existing output, and a noninteractive rerun needs `--overwrite`. Regeneration creates new keys and passwords. Do not apply those new secrets to an existing database; copy the existing values, especially `GOIABADA_AES_ENCRYPTION_KEY`, into the generated file.
7. **Set database TLS explicitly for network databases.** For MySQL, PostgreSQL, and SQL Server, choose `GOIABADA_DB_TLS_MODE=verify-full` where the certificate names `GOIABADA_DB_HOST`, to encrypt the connection and verify the database. Add `GOIABADA_DB_TLS_CA_FILE` if its signing authority is absent from the system roots. An unset mode still uses `prefer`, which does not verify the server certificate and now logs a warning. PostgreSQL deployments using `PGSSLMODE`, `PGSSLROOTCERT`, or related libpq TLS variables must remove them before upgrading: the auth server now refuses to start while they are set. Set `GOIABADA_DB_TLS_MODE` and, when needed, `GOIABADA_DB_TLS_CA_FILE` instead. If you used `PGSSLMODE=require` with `PGSSLROOTCERT`, choose `verify-ca` to retain certificate-chain checking; `PGSSLMODE=allow` has no matching mode, so choose a mode deliberately. The auth server presents no client certificate, so there is no replacement for `PGSSLCERT`, `PGSSLKEY`, or `PGSSLPASSWORD`. [Issue #502](https://github.com/leodip/goiabada/issues/502)

### Rollback boundary

The new `goiabada-authserver migrate version` and `migrate to <version>` commands can step down only to schema `000044`. **v1.6.0 uses schema `000029`, so `migrate to 29` cannot roll v1.7.0 back to v1.6.0.** To return to v1.6.0, restore the pre-upgrade database backup and its matching secrets, then reinstall the old binaries. A down migration would not recover the sessions, codes, consent duplicates, and other data changed by this release.

## Breaking behavior and security boundaries

- **Public clients now require PKCE.** Existing public-client authorization requests without a challenge fail. Previously issued challenge-less codes and their descendant refresh tokens cannot be used; update the client and authenticate again. Changing a confidential client to public also revokes outstanding codes and refresh tokens. [PR #258](https://github.com/leodip/goiabada/pull/258)
- **Administrative scopes require explicit allowance.** After migration, only the built-in admin console client may request the six administrative `authserver` scopes by default. For another trusted client, an administrator with `authserver:manage` must enable **May request administrative scopes** in the console or through `PUT /api/v1/admin/clients/{id}/administrative-scopes`. Otherwise new authorization and password requests fail with `invalid_scope`, and affected refresh requests fail with `invalid_grant`. Possession of narrower admin scopes no longer grants control over administrators, admin clients, or their grants. [PR #508](https://github.com/leodip/goiabada/pull/508)
- **`authserver:manage-account` now requires user consent for other clients.** A client other than the built-in admin console must obtain the user's approval for this scope even when its **Consent required** setting is off. An interactive sign-in shows the consent screen until approval is stored; `prompt=none` returns `consent_required` without it. A live authorization-code refresh token carrying this scope can fail with `invalid_grant` until the user approves it at a new interactive sign-in; a refresh narrowed to omit the scope can still succeed. Password-grant refresh tokens and the built-in admin console client are exempt. [Issue #509](https://github.com/leodip/goiabada/issues/509)
- **The built-in admin console client is reserved for its browser-session API.** Migration removes its other permission grants and gives it `authserver:browser-sessions`. Any automation using that built-in client for admin APIs needs its own client and explicit grants. Admin console tokens are now kept in an auth-server-owned browser session behind an opaque cookie, which also avoids oversized cookies. The console's browser-session cookie now expires when the browser closes. [PR #267](https://github.com/leodip/goiabada/pull/267)
- **`authserver:userinfo` is gone.** `/userinfo` is authorized by `openid`; the old permission and its grants are removed. Tokens no longer carry that scope. A stored refresh grant naming it must be replaced by a new sign-in. [PR #450](https://github.com/leodip/goiabada/pull/450)
- **Self-registered clients have legacy flows disabled.** Dynamic registration now explicitly disables implicit and resource-owner-password flows, regardless of global defaults. Migration `000061` applies this to existing clients it can identify when their per-client switches were unset; it preserves an administrator's explicit setting. An older self-registered client renamed by an administrator before v1.6.0 cannot be identified by that migration; check those clients manually. Previously issued ROPC refresh tokens also stop refreshing while that client's ROPC switch is off.
- **Authorization input is stricter.** Duplicate authorization and token parameters, malformed space-delimited values, query-string credentials, and invalid redirect URIs are rejected. `state`, `nonce`, and `scope` are capped at 2048 bytes. An explicit `response_mode=query` is refused for implicit responses. Clients should send credentials in the request body or HTTP Basic, use one space between scope-like values, and retain a valid registered redirect URI.
- **Dynamic registration and client credentials are stricter.** `/connect/register` accepts `client_name` of at most 100 UTF-16 code units, down from the former 128-byte check, and refuses angle brackets. A client-credentials grant requesting `openid` now gets `invalid_scope` instead of an unusable token.
- **Two-factor and SSO claims are rechecked.** `acr_values` cannot lower a client's default ACR; `prompt=login` completes every factor the target level requires. Removing an authenticator lowers existing sessions to the level actually earned by their password, and an OTP claim from a removed authenticator cannot finish issuance. Users may see an interactive sign-in or re-enrollment where an old session previously passed silently.
- **OIDC claim timing is more precise.** `updated_at` is emitted only when `profile` is in scope, including in access tokens. `max_age` is checked from the last password sign-in, and refreshed password-grant tokens retain the original authentication time instead of treating a refresh as a new sign-in. Relying parties that expected the old claim set or times should check their assumptions.
- **Account and email rate limits always apply.** With `GOIABADA_AUTHSERVER_RATELIMITER_ENABLED=false`, the per-user limits for wrong OTP codes, account password checks, email verification codes, and verification mail still apply. So do the per-email limits: 100 wrong passwords per account per hour, shared by browser sign-in and the password grant, and limits on password-reset and registration mail to one address. The switch now controls only limits keyed by the client's IP address, including wrong passwords for one account from one network. The account-wide limit means someone who knows an email address can block its password sign-in for up to an hour; blocking the attacker at the proxy or CDN is the remedy. Clients should handle `429` responses. [Issue #503](https://github.com/leodip/goiabada/issues/503)
- **Text and web-origin validation changed.** Plain-text profile and admin fields reject `<` and `>` rather than silently stripping them; existing rows with those characters may need editing before they can be saved. Web origins are canonicalized; invalid or duplicate stored origins are removed by migration, and new writes must use canonical values. Case and accent comparisons are now consistent across the supported databases, which can change lookups that previously relied on a database collation.

## Admin and account API changes

| Contract | v1.7.0 action |
|---|---|
| Admin/account `ErrorResponse` | Read `error_code` and `error_description`; `error_args` is removed. OAuth protocol errors retain their protocol shape. |
| `GET /api/v1/admin/clients/{id}` | No longer returns a decrypted `clientSecret`. Use `GET /api/v1/admin/clients/{id}/secret` with `authserver:manage` when disclosure is required. |
| User responses | No longer embed `groups`, `permissions`, or `attributes`. Fetch the corresponding resource routes. |
| Redirect URI and web-origin records | Use lower-camel-case JSON keys such as `id`, `clientId`, `createdAt`, `uri`, and `origin` instead of the old Go-style spellings. |
| Account, user, and client session lists | Use `started` and `lastAccessed` RFC 3339 timestamps. The computed `durationSinceStarted`, `durationSinceLastAccessed`, `isValid`, and old timestamp fields are gone. Client session results include normalized `users` data. |
| `PUT /api/v1/admin/user-sessions/{sessionIdentifier}` | Removed. Use the remaining session endpoints to list or end sessions. |
| Replacement writes for user groups/permissions, group/client permissions, resource permissions, and client redirect URIs/web origins | Include the corresponding `expectedGroupIds`, `expectedPermissionIds`, `expectedPermissions`, `expectedRedirectURIs`, or `expectedWebOrigins` snapshot. Missing values get `400`; a stale snapshot gets `409 CONCURRENT_UPDATE`. An empty array is valid when clearing a list. |
| `PUT /api/v1/account/email` | Include `currentPassword`. The new address is saved immediately as unverified; password recovery will not use it until it is verified. |
| `PUT /api/v1/account/otp` | Send `otpCode` for the enrollment begun by the GET endpoint. `secretKey`, even `null`, is refused. |
| Audit data | Details use snake-case JSON keys and records include `requestId`; `createdAt` may include fractional seconds while remaining RFC 3339. Clients parsing or filtering audit rows should update. |

HTTP statuses for several admin errors have been corrected, and adding a group member now returns `201`. API consumers should handle the documented status and error code rather than assume the old response status. [Session response change](https://github.com/leodip/goiabada/pull/374) · [client secret change](https://github.com/leodip/goiabada/pull/497)

## Configuration and deployment changes

| Setting or behavior | What to change |
|---|---|
| `GOIABADA_ADMINCONSOLE_ISSUER`, `--adminconsole-issuer` | Remove them. The console discovers the issuer from the auth server's public settings. Even an empty issuer environment variable prevents startup. |
| `GOIABADA_ADMINCONSOLE_OAUTH_CLIENT_ID`, `--adminconsole-oauth-client-id` | Remove them. The console uses `admin-console-client`; a different or empty environment value prevents startup. Upgrade the auth server first so its public settings include the issuer. |
| `GOIABADA_ADMIN_PASSWORD` on a new database | Supply a password of at least 15 characters and at most 72 bytes that is not `changeme`. The old default is no longer accepted for first-run seeding; existing databases are unaffected. The first-run admin email default is now `admin@example.com`. |
| Session key rotation | Optional `GOIABADA_{AUTHSERVER,ADMINCONSOLE}_SESSION_AUTHENTICATION_KEY_PREVIOUS` and `_SESSION_ENCRYPTION_KEY_PREVIOUS` accept the previous pair while issuing sessions with the current pair. |
| Database startup and pool | `GOIABADA_DB_CREATE` defaults to `true`. New `GOIABADA_DB_MAX_OPEN_CONNS` (20), `MAX_IDLE_CONNS` (defaults to open count), `CONN_MAX_LIFETIME` (30m), and `CONN_MAX_IDLE_TIME` (5m) control non-SQLite pools. SQLite remains one connection. |
| Database TLS | `GOIABADA_DB_TLS_MODE` / `--db-tls-mode` accepts `disable`, `prefer`, `require`, `verify-ca`, or `verify-full` for MySQL, PostgreSQL, and SQL Server. The default `prefer` does not verify the certificate; on PostgreSQL and MySQL it can fall back to plaintext, while on SQL Server it encrypts the login and encrypts the session only when the server requires it. `require` encrypts without verification; `verify-ca` checks the signing authority; `verify-full` also checks the host name. `GOIABADA_DB_TLS_CA_FILE` / `--db-tls-ca-file` supplies trusted PEM authorities for the two verification modes. SQLite ignores both settings. [Database guide](https://goiabada.dev/deploy/database/#where-the-database-sits) |
| Self-registration on a new database | First-run settings now start with **User self registration enabled** off and **User self registration requires email verification** on. Set up SMTP before enabling the verified flow; an administrator can explicitly turn verification off instead. If verification is on but email is off, registration is unavailable and its GET and POST routes return `404` rather than creating unverified accounts. Previously sent activation links still work when email is off. Existing installations keep their settings; there is no migration. [Issue #526](https://github.com/leodip/goiabada/issues/526) |
| Logging and metrics | Each process accepts its own `LOG_LEVEL` and `LOG_FORMAT` environment variables; metrics are off by default. Set `GOIABADA_{AUTHSERVER,ADMINCONSOLE}_METRICS_ENABLED=true` and configure `LISTEN_HOST_METRICS` and `LISTEN_PORT_METRICS` (defaults `0.0.0.0`, ports `9190` and `9191`) to expose Prometheus metrics. |
| Translation overrides | `GOIABADA_I18N_OVERRIDES_DIR` points both processes to a directory containing `catalogs/`. |
| Startup validation | Malformed booleans, numbers, durations, time zones, and proxy ranges now fail startup instead of quietly taking defaults. Each binary accepts only its own command-line flags; remove flags for the other process. |

The auth server now checks on startup that its AES key can decrypt stored data. The admin console checks its client secret with the auth server before listening and waits while the auth server starts. A mismatched secret that previously led to request-time errors now prevents startup. [PR #296](https://github.com/leodip/goiabada/pull/296) · [PR #375](https://github.com/leodip/goiabada/pull/375)

The five hand-written `src/build/docker-compose-*.yml` samples were deleted. Generate new Compose files with `goiabada-setup`; keep your existing generated deployment and secrets when upgrading.

The release images use Alpine 3.24, Go 1.27.2, an embedded time-zone database, and UID `10001`.

## Improvements

- The auth server and admin console expose Prometheus request, runtime, and build metrics when enabled, plus structured text or JSON logging with configurable level. Audit records carry request IDs. Graceful shutdown drains listeners and post-response work.
- Account recovery and **email-verified** self-registration answer without revealing whether an address is registered. In that registration mode, the user chooses a password after following the link. An administrator can explicitly turn off verification; that mode still reveals an existing address and creates an unverified account immediately. Administrator-created users can receive a setup link valid for 24 hours. Password recovery requires a verified, enabled account. With email disabled, `/forgot-password` returns `404`.
- Admins can inspect and end user and client sessions, view richer audit logs, manage more client settings, and rotate secrets without exposing them in the normal client response. The setup wizard supports separate secret files, metrics, and a Gateway API Kubernetes deployment.
- The documentation site now has expanded deployment, upgrade, API, and troubleshooting guides. Pages ship their JavaScript and CSS locally. If you use `GOIABADA_AUTHSERVER_STATICDIR` or `GOIABADA_ADMINCONSOLE_STATICDIR`, refresh those copied assets and rebuild `main.css` with the v1.7.0 Tailwind sources so pages retain their styling.
