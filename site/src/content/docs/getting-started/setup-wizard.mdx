The **goiabada-setup** wizard is the easiest way to get Goiabada running. It generates configuration files with all credentials pre-configured.

## Download

Download the binary for your platform from the [releases page](https://github.com/leodip/goiabada/releases):

| Platform | Binary |
|----------|--------|
| Linux (x86_64) | [`goiabada-setup-linux-amd64`](https://github.com/leodip/goiabada/releases/latest/download/goiabada-setup-linux-amd64) |
| Linux (ARM64) | [`goiabada-setup-linux-arm64`](https://github.com/leodip/goiabada/releases/latest/download/goiabada-setup-linux-arm64) |
| macOS (Intel) | [`goiabada-setup-darwin-amd64`](https://github.com/leodip/goiabada/releases/latest/download/goiabada-setup-darwin-amd64) |
| macOS (Apple Silicon) | [`goiabada-setup-darwin-arm64`](https://github.com/leodip/goiabada/releases/latest/download/goiabada-setup-darwin-arm64) |
| Windows | [`goiabada-setup-windows-amd64.exe`](https://github.com/leodip/goiabada/releases/latest/download/goiabada-setup-windows-amd64.exe) |

The wizard will ask you a few questions:

1. **Deployment type**:
   - Local testing (HTTP) - for development
   - Production with reverse proxy - for Docker with Nginx/Cloudflare
   - Kubernetes cluster - generates Kubernetes manifests
   - Native binaries - generates environment file for running without Docker

2. **Database** - MySQL, PostgreSQL, SQL Server, or SQLite

3. **Domain names** - Your auth and admin console URLs (production/Kubernetes/native)

4. **Gateway traffic policy** (Kubernetes only) - The `externalTrafficPolicy` of Envoy Gateway's load balancer Service. `Cluster`, the default, works behind every load balancer, and Goiabada sees a node's address for every client; `Local`, with Envoy on every node as a DaemonSet, keeps the client's address at the cost of an Envoy pod per node. The answer decides the EnvoyProxy the wizard prints and the manifest's comments on which address the servers see (see [Kubernetes: Step 1](/production-deployment/kubernetes/#step-1-install-envoy-gateway)). `--gateway-traffic-policy=cluster` or `=local` answers without the prompt

5. **Network policy** (Kubernetes only) - Whether NetworkPolicies admit only Envoy's namespace to both servers, and the admin console to the auth server. No, the default, emits none, and any pod in the cluster can then reach both servers; yes needs a CNI that enforces NetworkPolicy, and refuses in-cluster callers of the auth server's Service until you admit their namespace (see [Kubernetes: who can reach Goiabada](/production-deployment/kubernetes/#who-can-reach-goiabada)). `--network-policy` answers yes without the prompt

6. **Reverse proxy** (native binaries only) - Whether a reverse proxy on the same machine, such as Nginx, forwards to Goiabada. Yes, the default, has both servers listen on `127.0.0.1` and trust its forwarded headers alone; no has them listen on every interface, trust no forwarded header, and wait for you to configure HTTPS. `--local-proxy=false` answers no without the prompt

7. **Rate limiter** (production, Kubernetes and native binaries) - Whether to turn on the auth server's built-in [rate limiter](/reference/environment-variables/#security-settings), which the server leaves off by default. Yes is the default, except for Kubernetes under the `Cluster` traffic policy: there Goiabada sees a node's address for every client, so the per-IP limits would count every user arriving through one node together and throttle sign-ins on a busy site, while the limits on failed passwords and codes hold under either policy. The answer is written as `GOIABADA_AUTHSERVER_RATELIMITER_ENABLED`, `true` or `false`, under a comment. `--rate-limiter=true` or `=false` answers without the prompt; left out, the deployment's default applies. Local testing never asks and leaves it off. With the limiter on, the auth server logs a warning about its proxy trust at every start of a production Compose or Kubernetes deployment, which is expected behind one proxy (see [client IP resolution](/production-deployment/reverse-proxy/#client-ip-resolution-and-spoofing-protection))

8. **Admin credentials** - Email and password for the first admin user. The password is read without
   echo (see [Passwords and the terminal](#passwords-and-the-terminal))

9. **Database password** - A strong password, generated if you press Enter. The prompt shows the
   generated default as `[generated]`, never its value, and reads what you type without echo

## What gets generated

### For Docker deployments (options 1 and 2)

The wizard creates a `docker-compose.yml` file with:

- Database service configured
- Both auth server and admin console ready to start

and, beside it, a `docker-compose.override.yml` file holding every secret, under the service that reads
it:

- All session keys and the AES key cryptographically generated
- OAuth client credentials pre-configured
- The admin and database passwords

Docker Compose merges the override into `docker-compose.yml` by itself, so you start both with:

```bash
docker compose up -d
```

`docker-compose.yml` holds no secret and can be committed; keep `docker-compose.override.yml` out of
version control. With `--output` naming a file, the override is that name with `.override` before its
extension, so a `compose.yaml` gets the `compose.override.yaml` Compose looks for; any other name is
started with both files named, `docker compose -f <file> -f <override> up -d`, as the wizard prints.

### For Kubernetes (option 3)

The wizard creates a `goiabada-k8s.yaml` file with:

- Namespace (labelled to warn about pods that break the restricted Pod Security Standard)
- One ConfigMap per server, holding only what that server reads
- Deployments (auth server and admin console), each with a PodDisruptionBudget
- Services
- Gateway and HTTPRoutes (TLS by cert-manager)
- NetworkPolicies, one per Deployment, if you asked for them

and, beside it, a `goiabada-secrets.yaml` file with the Secrets the manifest reads, pre-generated and
base64 encoded: the AES key alone in `goiabada-encryption-key`, so access to it can be restricted on its
own, and every other secret in `goiabada-secrets`. With `--output` naming a file, the Secrets file is
that name with `-secrets` before its extension.

Deploy both with one command, the manifest first, since it creates the namespace the Secrets are in:

```bash
kubectl apply -f goiabada-k8s.yaml -f goiabada-secrets.yaml
```

The manifest holds no secret and can be committed; keep `goiabada-secrets.yaml` out of version control.

### For native binaries (option 4)

The wizard creates a `goiabada.env` file with:

- All environment variables for both auth server and admin console
- Session keys cryptographically generated
- OAuth client credentials pre-configured
- Database connection settings
- Listen hosts and proxy trust following your reverse proxy answer, under a comment saying whom each server trusts (see [native binaries: reverse proxy](/production-deployment/native-binaries/#reverse-proxy))

The file is the secret material itself: keep it out of version control.

Use with:

```bash
set -a && . ./goiabada.env && set +a && ./goiabada-authserver
set -a && . ./goiabada.env && set +a && ./goiabada-adminconsole
```

Every file the wizard writes is readable by its owner alone (mode `0600`), the secret-free ones too.
When it writes into a git working tree, it warns and gives the line to add to the tree's
`.gitignore`; it never edits one itself. It also warns when it generates the AES key: back it up
separately from the database, since without it the client secrets, SMTP credentials, OTP seeds and
signing keys the database holds cannot be recovered.

## Passwords and the terminal

The wizard prints no secret. Earlier versions printed the generated admin and database passwords, the
database password even when you passed it with `--db-password`, and the admin password again at the
end as `Login with: <email> / <password>`, and they echoed both password prompts. Whatever a terminal
shows reaches its scrollback, screen recordings, and the log of every CI job that runs the wizard.

Now each password step says only whether the password was set or generated, and where it is stored,
and the summary shows `(set)` or `(generated)`. The completion message says where to find the admin
password: `GOIABADA_ADMIN_PASSWORD` in `docker-compose.override.yml` or `goiabada.env`, or, for
Kubernetes, the command that reads it back out of the cluster:

```bash
kubectl get secret goiabada-secrets -n goiabada -o jsonpath='{.data.admin-password}' | base64 -d
```

At a terminal, the password prompts read without echo and keep nothing in the line history, so the
up arrow at a later prompt does not recall a password. Input piped to the wizard is read as before.
There is no confirmation prompt: the file holds what you typed, and a mistyped database password fails
the connection test.

Every secret is in a file only its owner can read, so you never need to copy one from the terminal.
Prefer the prompt, or a generated password, to `--admin-password` and `--db-password`: a password
passed as a flag lands in your shell history and, while the wizard runs, in the process list, which
other accounts on the machine can usually read. In non-interactive mode, leave both flags out and the
wizard generates the passwords into the secrets file.
