This guide covers deploying Goiabada to a Kubernetes cluster.

<Aside type="tip" title="Flexibility">
Kubernetes environments vary significantly. This guide presents **one tested recipe** using Envoy Gateway and cert-manager, but you're free to use any Gateway API implementation or TLS certificate solution that fits your infrastructure.

The key Goiabada-specific requirements are covered in the [What Goiabada needs](#what-goiabada-needs) section.
</Aside>

## What Goiabada needs

Regardless of your Kubernetes setup, Goiabada requires:

| Requirement | Details |
|-------------|---------|
| **HTTPS access** | Both auth server and admin console must be accessible via HTTPS |
| **Two hostnames** | Separate domains/subdomains for auth server and admin console |
| **Shared database** | MySQL, PostgreSQL, or SQL Server (SQLite not supported - pods need a shared database) |
| **Empty database** | For fresh deployments, the database must be empty - Goiabada seeds it with OAuth clients configured for your specific URLs |
| **Proxy headers** | The generated manifests trust one proxy hop, the gateway, to resolve the client IP (see [client IP and proxy trust](#client-ip-and-proxy-trust)) |

<Aside type="caution" title="Database must be empty">
Goiabada automatically seeds the database on first startup with an admin user and OAuth clients configured for your URLs. If you redeploy with different URLs against an existing database, authentication will fail because the OAuth client redirect URIs won't match.

**Options if redeploying with different URLs:**
1. Use a fresh/empty database
2. Keep the same URLs as before
3. Manually update the OAuth client redirect URIs in the database
</Aside>

## Architecture

```
Internet → Gateway/Ingress (HTTPS/TLS) → {
    auth.example.com    → goiabada-authserver Service (9090) → Pods
    admin.example.com   → goiabada-adminconsole Service (9091) → Pods
}
```

The setup wizard generates:
- **Namespace**: Isolated environment for Goiabada resources, labelled to warn about any pod that
  breaks the restricted Pod Security Standard (see [Pod security](#pod-security))
- **Secret**: Database password, session keys, OAuth client secret (base64 encoded)
- **ConfigMaps**: `goiabada-authserver-config` and `goiabada-adminconsole-config`, one per server,
  each holding only the variables that server reads. The three URLs are in both, written from the
  same answers, so if you change one, change it in both
- **Deployments**: Auth server and admin console, hardened to the restricted standard, with health
  checks, resource limits, a rolling update strategy and a spread over nodes
- **PodDisruptionBudgets**: One per Deployment (see [Disruptions](#disruptions-and-spread))
- **Services**: ClusterIP services for internal routing
- **NetworkPolicies**, if you ask for them: one per Deployment, admitting only Envoy and the admin
  console (see [Who can reach Goiabada](#who-can-reach-goiabada))
- **Gateway and HTTPRoutes**: External access with TLS termination

## Prerequisites

- A Kubernetes cluster
- `kubectl` configured to access your cluster
- A database server (MySQL, PostgreSQL, or SQL Server) - can be in-cluster or external
- Two domain names for auth server and admin console

## Example setup: Envoy Gateway + cert-manager

This is the recipe we tested. Adapt as needed for your environment.

<Aside type="caution" title="For clean clusters">
This guide assumes a **fresh cluster** without an existing Gateway API implementation or cert-manager installation.

If your cluster already has these components:
- **Skip the installation steps** for components you already have
- **Verify compatibility** with your existing configuration
- **Do not blindly apply** the commands below as they may conflict with or overwrite your existing setup

When in doubt, consult your cluster administrator before proceeding.
</Aside>

### Step 1: Install Envoy Gateway

Envoy Gateway's install brings the Gateway API CRDs:

```bash
kubectl apply --server-side -f https://github.com/envoyproxy/gateway/releases/download/v1.9.1/install.yaml
```

<Aside type="note">
Check the [Envoy Gateway releases](https://github.com/envoyproxy/gateway/releases) for the latest version.
</Aside>

Wait for it to be ready:

```bash
kubectl wait --timeout=5m -n envoy-gateway-system \
  deployment/envoy-gateway --for=condition=Available
```

Then create the `eg` GatewayClass the generated manifest names, backed by an EnvoyProxy that sets
the traffic policy of the load balancer Service in front of Envoy. The wizard asks which policy you
want and prints the matching file; both are below. The policy decides which address Goiabada sees
for a client, and so what its rate limits, audit records and session records count.

**`Cluster`, the wizard's default**, works behind every load balancer: the load balancer may send a
connection to any node, and kube-proxy forwards it to an Envoy pod wherever one runs. The cost is
that the forwarding node replaces the client's address with its own, so Envoy, and Goiabada behind
it, see a node's address for every client. Save as `gatewayclass.yaml`:

```yaml
apiVersion: gateway.envoyproxy.io/v1alpha1
kind: EnvoyProxy
metadata:
  name: goiabada-proxy
  namespace: envoy-gateway-system
spec:
  provider:
    type: Kubernetes
    kubernetes:
      envoyService:
        externalTrafficPolicy: Cluster
---
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: eg
spec:
  controllerName: gateway.envoyproxy.io/gatewayclass-controller
  parametersRef:
    group: gateway.envoyproxy.io
    kind: EnvoyProxy
    name: goiabada-proxy
    namespace: envoy-gateway-system
```

**`Local`, with Envoy on every node** (`--gateway-traffic-policy=local`), keeps the client's
address: a node delivers a connection only to an Envoy pod on that same node, so nothing rewrites
its source. Under `Local` a node with no Envoy pod drops the traffic the load balancer sends it,
which is why Envoy Gateway's own default, `Local` with a one-pod Deployment, can time out on some
clouds. Running Envoy as a DaemonSet puts a pod on every node, at the cost of one Envoy pod, with
its CPU and memory, per node.
Save this as `gatewayclass.yaml` instead:

```yaml
apiVersion: gateway.envoyproxy.io/v1alpha1
kind: EnvoyProxy
metadata:
  name: goiabada-proxy
  namespace: envoy-gateway-system
spec:
  provider:
    type: Kubernetes
    kubernetes:
      envoyDaemonSet: {}
      envoyService:
        externalTrafficPolicy: Local
---
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: eg
spec:
  controllerName: gateway.envoyproxy.io/gatewayclass-controller
  parametersRef:
    group: gateway.envoyproxy.io
    kind: EnvoyProxy
    name: goiabada-proxy
    namespace: envoy-gateway-system
```

An empty `envoyDaemonSet` is a DaemonSet with every default; an EnvoyProxy takes either it or
`envoyDeployment`, not both. This variant follows Envoy Gateway v1.9.1's API and has not been tried
on a load-balanced cluster by the project, so check that a pod runs on every node after applying it:
`kubectl get daemonset -n envoy-gateway-system`.

A third route keeps the client's address without an Envoy pod per node: Proxy Protocol, where the
load balancer prepends the client's address to each connection and Envoy reads it. It needs
annotations on the load balancer Service that differ from cloud to cloud, which the wizard cannot
know, so it does not offer it; Envoy Gateway's
[client traffic policy](https://gateway.envoyproxy.io/docs/tasks/traffic/client-traffic-policy/)
documentation covers the Envoy side.

<Aside type="caution" title="The EnvoyProxy and GatewayClass are cluster-wide">
Every Gateway of class `eg` shares them. On a cluster that already runs Envoy Gateway, the traffic
policy belongs to whoever runs it: agree it with them rather than apply either file over theirs, and
answer the wizard's question with the policy the cluster actually uses, since the manifest's
comments follow it.
</Aside>

```bash
kubectl apply -f gatewayclass.yaml
```

### Step 2: Install cert-manager

Install it after Envoy Gateway and turn on its Gateway API support:

```bash
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.21.2/cert-manager.yaml
kubectl -n cert-manager patch deployment cert-manager --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--enable-gateway-api"}]'
```

<Aside type="note">
Check the [cert-manager releases](https://github.com/cert-manager/cert-manager/releases) for newer versions.
</Aside>

Wait for it to be ready:

```bash
kubectl -n cert-manager rollout status deployment/cert-manager --timeout=5m
kubectl -n cert-manager rollout status deployment/cert-manager-webhook --timeout=5m
kubectl -n cert-manager rollout status deployment/cert-manager-cainjector --timeout=5m
```

### Step 3: Create ClusterIssuer for Let's Encrypt

Save as `letsencrypt-issuer.yaml`:

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: your-email@example.com  # Replace with your email
    privateKeySecretRef:
      name: letsencrypt-prod
    solvers:
    - http01:
        gatewayHTTPRoute:
          parentRefs:
          - name: goiabada
            namespace: goiabada  # Your Kubernetes namespace
            kind: Gateway
```

Apply it:

```bash
kubectl apply -f letsencrypt-issuer.yaml
```

### Step 4: Configure your database

Goiabada needs a shared database (SQLite is not supported for Kubernetes). Options include:

- **Managed services**: AWS RDS, Google Cloud SQL, Azure Database, Supabase, PlanetScale, Neon
- **Self-hosted**: Deploy MySQL/PostgreSQL in your cluster or on a VM

<Aside type="caution" title="Managed database tips">
**IPv6 Connectivity**: Some services (like Supabase) use IPv6 for direct connections. If your cluster doesn't support IPv6, use the **connection pooler endpoint** instead.

**Network Access**: Ensure your database allows connections from your Kubernetes cluster's IP range.
</Aside>

**Example (Supabase):** Use the **connection pooler** (not direct connection):
```
Host: aws-0-us-east-1.pooler.supabase.com
Port: 5432
User: postgres.your-project-ref
```

### Step 5: Generate and deploy Goiabada

Use the [setup wizard](/getting-started/setup-wizard/):

```bash
./goiabada-setup
```

<Steps>
1. Select **"3. Kubernetes cluster"**
2. Choose your database type
3. Enter your domain names (e.g., `https://auth.example.com`)
4. Enter your Kubernetes namespace (default: `goiabada`)
5. Choose the gateway's traffic policy, `Cluster` (default) or `Local` (see [Step 1](#step-1-install-envoy-gateway))
6. Choose whether NetworkPolicies restrict who can reach Goiabada (default: no; see [Who can reach Goiabada](#who-can-reach-goiabada))
7. Configure admin credentials
8. Enter your database connection details
</Steps>

The wizard will:
- Test database connectivity
- **Check if the database is empty** (warns you if it contains existing Goiabada data)
- Generate the Kubernetes manifests in `goiabada-k8s.yaml`, which holds no secret, and the Secrets they
  read in `goiabada-secrets.yaml` beside it, the AES key in a Secret of its own, `goiabada-encryption-key`

Deploy both, the manifest first, since it creates the namespace the Secrets are in:

```bash
kubectl apply -f goiabada-k8s.yaml -f goiabada-secrets.yaml
```

Keep `goiabada-secrets.yaml` out of version control; the manifest can be committed. The wizard warns
when it writes into a git working tree, and gives the line to add to its `.gitignore`. Back up the AES
key separately from the database: without it, the client secrets, SMTP credentials, OTP seeds and
signing keys the database holds cannot be recovered.

The wizard prints no secret, a generated admin password included. Read the admin password back out of
the cluster when you first sign in:

```bash
kubectl get secret goiabada-secrets -n goiabada -o jsonpath='{.data.admin-password}' | base64 -d
```

### Step 6: Configure DNS

After deploying, get the Gateway's address:

```bash
kubectl get gateway goiabada -n goiabada -o jsonpath='{.status.addresses[0].value}'
```

Create DNS A records pointing to this IP:

| Record | Value |
|--------|-------|
| `auth.example.com` | `<ADDRESS>` |
| `admin.example.com` | `<ADDRESS>` |

<Aside type="tip">
DNS propagation can take a few minutes. Verify with `nslookup auth.example.com`
</Aside>

### Step 7: Verify deployment

```bash
# Check pods
kubectl get pods -n goiabada

# Check the Gateway (should show ADDRESS and PROGRAMMED=True) and its routes
kubectl get gateway,httproute -n goiabada

# Check certificates (should show READY=True after DNS propagates)
kubectl get certificates -n goiabada
```

Expected output:
```
NAME                                     READY   STATUS    RESTARTS   AGE
goiabada-authserver-xxxxx-xxxxx          1/1     Running   0          1m
goiabada-adminconsole-xxxxx-xxxxx        1/1     Running   0          1m
```

## Troubleshooting

### Certificates not issuing

```bash
# Check certificate status
kubectl describe certificate -n goiabada

# Check challenges
kubectl get challenges -n goiabada
kubectl describe challenges -n goiabada
```

| Problem | Solution |
|---------|----------|
| DNS not resolving | Verify DNS A records point to the Gateway's address |
| Port 80 not accessible | Check firewall rules; ACME HTTP-01 needs port 80 |
| Challenge timeout | See "Connectivity Issues" below |

### Connectivity issues (port 80 not responding)

Under `externalTrafficPolicy: Local`, a node with no Envoy pod drops what the load balancer sends
it, so a single Envoy pod leaves most nodes answering nothing. Under the `Cluster` EnvoyProxy of Step
1 that cannot happen. Under the `Local` one, check that the DaemonSet runs a pod on every node:

```bash
kubectl get daemonset -n envoy-gateway-system
```

If your load balancer still cannot reach Envoy under `Local`, switch to the `Cluster` file of Step 1,
which has no `envoyDaemonSet`; Goiabada then sees a node's address for every client.

If your `eg` GatewayClass has no `parametersRef` to the EnvoyProxy, apply Step 1's file:

```bash
kubectl apply -f gatewayclass.yaml
```

Then delete any failed certificate challenges to trigger a retry:

```bash
kubectl delete challenges -n goiabada --all
```

### OAuth "Invalid redirect_uri" error

This means the database has OAuth clients configured for different URLs than you're using.

**Solutions:**
1. Use a fresh/empty database
2. Use the same URLs as the previous deployment
3. Manually update `redirect_uris` in the `clients` table

### Database connection errors

```bash
# Check pod logs
kubectl logs -n goiabada deployment/goiabada-authserver

# Test connectivity from within cluster
kubectl run -it --rm debug --image=busybox --restart=Never -- \
  nc -zv your-db-host 5432
```

### Pods in CrashLoopBackOff

```bash
kubectl logs -n goiabada deployment/goiabada-authserver --previous
```

Common causes:
- Database connection failed
- Invalid configuration values
- Database not empty with mismatched URLs

## High availability

For production deployments:

### Scale replicas

```bash
kubectl scale deployment goiabada-authserver -n goiabada --replicas=3
kubectl scale deployment goiabada-adminconsole -n goiabada --replicas=2
```

Every auth server pod opens its own connection pool, of at most `GOIABADA_DB_MAX_OPEN_CONNS`
connections (20 unless you set it), against the one database they share. Before you scale, check
that the pods fit under the database's connection limit:

```text
(replicas + surge) × GOIABADA_DB_MAX_OPEN_CONNS + headroom < max_connections
```

- **Surge** is the extra pods a rolling update runs beside the old ones. The generated Deployments
  set `maxSurge: 1` and `maxUnavailable: 0`: a rollout starts one new pod, waits for it to be ready,
  and only then stops an old one, so three replicas briefly run four and never fewer than three.
- **Headroom** is every other connection the database must accept: the `migrate` subcommand, the
  maintenance connection a starting pod opens to create the database when `GOIABADA_DB_CREATE` is
  on, your own sessions, and any other application on the same server. The admin console opens
  none.
- With a HorizontalPodAutoscaler, **replicas is its `maxReplicas`**, not today's count (see
  [Autoscaling](#autoscaling)).

With the defaults, three replicas and one surge pod make 4 × 20 = 80 connections. A stock
PostgreSQL allows 100, less 3 reserved for superusers, which leaves 17 for the headroom; a stock
MySQL allows 151. Lower `GOIABADA_DB_MAX_OPEN_CONNS`, or raise `max_connections`, until the
arithmetic holds for the replica count you run.

A capped pool trades one failure for another, deliberately: when every connection of a pod is busy,
its next request waits for one to be released, until the client or the gateway gives up, rather
than the database refusing a new connection to every pod at once. Raising replicas without raising
`max_connections` does not add capacity at the database: it moves the bottleneck from the pods'
queues to the database's refusals. The pool settings are in the
[environment variable reference](/reference/environment-variables/#database-configuration).

### Disruptions and spread

Each Deployment has a PodDisruptionBudget with `maxUnavailable: 1`, so a voluntary disruption (a
`kubectl drain`, a node pool upgrade, a cluster autoscaler removing a node) evicts at most one of its
pods at a time. The budget does not stop that one: at the generated `replicas: 1`, a drain evicts the
only pod, and the server is down until its replacement is scheduled elsewhere and ready. The rollout
strategy does not help here, because an eviction is not a rollout and starts no surge pod first. To
keep serving through a drain, run at least two replicas; the same budget then keeps all but one
serving at any replica count, so it needs no change when you scale.

Each pod template also spreads its pods over nodes (`topologySpreadConstraints` on
`kubernetes.io/hostname`, `maxSkew: 1`, `whenUnsatisfiable: ScheduleAnyway`). At one replica it does
nothing. At three on three nodes it places one per node, so losing or draining a node takes one pod
rather than all of them; on fewer nodes than replicas it still schedules every pod rather than
leaving one pending.

### Autoscaling

The manifest runs one replica of each server and emits no HorizontalPodAutoscaler. You can add one,
but settle two things first:

- **The database's connections.** An autoscaler's `maxReplicas`, plus the one surge pod, is the
  count the [connection arithmetic](#scale-replicas) above has to hold for, because it may scale out
  to it at the worst moment, under load. Size `GOIABADA_DB_MAX_OPEN_CONNS` and the database's
  `max_connections` for that count before you set it.
- **What to scale on.** CPU is the auth server's bottleneck under a burst of sign-ins (see
  [Resource limits](#resource-limits)), so a CPU target relative to the `100m` request is a
  reasonable signal; the admin console verifies no passwords and rarely needs more than one or two
  replicas.

If the rate limiter is on, more replicas also multiply its per-pod limits (see below).

### Rate limiting across replicas

The built-in rate limiter is off in the server by default (`GOIABADA_AUTHSERVER_RATELIMITER_ENABLED`).
The wizard asks whether to turn it on, and writes the answer into the auth server's ConfigMap, under
a comment, either way; `--rate-limiter=true` or `=false` answers without the prompt. Its default
follows the traffic policy of Step 1:

- **Under `Cluster`, off.** Goiabada sees a node's address for every client, so a per-IP limit
  counts every user the load balancer sends through one node together: 30 password posts a minute
  and 20 forgot-password requests per 5 minutes per node, for example, which throttles sign-ins on a
  busy site. The limits on failed passwords and codes would still hold, being keyed on the email or
  the user rather than the address; turn the limiter on if those matter more to you than the per-IP
  limits cost.
- **Under `Local`, on.** Goiabada sees each client's address, so each per-IP limit counts one
  client.

With the limiter on, not every limit holds across replicas:

- **Shared:** the limits on credential guessing, which count failed passwords (at sign-in and
  through the password grant), failed OTP codes, failed account password checks and failed email
  verification codes. On PostgreSQL, MySQL and SQL Server they are counted in the database every
  pod shares, so three replicas still allow one budget, and a rollout does not reset it. If the
  database cannot answer such a check within 5 seconds, the request is answered with a server error
  rather than let through.
- **Per pod:** every other limit, the per-IP limits and the limits on outbound mail. Behind the
  Service, three replicas give a client up to three times each budget, and a rollout resets them.
  For a request limit across the whole deployment, use the gateway's own rate limiting.
- **The per-IP limits depend on the client IP.** The generated manifests trust one proxy hop with
  `GOIABADA_AUTHSERVER_TRUSTED_PROXIES` empty. Under the `Cluster` traffic policy of Step 1 the
  address Goiabada sees is a node's, so a per-IP limit counts everyone arriving through one node
  together; under `Local` it is the client's. See [client IP and proxy trust](#client-ip-and-proxy-trust) before relying on one.

The budgets are in the [rate limiting table](/reference/environment-variables/#security-settings).

**The startup warning.** With the limiter on, the auth server logs a `rate limiter configuration
warning` at every start, saying it trusts one proxy hop with no `GOIABADA_AUTHSERVER_TRUSTED_PROXIES`.
With the generated manifest that is expected. The server cannot see what is in front of it, and the
record is there for the cases where one hop is not sound: a proxy that passes `X-Forwarded-For`
through untouched, or a caller that reaches the Service around the proxy. Envoy appends to the
header, so one hop is sound behind it (see [client IP and proxy trust](#client-ip-and-proxy-trust)).
Once Envoy is the only gateway in front, and the [NetworkPolicies](#who-can-reach-goiabada) or your
own controls keep other pods off the Services, the warning has been checked and can be left as it is.

### Resource limits

Both containers request `100m` of CPU and `128Mi` of memory, and are limited to `500m` and `512Mi`:

```yaml
resources:
  requests:
    memory: "128Mi"
    cpu: "100m"
  limits:
    memory: "512Mi"
    cpu: "500m"
```

What the CPU numbers mean for the auth server comes down to one operation. A sign-in costs one
bcrypt password check at cost 10, about 35 ms of CPU on a modern core, which no limit slows when it
runs alone. Under the `500m` limit a pod verifies about 14 passwords a second, and a burst queues
behind that: measured, 16 sign-ins arriving at once took about 1.2 s to complete, and every other
request on that pod waited with them. Cloud vCPUs are often slower than the core measured, and the
`100m` request is all the scheduler guarantees when the node is busy. If your sign-in peak is higher,
raise the CPU limit or add replicas. The limit stays because it bounds a server an attacker can make
spend CPU on purpose, by sending passwords to check.

The admin console verifies no passwords and needs less; it carries the same numbers for simplicity.

## Pod security

Every generated container runs with this `securityContext`, which is everything the restricted
[Pod Security Standard](https://kubernetes.io/docs/concepts/security/pod-security-standards/)
requires and a read-only root filesystem besides:

```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  runAsGroup: 10001
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities:
    drop: ["ALL"]
  seccompProfile:
    type: RuntimeDefault
```

uid 10001 is the user both images run as (see [the user the images run
as](/production-deployment/#the-user-the-images-run-as)). No writable volume is mounted, because
neither server writes to its filesystem under Kubernetes: the legacy bootstrap file is not used here,
and the auth server's one other write, Go spilling a picture upload over its size limit to `/tmp`,
fails on the read-only root and is refused as `FILE_TOO_LARGE` rather than by the image check, a 400
either way.
A certificate or customization you mount from a Secret or ConfigMap volume is readable by default
(mode `0644`); if you set a stricter `defaultMode`, keep it readable by uid or gid 10001.

Both pod specs also set:

- `automountServiceAccountToken: false`, because neither server calls the Kubernetes API, so a
  compromised pod gets no API credential.
- `enableServiceLinks: false`, because Kubernetes would otherwise inject variables for every Service
  in the namespace, and two of the generated Services are named so that those variables begin with
  `GOIABADA_` (`GOIABADA_AUTHSERVER_PORT`, `GOIABADA_ADMINCONSOLE_SERVICE_HOST` and the rest), which
  neither server reads.

The generated Namespace is labelled `pod-security.kubernetes.io/warn: restricted` and
`pod-security.kubernetes.io/audit: restricted`. `kubectl apply` then prints a warning, and the API
server writes an audit entry, for any pod in the namespace that breaks the standard, Goiabada's own
included, and nothing is refused. It does not enforce, because the wizard accepts an existing
namespace whose other workloads `kubectl apply` would then start refusing. If you own the namespace
outright, add the enforcing label once you have checked that everything else running there meets
the standard, including cert-manager's HTTP-01 solver pods, which run in it while a certificate is
issued:

```bash
kubectl label namespace goiabada pod-security.kubernetes.io/enforce=restricted
```

## Client IP and proxy trust

Goiabada keys its rate limits, audit records and session records on the client IP, which behind
the gateway it reads from `X-Forwarded-For`. Each generated ConfigMap sets its server's pair side by
side, under a comment saying why:

```yaml
GOIABADA_AUTHSERVER_TRUST_PROXY_HEADERS: "true"
GOIABADA_AUTHSERVER_TRUSTED_PROXIES: ""
```

With the headers trusted and the list empty, Goiabada trusts one hop and takes the client from the
rightmost `X-Forwarded-For` entry. Envoy appends the address it received each connection from to
that header, so the rightmost entry is Envoy's own observation: whatever a client sends in
`X-Forwarded-For` ends up to its left and is never read. Which address Envoy observes depends on the
traffic policy of Step 1: under `Cluster`, a node's; under `Local` with Envoy on every node, the
client's. The comment above each pair in the manifest says which, following your answer to the
wizard.

**Why the list is empty.** A trusted-proxy list makes Goiabada walk `X-Forwarded-For` from the right
past every address in it. The lists that come to mind for a cluster both go wrong here. The private
ranges hold the node addresses Envoy records under `Cluster`, so Goiabada would walk past Envoy's
entry and adopt whatever the client put to its left. The pod CIDR does the same on clusters where
pods and nodes share a subnet, as on EKS with the VPC CNI and with Azure CNI. One gateway needs no
list.

**When to set it.** Set `GOIABADA_AUTHSERVER_TRUSTED_PROXIES` and
`GOIABADA_ADMINCONSOLE_TRUSTED_PROXIES` only when a CDN or a second load balancer that appends
`X-Forwarded-For` sits in front of Envoy. Name every hop you control, the Envoy pods included:
Goiabada reads the forwarded headers only from a connection whose address is in the list.

**What no list stops.** A pod in the cluster that calls the `goiabada-authserver` or
`goiabada-adminconsole` Service directly, around Envoy, connects from its own address and can send
any `X-Forwarded-For` it likes, choosing the address it is rate limited and audited under. No
trusted-proxy list prevents that, since Envoy's pods are pods too; a NetworkPolicy admitting only
Envoy's namespace does (see [Who can reach Goiabada](#who-can-reach-goiabada)).

See [client IP resolution](/production-deployment/reverse-proxy/#client-ip-resolution-and-spoofing-protection)
for how the resolution works, and the startup warning the auth server logs about it when the rate
limiter is on.

## Who can reach Goiabada

Without a NetworkPolicy, any pod in the cluster can call the `goiabada-authserver` and
`goiabada-adminconsole` Services directly, around Envoy. Besides reaching the admin console from
inside the cluster, such a pod chooses the address it is rate limited and audited under, by sending
its own `X-Forwarded-For` (see [client IP and proxy trust](#client-ip-and-proxy-trust)). The wizard
asks whether to close that; the answer is no unless you say yes, or pass `--network-policy`.

On yes, the manifest carries one ingress-only NetworkPolicy per Deployment:

| Pods | Admitted on | From |
|------|-------------|------|
| `goiabada-authserver` | TCP 9090 | Envoy's namespace, `envoy-gateway-system`; the admin console's pods |
| `goiabada-adminconsole` | TCP 9091 | Envoy's namespace, `envoy-gateway-system` |

Envoy's namespace is selected by its `kubernetes.io/metadata.name` label, which Kubernetes sets on
every namespace. `envoy-gateway-system` is where Envoy Gateway runs its proxies by default; if yours
runs them elsewhere, change the name in both policies. The kubelet's health probes come from the
pod's own node, which a NetworkPolicy cannot block, and cert-manager's HTTP-01 solver pods carry
other labels, so neither is affected.

Before you answer yes, check two things:

- **Your CNI enforces NetworkPolicy.** Calico and Cilium do. Some clusters' default network plugin
  does not, or does only once enforcement is turned on in the cluster's settings; there the policies
  are accepted and do nothing.
- **Nothing else in the cluster calls the auth server through its Service.** A resource server that
  fetches `/certs` or calls `/userinfo` at `http://goiabada-authserver.goiabada:9090` is refused once
  the policy applies, and the connection times out rather than being refused. Admit its namespace
  by adding a peer to the auth server's policy, as its comment shows:

  ```yaml
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: envoy-gateway-system
    - podSelector:
        matchLabels:
          app: goiabada-adminconsole
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: my-resource-server
  ```

  A workload that calls the auth server's public URL goes through Envoy and needs nothing.

The policies state no egress rules, so they restrict nothing the servers connect to. An egress rule
would have to name every destination, and two cannot be named: the SMTP host and port are settings
in the database, changed in the admin console, and the database host is often a DNS name, while a
NetworkPolicy selects only pods, namespaces and IP blocks. A rule written for today's addresses
would cut email or the database when either moved.

To see what the policies admit:

```bash
kubectl describe networkpolicy -n goiabada
```

## Health endpoints

Both services expose a health endpoint, and the generated manifest points every probe at it:

- Auth server: `http://goiabada-authserver:9090/health`
- Admin console: `http://goiabada-adminconsole:9091/health`

`/health` answers `200` with the body `healthy` whenever the process is up and listening. That is
all it tells you. It does not read the database, the settings or the session, and the admin
console's does not call the auth server, so it keeps answering `200` while the database or the auth
server is down. Watch the applications' own error records, or your database's monitoring, for
those.

That is deliberate. Every auth server pod shares one database and every admin console pod shares
one auth server, so a probe that checked either would fail on every pod at the same moment: a
liveness probe would restart them all at once, and a readiness probe would take every pod out of
the Service together, so clients would get the gateway's "no healthy upstream" in place of the
application's own error and recovery would wait a probe period longer. A pod that cannot reach the
database at start never answers `/health` at all, because the auth server opens and migrates the
database before it listens.

## First start and upgrades

The auth server does its database work before it listens: it opens the database, runs every
outstanding migration, and on a first start seeds the empty database. Until that is done `/health`
does not answer, so the generated manifest gives each container a startup probe on it, every 5
seconds with 60 failures allowed: up to 5 minutes to start. Liveness and readiness wait for the
startup probe's first success, so neither counts a slow start against the pod, and once it
succeeds they take over at their own periods. The admin console gets the same probe and starts in
seconds.

With several replicas, the first pod to start takes the migration lock and migrates; the others
wait for the lock, then find the schema current and start. Every pod's wait counts against its own
startup budget, so the budget must exceed the longest migration an upgrade runs. If yours takes
longer, as it can on a large installation, raise the startup probe's `failureThreshold` on the auth
server's container until `failureThreshold × periodSeconds` covers it; otherwise Kubernetes restarts
the container before the migration finishes. Leave liveness on `/health` with its own thresholds.

A pod stopped while it starts, because it was deleted or its startup budget ran out, stops cleanly:
a wait for the database or the migration lock ends at once, a migration file already running runs to
its end and the next does not start, and the auth server exits 0 with the schema clean at the version
it reached, which the next start carries on from. The [database
page](/production-deployment/database/#schema-migrations-and-rollback) has the details and the
records. The grace period below bounds that too: a single migration file running longer than 65
seconds is ended by SIGKILL mid-file, leaving the schema dirty, so the startup budget is what has to
cover the longest migration, not the grace period.

## Stopping and the grace period

When a pod is deleted (a rollout, a scale-down, a node drain), Kubernetes removes it from the
Service and starts stopping its containers at the same moment. The generated manifest gives both
containers a five-second pause before they are signalled, through Kubernetes' native `preStop`
sleep action, because both servers close their listening socket the moment the signal arrives: a
connection the gateway opens before it has learned the pod is gone would be refused, and its client
answered 503. The pause keeps the pod serving normally while the gateway catches up. The sleep
action is on by default from Kubernetes 1.30 and GA from 1.34.

Once signalled, the auth server stops in three steps, each bounded:

1. up to 15 seconds for in-flight requests to finish,
2. up to 15 seconds for the work handlers hand off after answering (a forgot-password request's
   code, audit record and email, for example),
3. up to 20 seconds for the background cleanup worker.

The admin console only drains its requests, within 15 seconds. Both pods get the same grace period,
`terminationGracePeriodSeconds: 65`, from this formula:

```
terminationGracePeriodSeconds = preStop pause + auth server's stop + headroom
                           65 =              5 +       (15 + 15 + 20) +       10
```

The grace period is a ceiling, not a wait: a container that exits sooner is not held, so the admin
console loses nothing by sharing the auth server's value. Kubernetes counts the `preStop` pause
against it, so if you change the pause, change the grace period by the same amount.

Do not set it lower. Kubernetes' default is 30 seconds, and whatever is left of the stop when the
grace period runs out is ended by SIGKILL: the cleanup worker, the last step, is cut short first,
then the handed-off work, then requests still in flight.

## Updating Goiabada

A release of the setup wizard writes its own version into both image lines with
`imagePullPolicy: IfNotPresent`, since a version tag names one build. A wizard built from source has
no version to write and uses `latest` with `imagePullPolicy: Always`, under a comment, and warns you
when it finishes: `latest` moves, so pods started at different times can run different releases.
Replace it with a [release version](https://github.com/leodip/goiabada/releases) before production.

1. Update image tags in your manifest or regenerate with the setup wizard
2. Apply changes. The manifest alone carries the image tags, so the Secrets need not be applied again:
   ```bash
   kubectl apply -f goiabada-k8s.yaml
   ```
3. Monitor rollout:
   ```bash
   kubectl rollout status deployment/goiabada-authserver -n goiabada
   ```

### From a manifest with one shared ConfigMap

Manifests generated before each server got its own ConfigMap had one, `goiabada-config`, read by
both. Applying a new manifest creates the two new ConfigMaps and points the Deployments at them, but
`kubectl apply` does not delete a resource the file no longer names, so delete the old one once the
rollout has finished:

```bash
kubectl delete configmap goiabada-config -n goiabada
```
