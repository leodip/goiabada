Goiabada applies its own database migrations. The first instance of the new version to start updates the schema, before it serves any traffic. There is nothing to run by hand.

## Run one version at a time

Stop every instance of the old version, then start the new one. Don't run the two versions against the same database at once.

A new version can add columns, indexes and constraints the old one knows nothing about, and it can change what the server puts in the links it emails. While the two overlap, old instances keep writing rows in the old shape and emailing links in the old format, and neither version is built to read what the other wrote. What that breaks depends on the release.

If you run a single container or a single binary, you already do this. Replacing it stops the old version before the new one starts.

<Aside type="caution">
On Kubernetes, a rolling update deliberately runs both versions side by side until the rollout finishes. Set the deployment's strategy to `Recreate`, or scale it to zero and apply once the old pods are gone. `kubectl scale` returns before they are, so that path needs an explicit wait: [Updating Goiabada](/production-deployment/kubernetes/#updating-goiabada) has the commands.
</Aside>

Back up your database first. Migrations only run forward, and some of them delete rows, so a downgrade won't always give you what you had.

## Upgrading from v1.5.2 or earlier

Password reset and account activation links changed shape. They now carry a verification code and nothing else, and that code reaches a URL only once: following a link answers a redirect to the same page with no query string. Reset and activation now work for addresses containing a `+`, which used to arrive at the server mangled.

Four things happen at the moment you cut over.

**Links emailed before the upgrade stop working.** The server finds the account from the code itself now, and a link the older version sent can't be matched that way. Both kinds of link expire five minutes after they're sent, so this only reaches people who asked for one in the last few minutes.

The two flows say so differently. An old password reset link reaches the usual page saying the code is invalid or expired, and asking for another link works normally. An old activation link has nothing left to point at, because the migration below deletes the pending registration it names, so it reaches the generic error page instead and the server logs an error carrying that request's id. Those log entries are expected during the cutover, and the person registers again rather than asking for another link.

**Pending self-registrations are cleared.** The migration empties the table holding registrations that are waiting for someone to click their activation link, because those rows can't be matched either. Anyone in that state registers again. A pending registration also lives five minutes, so it's the same handful of people.

**The rate limits on those two pages are keyed on the client IP address**, where they used to be keyed on the email address in the link. `GET` and `POST /reset-password` allow 30 requests per 5 minutes per IP, and `GET /account/activate` allows 20. That works out at ten complete operations per five minutes in each flow. See [Security settings](/reference/environment-variables/#security-settings) for the full table.

**Audit events for failed password resets carry different details.** The payload records the client IP address, plus the user id on the branches where the server identified the account. It no longer records an email address. The `reason` values `missing_code_or_email`, `unknown_email`, `no_code_issued` and `code_mismatch` are no longer emitted, replaced by `unknown_code`, `code_expired`, `marker_missing`, `marker_expired`, `marker_wrong_flow`, `code_no_longer_outstanding` and `claim_lost`. If you alert or report on any of the retired values, update the query. `code_expired` is the one name kept, with the same meaning as before: the code's five minute lifetime had passed.
