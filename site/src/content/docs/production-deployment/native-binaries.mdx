Run Goiabada without Docker using pre-built binaries from the [releases page](https://github.com/leodip/goiabada/releases).

## Download

Download the ZIP for your platform from the [releases page](https://github.com/leodip/goiabada/releases). Each ZIP contains both the auth server and admin console binaries:

| Platform | ZIP file | Contains |
|----------|----------|----------|
| Linux (x64) | `goiabada-VERSION-linux-amd64.zip` | `goiabada-authserver`, `goiabada-adminconsole` |
| Linux (ARM) | `goiabada-VERSION-linux-arm64.zip` | `goiabada-authserver`, `goiabada-adminconsole` |
| macOS (Intel) | `goiabada-VERSION-darwin-amd64.zip` | `goiabada-authserver`, `goiabada-adminconsole` |
| macOS (Apple Silicon) | `goiabada-VERSION-darwin-arm64.zip` | `goiabada-authserver`, `goiabada-adminconsole` |
| Windows | `goiabada-VERSION-windows-amd64.zip` | `goiabada-authserver.exe`, `goiabada-adminconsole.exe` |

```bash
# Example for Linux amd64 - download from the releases page
# https://github.com/leodip/goiabada/releases
unzip goiabada-VERSION-linux-amd64.zip
chmod +x goiabada-authserver goiabada-adminconsole
```

## Prerequisites

- A database server (MySQL, PostgreSQL, SQL Server) or SQLite
- SSL certificates for HTTPS
- A reverse proxy (Nginx recommended) or direct HTTPS configuration

## Configuration

Configure via environment variables. You can export them directly or use an environment file.

### Auth server configuration

```bash
# Admin user (created on first startup)
export GOIABADA_ADMIN_EMAIL="admin@example.com"
export GOIABADA_ADMIN_PASSWORD="changeme"
export GOIABADA_APPNAME="Goiabada"

# Server URLs
export GOIABADA_AUTHSERVER_BASEURL="https://auth.example.com"
export GOIABADA_AUTHSERVER_INTERNALBASEURL="http://127.0.0.1:9090"

# Listener configuration
export GOIABADA_AUTHSERVER_LISTEN_HOST_HTTP="0.0.0.0"
export GOIABADA_AUTHSERVER_LISTEN_PORT_HTTP="9090"

# Session keys (generate: openssl rand -hex 64 and openssl rand -hex 32)
export GOIABADA_AUTHSERVER_SESSION_AUTHENTICATION_KEY="<64-byte-hex>"
export GOIABADA_AUTHSERVER_SESSION_ENCRYPTION_KEY="<32-byte-hex>"

# Data encryption key (generate: openssl rand -hex 32). Back it up apart from the database
export GOIABADA_AES_ENCRYPTION_KEY="<32-byte-hex>"

# Database (MySQL example)
export GOIABADA_DB_TYPE="mysql"
export GOIABADA_DB_USERNAME="goiabada"
export GOIABADA_DB_PASSWORD="your-password"
export GOIABADA_DB_HOST="localhost"
export GOIABADA_DB_PORT="3306"
export GOIABADA_DB_NAME="goiabada"

# Admin console URLs
export GOIABADA_ADMINCONSOLE_BASEURL="https://admin.example.com"

# OAuth client secret for seeding
export GOIABADA_ADMINCONSOLE_OAUTH_CLIENT_SECRET="<generated-secret>"
```

### Admin console configuration

```bash
# Server URLs
export GOIABADA_ADMINCONSOLE_BASEURL="https://admin.example.com"

# Listener configuration
export GOIABADA_ADMINCONSOLE_LISTEN_HOST_HTTP="0.0.0.0"
export GOIABADA_ADMINCONSOLE_LISTEN_PORT_HTTP="9091"

# OAuth credentials
export GOIABADA_ADMINCONSOLE_OAUTH_CLIENT_SECRET="<same-secret-as-above>"

# Session keys
export GOIABADA_ADMINCONSOLE_SESSION_AUTHENTICATION_KEY="<64-byte-hex>"
export GOIABADA_ADMINCONSOLE_SESSION_ENCRYPTION_KEY="<32-byte-hex>"

# Auth server URLs
export GOIABADA_AUTHSERVER_BASEURL="https://auth.example.com"
export GOIABADA_AUTHSERVER_INTERNALBASEURL="http://127.0.0.1:9090"
```

Use the [setup wizard](/getting-started/setup-wizard/) and select **"4. Native binaries"** to automatically generate a `goiabada.env` file with all keys and secrets pre-configured.
</Aside>

## Secrets

The wizard writes one file, `goiabada.env`, holding the configuration and every secret, which both
servers read. It is plain text, and its mode, `0600`, is its only protection: keep it out of version
control, owned by the user the servers run as, and readable by that user alone. Root reads it, and
the environment of the running processes, whatever its mode.

### Backing up the AES key

`GOIABADA_AES_ENCRYPTION_KEY` encrypts the client secrets, the SMTP password, the OTP seeds, the
verification and reset codes, and the token signing keys the database holds. A database backup
restored without it gives an auth server that can decrypt none of them, and a backup kept with it
gives all of them to whoever reads it. Copy the key to a password manager, a secret manager or an
offline copy, apart from your database backups, after the first start and after every rotation. Keep
each key as long as you keep a database backup taken under it: to restore one, start the auth server
with that key as `GOIABADA_AES_ENCRYPTION_KEY`, or with today's key there and the old one as
`GOIABADA_AES_ENCRYPTION_KEY_PREVIOUS`, which re-encrypts the restored data to today's key at start.

### Rotating secrets

Both servers read their secrets from the environment, and only when they start. Each runs as one
process, which a restart stops before it starts the new one, so each change below is one restart.
Generate each new key with `openssl rand -hex 64` for an authentication key and `openssl rand -hex 32`
for the rest.

**The session keys.** Each server seals its browser sessions with its current session key pair, and
opens them with that pair and then, when it is set, the previous one. In the env file, give each
server's current pair to its previous pair, and new keys to the current pair:

```bash
GOIABADA_AUTHSERVER_SESSION_AUTHENTICATION_KEY="<new, openssl rand -hex 64>"
GOIABADA_AUTHSERVER_SESSION_ENCRYPTION_KEY="<new, openssl rand -hex 32>"
GOIABADA_AUTHSERVER_SESSION_AUTHENTICATION_KEY_PREVIOUS="<its value before>"
GOIABADA_AUTHSERVER_SESSION_ENCRYPTION_KEY_PREVIOUS="<its value before>"

GOIABADA_ADMINCONSOLE_SESSION_AUTHENTICATION_KEY="<new, openssl rand -hex 64>"
GOIABADA_ADMINCONSOLE_SESSION_ENCRYPTION_KEY="<new, openssl rand -hex 32>"
GOIABADA_ADMINCONSOLE_SESSION_AUTHENTICATION_KEY_PREVIOUS="<its value before>"
GOIABADA_ADMINCONSOLE_SESSION_ENCRYPTION_KEY_PREVIOUS="<its value before>"
```

Then restart both servers, with systemd `sudo systemctl restart goiabada-authserver
goiabada-adminconsole`. Nobody is signed out: each server seals under the new pair and still opens
what the old one sealed. Once the maximum session lifetime has passed, which is on the admin
console's **Settings → Sessions** page, 24 hours unless you changed it, every signed-in session has
been sealed again under the new pair: delete the four `_PREVIOUS` lines and restart both again. A
sign-in still in progress may restart, costing that person the form they were filling in.

**The AES key.** The auth server encrypts and decrypts with `GOIABADA_AES_ENCRYPTION_KEY` alone, and
reads `GOIABADA_AES_ENCRYPTION_KEY_PREVIOUS` only when it starts: if the database is still under that
key, it re-encrypts all of it to the current one, in one transaction, before it listens. Run one auth
server process while you rotate: a second one still running with the old key would decrypt nothing
once the first has re-encrypted, and what it encrypted would stay unreadable.

1. Back up the database and the current key.
2. In the env file, add `GOIABADA_AES_ENCRYPTION_KEY_PREVIOUS="<the current key>"`, set
   `GOIABADA_AES_ENCRYPTION_KEY` to a new key, and back the new key up: the next start puts the
   database under it.
3. Restart the auth server, and check that the re-encryption committed:

   ```bash
   sudo systemctl restart goiabada-authserver
   sudo journalctl -u goiabada-authserver | grep 'rotated data-at-rest encryption'
   ```

   If it stops instead with `data-at-rest decrypts under neither GOIABADA_AES_ENCRYPTION_KEY nor
   GOIABADA_AES_ENCRYPTION_KEY_PREVIOUS`, the previous key is not the one the database is under, and
   nothing was changed.
4. Once sign-ins and your clients work, delete the `_PREVIOUS` line and restart the auth server
   again. Until then it is harmless: at each start the auth server finds the database under the
   current key and re-encrypts nothing.

The other secrets are not Goiabada's to rotate. `GOIABADA_ADMIN_PASSWORD` is read only by the first
start: change the administrator's password in the admin console. The OAuth client secret must match
the admin console client's secret in the database, and the database password the database user's.

### Upgrading a configuration from an earlier release

An env file from an earlier release keeps working. If you generate a new one, copy every secret
value from the old file over the new values the wizard generated: `GOIABADA_AES_ENCRYPTION_KEY` above
all, since a new key cannot decrypt the database; `GOIABADA_DB_PASSWORD`, which must match the
database user's; `GOIABADA_ADMINCONSOLE_OAUTH_CLIENT_SECRET`, which must match the admin console's
client in the database; and the four session keys, unless everybody signing in again is acceptable.

## Running on Linux with systemd

### 1. Create a dedicated user

```bash
sudo useradd -r -s /bin/false goiabada
sudo mkdir -p /opt/goiabada
sudo mkdir -p /etc/goiabada
sudo mkdir -p /var/lib/goiabada

sudo mv goiabada-authserver goiabada-adminconsole /opt/goiabada/
sudo chmod +x /opt/goiabada/goiabada-*
sudo chown -R goiabada:goiabada /opt/goiabada
sudo chown -R goiabada:goiabada /var/lib/goiabada
```

### 2. Create environment files

```bash
# Auth server environment
sudo nano /etc/goiabada/authserver.env

# Admin console environment
sudo nano /etc/goiabada/adminconsole.env
```

### 3. Create systemd service files

**Auth server** (`/etc/systemd/system/goiabada-authserver.service`):

```ini
[Unit]
Description=Goiabada Auth Server
After=network.target mysql.service

[Service]
Type=simple
User=goiabada
Group=goiabada
WorkingDirectory=/opt/goiabada
EnvironmentFile=/etc/goiabada/authserver.env
ExecStart=/opt/goiabada/goiabada-authserver
Restart=on-failure
RestartSec=5s

[Install]
WantedBy=multi-user.target
```

**Admin console** (`/etc/systemd/system/goiabada-adminconsole.service`):

```ini
[Unit]
Description=Goiabada Admin Console
After=network.target goiabada-authserver.service
Requires=goiabada-authserver.service

[Service]
Type=simple
User=goiabada
Group=goiabada
WorkingDirectory=/opt/goiabada
EnvironmentFile=/etc/goiabada/adminconsole.env
ExecStart=/opt/goiabada/goiabada-adminconsole
Restart=on-failure
RestartSec=5s

[Install]
WantedBy=multi-user.target
```

### 4. Enable and start services

```bash
sudo systemctl daemon-reload
sudo systemctl enable goiabada-authserver
sudo systemctl enable goiabada-adminconsole
sudo systemctl start goiabada-authserver
sudo systemctl start goiabada-adminconsole
```

### 5. Check status and logs

```bash
sudo systemctl status goiabada-authserver
sudo systemctl status goiabada-adminconsole

# View logs
sudo journalctl -u goiabada-authserver -f
sudo journalctl -u goiabada-adminconsole -f
```

## Reverse proxy

For production, use Nginx as a reverse proxy (see [reverse proxy guide](/production-deployment/reverse-proxy/)). Configure Nginx to proxy to:

- Auth server: `http://127.0.0.1:9090`
- Admin console: `http://127.0.0.1:9091`

The setup wizard asks whether a reverse proxy on the same machine forwards to Goiabada (`--local-proxy`, yes by default). On yes, `goiabada.env` has both servers listen on `127.0.0.1` alone and trust the forwarded headers of a connection from `127.0.0.1` alone:

```bash
GOIABADA_AUTHSERVER_LISTEN_HOST_HTTP="127.0.0.1"
GOIABADA_AUTHSERVER_TRUST_PROXY_HEADERS="true"
GOIABADA_AUTHSERVER_TRUSTED_PROXIES="127.0.0.1"

GOIABADA_ADMINCONSOLE_LISTEN_HOST_HTTP="127.0.0.1"
GOIABADA_ADMINCONSOLE_TRUST_PROXY_HEADERS="true"
GOIABADA_ADMINCONSOLE_TRUSTED_PROXIES="127.0.0.1"
```

Nothing outside the machine reaches the plain HTTP listeners, and Goiabada takes the client from the `X-Forwarded-For` entry Nginx appends. For a proxy on another host, set each listen host to an address that host reaches and each list to that host's address, and keep the ports closed to everything else.

On no (`--local-proxy=false`), both servers listen on every interface and trust no forwarded header, so each client is the address it connects from. They serve plain HTTP until you configure direct HTTPS, below.

The wizard also asks whether to turn on the auth server's [rate limiter](/reference/environment-variables/#security-settings), yes by default, and writes `GOIABADA_AUTHSERVER_RATELIMITER_ENABLED` either way (`--rate-limiter=false` answers no). Behind a reverse proxy on the same machine, the `127.0.0.1` list keeps the auth server's startup warnings about proxy trust silent. With no proxy, the auth server logs a warning at every start that it trusts no forwarded header and that, behind a proxy, everyone would share one per-IP bucket; with nothing in front of it, that is expected.

## Direct HTTPS (optional)

If you prefer not to use a reverse proxy, configure direct HTTPS. Setting the certificate and key turns on the HTTPS listener; set `LISTEN_HOST_HTTP` empty as well to stop serving plain HTTP:

```bash
# Auth server
export GOIABADA_AUTHSERVER_LISTEN_HOST_HTTPS="0.0.0.0"
export GOIABADA_AUTHSERVER_LISTEN_PORT_HTTPS="8443"
export GOIABADA_AUTHSERVER_CERTFILE="/path/to/fullchain.pem"
export GOIABADA_AUTHSERVER_KEYFILE="/path/to/privkey.pem"

# Admin console
export GOIABADA_ADMINCONSOLE_LISTEN_HOST_HTTPS="0.0.0.0"
export GOIABADA_ADMINCONSOLE_LISTEN_PORT_HTTPS="9444"
export GOIABADA_ADMINCONSOLE_CERTFILE="/path/to/fullchain.pem"
export GOIABADA_ADMINCONSOLE_KEYFILE="/path/to/privkey.pem"
```
