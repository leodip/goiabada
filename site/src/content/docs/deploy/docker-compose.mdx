## Quick comparison

| Method | SSL management | Complexity | Best for |
|--------|---------------|------------|----------|
| Cloudflare Tunnel | Cloudflare handles it | ⭐ Easiest | Most users |
| Cloudflare + Nginx | Cloudflare + local certs | ⭐⭐ Medium | Existing Nginx servers |
| Reverse proxy | Let's Encrypt | ⭐⭐ Medium | Non-Cloudflare users |
| Kubernetes | cert-manager | ⭐⭐⭐ Advanced | Kubernetes environments |
| Native binaries | Manual | ⭐⭐⭐ Advanced | No-Docker environments |

## Using the setup wizard

The [setup wizard](/get-started/setup-wizard/) can generate production-ready configurations:

```bash
./goiabada-setup-linux-amd64
```

Choose the deployment type that matches your setup:

| Option | Use case | Output |
|--------|----------|--------|
| **2. Production with reverse proxy** | Docker with Nginx/Cloudflare | `docker-compose.yml`, and its secrets in `docker-compose.override.yml` |
| **3. Kubernetes cluster** | Kubernetes deployment | `goiabada-k8s.yaml`, and its Secrets in `goiabada-secrets.yaml` |
| **4. Native binaries** | Running without Docker | `goiabada.env` |

The wizard will ask for your domain names, generate all credentials (session keys, OAuth secrets), and create the appropriate configuration file.

You still need to set up SSL termination using one of the methods above (except for Kubernetes, where the wizard configures cert-manager).

## Secrets

This section is about the Docker Compose output. The [Kubernetes](/deploy/kubernetes/#secrets)
and [native binaries](/deploy/native-binaries/#secrets) pages have their own.

The wizard writes every secret into `docker-compose.override.yml`, under the service that reads it,
and none into `docker-compose.yml`, which can therefore be committed. The override is plain text, and
its mode, `0600`, is its only protection: keep it out of version control and out of shared
directories. Anyone who can run `docker` on the host reads the secrets too, since `docker inspect`
shows a container's environment, and so does root.

### Backing up the AES key

`GOIABADA_AES_ENCRYPTION_KEY`, under `goiabada-authserver` in the override, encrypts the client
secrets, the SMTP password, the OTP seeds, the verification and reset codes, and the token signing
keys the database holds. A database backup restored without it gives an auth server that can decrypt
none of them, and a backup kept with it gives all of them to whoever reads it. Copy the key to a
password manager, a secret manager or an offline copy, apart from your database backups, after the
first start and after every rotation. Keep each key as long as you keep a database backup taken under
it: to restore one, start the auth server with that key as `GOIABADA_AES_ENCRYPTION_KEY`, or with
today's key there and the old one as `GOIABADA_AES_ENCRYPTION_KEY_PREVIOUS`, which re-encrypts the
restored data to today's key at start.

### Rotating secrets

Both servers read their secrets from the environment, and only when they start. Compose runs one
container per service, and `docker compose up -d` stops the container of a changed service before it
starts the new one, so two containers of one service never run together and each change below is one
restart. Generate each new key with `openssl rand -hex 64` for an authentication key and `openssl rand
-hex 32` for the rest.

**The session keys.** Each server seals its browser sessions with its current session key pair, and
opens them with that pair and then, when it is set, the previous one. In
`docker-compose.override.yml`, give each server's current pair to its previous pair, and new keys to
the current pair:

```yaml
  goiabada-authserver:
    environment:
      # ...the other entries stay as they are
      - "GOIABADA_AUTHSERVER_SESSION_AUTHENTICATION_KEY=<new, openssl rand -hex 64>"
      - "GOIABADA_AUTHSERVER_SESSION_ENCRYPTION_KEY=<new, openssl rand -hex 32>"
      - "GOIABADA_AUTHSERVER_SESSION_AUTHENTICATION_KEY_PREVIOUS=<its value before>"
      - "GOIABADA_AUTHSERVER_SESSION_ENCRYPTION_KEY_PREVIOUS=<its value before>"

  goiabada-adminconsole:
    environment:
      # ...the other entries stay as they are
      - "GOIABADA_ADMINCONSOLE_SESSION_AUTHENTICATION_KEY=<new, openssl rand -hex 64>"
      - "GOIABADA_ADMINCONSOLE_SESSION_ENCRYPTION_KEY=<new, openssl rand -hex 32>"
      - "GOIABADA_ADMINCONSOLE_SESSION_AUTHENTICATION_KEY_PREVIOUS=<its value before>"
      - "GOIABADA_ADMINCONSOLE_SESSION_ENCRYPTION_KEY_PREVIOUS=<its value before>"
```

Then run `docker compose up -d`. Nobody is signed out: each server seals under the new pair and still
opens what the old one sealed. Once the maximum session lifetime has passed, which is on the admin
console's **Settings → Sessions** page, 24 hours unless you changed it, every signed-in session has
been sealed again under the new pair: delete the four `_PREVIOUS` lines and run `docker compose up
-d` again. A sign-in still in progress may restart, costing that person the form they were filling
in.

**The AES key.** The auth server encrypts and decrypts with `GOIABADA_AES_ENCRYPTION_KEY` alone, and
reads `GOIABADA_AES_ENCRYPTION_KEY_PREVIOUS` only when it starts: if the database is still under that
key, it re-encrypts all of it to the current one, in one transaction, before it listens.

1. Back up the database and the current key.
2. Under `goiabada-authserver` in the override, add
   `GOIABADA_AES_ENCRYPTION_KEY_PREVIOUS=<the current key>`, set `GOIABADA_AES_ENCRYPTION_KEY` to a
   new key, and back the new key up: the next start puts the database under it.
3. Restart the auth server, and check that the re-encryption committed:

   ```bash
   docker compose up -d goiabada-authserver
   docker compose logs goiabada-authserver | grep 'rotated data-at-rest encryption'
   ```

   If it stops instead with `data-at-rest decrypts under neither GOIABADA_AES_ENCRYPTION_KEY nor
   GOIABADA_AES_ENCRYPTION_KEY_PREVIOUS`, the previous key is not the one the database is under, and
   nothing was changed.
4. Once sign-ins and your clients work, delete the `_PREVIOUS` line and run `docker compose up -d
   goiabada-authserver` again. Until then it is harmless: at each start the auth server finds the
   database under the current key and re-encrypts nothing.

**The database password.** The auth server signs in to the database service as its administrator:
`root` on MySQL, `postgres` on PostgreSQL, `sa` on SQL Server. The override holds the password twice,
as `GOIABADA_DB_PASSWORD` under `goiabada-authserver` and as the database service's own variable,
`MYSQL_ROOT_PASSWORD`, `POSTGRES_PASSWORD` or `MSSQL_SA_PASSWORD`. The image reads that variable only
to set up an empty volume, so changing it changes nothing in the database: the password changes in
the database first. The database checks a password only when a connection opens, so the running auth
server keeps the connections it holds through a change.

1. Change the password in the database. For MySQL and PostgreSQL, `openssl rand -hex 32` makes one;
   SQL Server's password policy asks for three of upper case, lower case, digits and symbols, which
   a hex string lacks.
   - **MySQL** keeps the current password too, as a second password that is still accepted. The
     image creates `root` twice, for connections from other containers (`%`), which is the auth
     server's, and from inside its own (`localhost`). In `docker compose exec mysql-server mysql -uroot
     -p`:

     ```sql
     ALTER USER 'root'@'%' IDENTIFIED BY '<new password>' RETAIN CURRENT PASSWORD;
     ALTER USER 'root'@'localhost' IDENTIFIED BY '<new password>' RETAIN CURRENT PASSWORD;
     ```

   - **PostgreSQL**: run `docker compose exec postgres-server psql -U postgres`, then `\password
     postgres`, which asks for the new password twice without echoing it and keeps it out of the
     server log and `psql`'s history.
   - **SQL Server**: in `docker compose exec mssql-server /opt/mssql-tools18/bin/sqlcmd -S localhost
     -U sa -C`, which asks for the current password:

     ```sql
     ALTER LOGIN sa WITH PASSWORD = '<new password>';
     GO
     ```

   On PostgreSQL and SQL Server, from here until step 3 the auth server cannot open a connection,
   and a request that needs a new one fails with a 500.
2. In the override, set `GOIABADA_DB_PASSWORD` and the database service's variable to the new
   password.
3. Restart the auth server alone, at once:

   ```bash
   docker compose up -d --no-deps goiabada-authserver
   ```

   Without `--no-deps`, Compose would also recreate the database's container, whose variable changed,
   restarting the database under the auth server. That container takes the new value the next time
   it is recreated, which changes nothing in the database. On SQL Server its healthcheck signs in with
   the value it holds, so it reports unhealthy until then: recreate it with `docker compose up -d`
   when a short database restart suits.
4. On MySQL, once the auth server is back, discard the old password:

   ```sql
   ALTER USER 'root'@'%' DISCARD OLD PASSWORD;
   ALTER USER 'root'@'localhost' DISCARD OLD PASSWORD;
   ```

If the auth server then stops on `Access denied`, `password authentication failed` or `Login failed`
in `docker compose logs goiabada-authserver`, the override and the database disagree: set the
database's password to the override's.

**The admin console's client secret.** `GOIABADA_ADMINCONSOLE_OAUTH_CLIENT_SECRET`, under both
services, is the secret of the admin console's OAuth client, `admin-console-client`, which the auth
server keeps, encrypted, in its database. The auth server reads its copy only at its first start, to
create that client. The admin console presents it on every sign-in, on every refresh of an
administrator's access token, and for the token it asks for to reach its own sessions.

1. In the admin console, open **Clients**, then `admin-console-client`, then its **Authentication**
   tab, click **Generate new secret**, then **Copy**. Do not save yet.
2. Paste it as `GOIABADA_ADMINCONSOLE_OAUTH_CLIENT_SECRET` under both services in the override. Nothing
   reads it before a restart, and it is now stored before the database depends on it.
3. **Save** the page, and confirm the warning about a system-level client.
4. Restart the admin console alone, at once, and check by signing in from a private window:

   ```bash
   docker compose up -d --no-deps goiabada-adminconsole
   ```

   Without `--no-deps`, Compose would also recreate the auth server, whose copy changed, stopping
   sign-in while it restarts. It reads that copy only to set up an empty database, so it can take it
   at its next restart.

Between steps 3 and 4 the auth server refuses the secret the running admin console presents: a
sign-in fails at its last step, an administrator whose access token falls due is signed out, and once
the token the admin console holds for its sessions expires, within 5 minutes unless you changed the
access token lifetime, every page behind the sign-in answers 500. Administrators signed in before
step 3 stay signed in through the restart, and the auth server and every other client work
throughout. If the admin console can no longer sign you in, set a secret you know through the admin
API, as [Locked out of the admin console](/troubleshooting/locked-out-of-the-admin-console/#the-admin-consoles-client-secret-changed)
shows.

`GOIABADA_ADMIN_PASSWORD` is read only by the first start, which creates the administrator: change the
administrator's password in the admin console.

### Upgrading a configuration from an earlier release

Earlier releases of the wizard wrote every secret into `docker-compose.yml` itself. That file keeps
working as it is. To move to the new shape, generate the new pair of files, then copy every secret
value from the old `docker-compose.yml` into the new `docker-compose.override.yml`, over the new
values the wizard generated:

- `GOIABADA_AES_ENCRYPTION_KEY`, above all: a new key cannot decrypt the database.
- The database password, in `GOIABADA_DB_PASSWORD` and in the database service's own variable
  (`POSTGRES_PASSWORD`, `MYSQL_ROOT_PASSWORD` or `MSSQL_SA_PASSWORD`). The database image sets the
  password only on an empty volume, so a new one would not match it.
- `GOIABADA_ADMINCONSOLE_OAUTH_CLIENT_SECRET`, under both services: it must match the admin console's
  client in the database.
- The four session keys, unless everybody signing in again is acceptable.

Then run `docker compose up -d`, and keep the old `docker-compose.yml` as carefully as the override,
or delete it. A deployment on SQLite also needs the one-time `chown` of [Upgrading a Compose deployment
that uses SQLite](#upgrading-a-compose-deployment-that-uses-sqlite).

## The user the images run as

Both images run as uid 10001 and gid 10001, a user and group named `goiabada`, and never as root.
The image names them by number, so a platform that refuses a root container, such as Kubernetes with
`runAsNonRoot`, can verify the user without reading the image's `/etc/passwd`. The binary and the
`/app` directory holding it belong to root, so the process cannot replace what its next start runs.

A file you mount into a container must be readable by uid 10001 or gid 10001: the certificate and
key named by `GOIABADA_AUTHSERVER_CERTFILE` and `GOIABADA_AUTHSERVER_KEYFILE` (and the admin
console's pair), and the templates and static files of a [customization](/guides/customizations/).
A key file left at mode `0600` and owned by root cannot be read; give it to the user, or to the group
with mode `0640`:

```bash
sudo chown 10001:10001 key.pem
# or
sudo chgrp 10001 key.pem && sudo chmod 0640 key.pem
```

The auth server writes to two directories, and its image creates both owned by 10001:

- `/data`, where the generated Compose file and the hand-written SQLite sample mount the SQLite
  volume. Docker copies a mount point's ownership into an empty named volume, so a new volume
  mounted here is writable from the first start. A volume mounted at a path the image lacks gets a directory Docker creates owned by root,
  where the server can write nothing.
- `/bootstrap`, where the legacy bootstrap writes `bootstrap.env` when
  `GOIABADA_AUTHSERVER_BOOTSTRAP_ENV_OUTFILE` names a file in it. Mount a named volume there, and
  read the file with `docker compose cp goiabada-authserver:/bootstrap/bootstrap.env .`. A bind mount
  of a host directory that does not exist yet is created owned by root, and the write is refused.

### Upgrading a Compose deployment that uses SQLite

The images of earlier releases ran as root, so a SQLite volume they wrote belongs to root, and the
auth server now stops at start with `unable to migrate the database: unable to clear
schema_migrations: attempt to write a readonly database`. Give the volume to uid 10001 once, from
the directory holding your `docker-compose.yml`, before starting the new image:

```bash
docker compose stop goiabada-authserver
docker compose run --rm --no-deps --user 0:0 --cap-add CHOWN --entrypoint chown \
  goiabada-authserver -R 10001:10001 /data
docker compose up -d
```

This runs `chown` once as root, in a throwaway container of the auth server's service, so it reaches
the volume wherever that service mounts it. `--cap-add CHOWN` is what lets root change the owner in
a service that drops every capability; where the service drops none, it changes nothing. Use the
path your file mounts the volume at: `/data` in the generated file and in the current SQLite
sample, while the sample of earlier releases mounted it at `/app/data`.

Nothing else needs this step. MySQL, PostgreSQL and SQL Server keep their data in their own
containers, which run their own images, and the Kubernetes manifest mounts no volume.
