Use this setup if you already have Nginx running on your server hosting other sites.

## Architecture

```
User → Cloudflare (HTTPS) → Nginx (HTTPS) → Goiabada (HTTP localhost)
```

- Cloudflare provides edge SSL termination
- Nginx receives HTTPS from Cloudflare (with valid SSL certificates)
- Nginx proxies to Goiabada's HTTP ports on localhost
- Ports 9090 and 9091 are NOT exposed to the internet

## Prerequisites

- Domain added to Cloudflare with proxy enabled (orange cloud)
- Nginx installed on your server
- Docker and docker-compose installed

## Setup

### 1. Configure Cloudflare SSL

In your domain's Cloudflare dashboard:

<Steps>
1. Go to **SSL/TLS** → **Overview**
   - Set encryption mode to **Full (strict)**

2. Go to **SSL/TLS** → **Edge Certificates**
   - Enable **"Always Use HTTPS"**
</Steps>

### 2. Configure DNS records

In Cloudflare DNS, add A records for both domains pointing to your server with **proxy enabled** (orange cloud):

```
Type: A    Name: auth    Content: <your-server-ip>    Proxy: ON
Type: A    Name: admin   Content: <your-server-ip>    Proxy: ON
```

### 3. Start Goiabada containers

Use the [setup wizard](/get-started/setup-wizard/) to generate your `docker-compose.yml`:

1. Select **"2. Production with reverse proxy"** when prompted
2. Enter your domain names (e.g., `https://auth.example.com` and `https://admin.example.com`)
3. The wizard automatically sets `TRUST_PROXY_HEADERS=true` with `TRUSTED_PROXIES` empty, trusting Nginx as the one proxy hop; step 6 below makes Nginx hand Goiabada the client's address rather than Cloudflare's (see [client IP behind Cloudflare](#client-ip-behind-cloudflare)). Because your base URLs are `https://`, cookies get the `Secure` flag automatically

Then start the containers:

```bash
docker compose up -d
```

Verify containers are running:

```bash
# Check containers are running
docker ps | grep goiabada

# Test auth server health (should return: healthy)
curl http://localhost:9090/health && echo

# Test admin console health (should return: healthy)
curl http://localhost:9091/health && echo
```

### 4. Get SSL certificates

<Steps>
1. Install certbot (Ubuntu/Debian):
   ```bash
   sudo apt-get update
   sudo apt-get install certbot
   sudo mkdir -p /var/www/certbot
   ```

2. Create a temporary Nginx config for certificate acquisition:
   ```bash
   sudo nano /etc/nginx/sites-available/goiabada
   ```

3. Add temporary HTTP config:

   <Aside type="caution">
   Replace `auth.example.com` and `admin.example.com` with your actual domain names throughout this configuration.
   </Aside>

   ```nginx
   server {
       listen 80;
       server_name auth.example.com;

       location /.well-known/acme-challenge/ {
           root /var/www/certbot;
       }

       location / {
           proxy_pass http://127.0.0.1:9090;
       }
   }

   server {
       listen 80;
       server_name admin.example.com;

       location /.well-known/acme-challenge/ {
           root /var/www/certbot;
       }

       location / {
           proxy_pass http://127.0.0.1:9091;
       }
   }
   ```

4. Enable and reload:
   ```bash
   sudo ln -s /etc/nginx/sites-available/goiabada /etc/nginx/sites-enabled/
   sudo nginx -t && sudo nginx -s reload
   ```

5. **Temporarily disable Cloudflare proxy** - In Cloudflare DNS, click the orange cloud to make it gray for both domains

6. Get certificates:
   ```bash
   sudo certbot certonly --webroot -w /var/www/certbot -d auth.example.com
   sudo certbot certonly --webroot -w /var/www/certbot -d admin.example.com
   ```

7. **Re-enable Cloudflare proxy** - Turn clouds back to orange
</Steps>

### 5. Configure Nginx with HTTPS

Replace the Nginx config with production HTTPS configuration:

```bash
sudo nano /etc/nginx/sites-available/goiabada
```

```nginx
# Auth Server - HTTPS
server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name auth.example.com;

    ssl_certificate /etc/letsencrypt/live/auth.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/auth.example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;
    ssl_prefer_server_ciphers on;

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    location / {
        proxy_pass http://127.0.0.1:9090;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }
}

# Auth Server - HTTP redirect
server {
    listen 80;
    listen [::]:80;
    server_name auth.example.com;

    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }

    location / {
        return 301 https://$server_name$request_uri;
    }
}

# Admin Console - HTTPS
server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name admin.example.com;

    ssl_certificate /etc/letsencrypt/live/admin.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/admin.example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;
    ssl_prefer_server_ciphers on;

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    location / {
        proxy_pass http://127.0.0.1:9091;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }
}

# Admin Console - HTTP redirect
server {
    listen 80;
    listen [::]:80;
    server_name admin.example.com;

    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }

    location / {
        return 301 https://$server_name$request_uri;
    }
}
```

Test and reload:

```bash
sudo nginx -t
sudo nginx -s reload
```

### 6. Have Nginx resolve Cloudflare

Every request reaches Nginx from a Cloudflare address, so without this step
Goiabada would see Cloudflare's edge as the client. Nginx's `real_ip` module
replaces that address with the client's, taken from the `CF-Connecting-IP` header,
but only on a connection that comes from one of Cloudflare's published ranges.
Write those ranges into a file Nginx loads in its `http` context:

```bash
{
  echo "# Cloudflare's ranges, from https://www.cloudflare.com/ips/ ($(date -I))"
  for range in $(curl -fsS https://www.cloudflare.com/ips-v4) $(curl -fsS https://www.cloudflare.com/ips-v6); do
    echo "set_real_ip_from $range;"
  done
  echo "real_ip_header CF-Connecting-IP;"
} | sudo tee /etc/nginx/conf.d/cloudflare-real-ip.conf
```

The file looks like this, with every range Cloudflare lists:

```nginx
# Cloudflare's ranges, from https://www.cloudflare.com/ips/ (2026-10-04)
set_real_ip_from 173.245.48.0/20;
set_real_ip_from 103.21.244.0/22;
# ...
set_real_ip_from 2400:cb00::/32;
# ...
real_ip_header CF-Connecting-IP;
```

Test and reload:

```bash
sudo nginx -t
sudo nginx -s reload
```

Debian's and Ubuntu's Nginx packages include `/etc/nginx/conf.d/*.conf` in the
`http` context and are built with the `real_ip` module (`nginx -V 2>&1 | grep -o
with-http_realip_module` shows it). Cloudflare changes its ranges rarely; run the
command again when it does, or from a monthly cron job. See
[client IP behind Cloudflare](#client-ip-behind-cloudflare) for why Goiabada
needs no list of its own.

### 7. Configure firewall

```bash
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
# Do NOT expose 9090 or 9091
```

- Auth server: `https://auth.example.com`
- Admin console: `https://admin.example.com`

## Client IP behind Cloudflare

Goiabada keys its rate limits and audit records on the client IP, which behind
proxies it reads from `X-Forwarded-For`. The wizard sets `TRUST_PROXY_HEADERS=true`
with `TRUSTED_PROXIES` empty, so Goiabada trusts one hop, the proxy that connects
to it, and takes the client from the rightmost entry, which that proxy appended.

Here that proxy is Nginx, and step 6 is what makes its entry the client's: with
`real_ip`, Nginx's `$remote_addr` is the address in `CF-Connecting-IP` on a
connection from Cloudflare, and the `X-Real-IP $remote_addr` and
`$proxy_add_x_forwarded_for` lines of step 5 pass that address on. A value a client
puts in `X-Forwarded-For` itself stays to the left and is never read. A request that
reaches Nginx directly, from outside Cloudflare's ranges, keeps its own address, so
a forged `CF-Connecting-IP` changes nothing. Without step 6, the rightmost entry is
a Cloudflare edge address: not forgeable, but shared by everyone that edge serves,
so many users would count against one rate-limit bucket.

Do not list Cloudflare's ranges, or `127.0.0.1`, in `TRUSTED_PROXIES`. Nginx
connects to `127.0.0.1:9090`, but a Compose service sees the connection come from
the Compose network's gateway, an address such as `172.21.0.1`; Goiabada reads
forwarded headers only from a connection whose address is in the list, so that list
makes it ignore them and resolve every request to the gateway, one bucket for
everyone.

To check, open the sign-in page and read the auth server's request log (`docker
compose logs goiabada-authserver`): the `ip` of your request should be your own
address, not Cloudflare's.
See [Reverse proxy: client IP resolution](/deploy/reverse-proxy/#client-ip-resolution-and-spoofing-protection)
for how the resolution works.
