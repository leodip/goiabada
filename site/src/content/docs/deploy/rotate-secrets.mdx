This page helps you replace each of Goiabada's secrets without signing anybody out, or with the shortest interruption that secret allows.

Every rotation works the same way: a server reads its secrets only when it starts, so you change a secret where your setup keeps it, then restart the server that reads it. Each step has a tab per platform for its commands. Pick yours once, and every tab on the page follows.

Generate a new key with `openssl rand -hex 64` for a session authentication key and `openssl rand -hex 32` for the rest. [Secrets](/deploy/secrets/#what-each-secret-protects) says what each one protects.

<Aside>
On Kubernetes, the steps change the Secrets with `kubectl patch`, which suits Secrets nothing else writes. When the External Secrets Operator, the SealedSecrets controller or a GitOps tool owns them, make each step's change in its source instead, as [Rotating Secrets something else owns](/deploy/kubernetes/secrets/#rotating-secrets-something-else-owns) describes. If you kept the generated `goiabada-secrets.yaml`, it still holds the keys from before the rotation, and applying it again puts them back: delete it once the Secrets are in the cluster.
</Aside>

## The session keys

Each server seals its browser sessions with its current session key pair, and opens them with that pair and then, when it's set, a previous pair. So you make the new pair current and keep the old one as the previous pair for as long as a session sealed under it can live. Done this way, nobody is signed out.

<Steps>

1. **Make new pairs current, and the old pairs previous, then restart both servers.**

   <Tabs syncKey="platform">
     <TabItem label="Docker Compose">
       In `docker-compose.override.yml`, give each server's current pair to its previous pair, and new keys to the current pair:

       ```yaml
         goiabada-authserver:
           environment:
             # ...the other entries stay as they are
             - "GOIABADA_AUTHSERVER_SESSION_AUTHENTICATION_KEY=<new, openssl rand -hex 64>"
             - "GOIABADA_AUTHSERVER_SESSION_ENCRYPTION_KEY=<new, openssl rand -hex 32>"
             - "GOIABADA_AUTHSERVER_SESSION_AUTHENTICATION_KEY_PREVIOUS=<its value before>"
             - "GOIABADA_AUTHSERVER_SESSION_ENCRYPTION_KEY_PREVIOUS=<its value before>"

         goiabada-adminconsole:
           environment:
             # ...the other entries stay as they are
             - "GOIABADA_ADMINCONSOLE_SESSION_AUTHENTICATION_KEY=<new, openssl rand -hex 64>"
             - "GOIABADA_ADMINCONSOLE_SESSION_ENCRYPTION_KEY=<new, openssl rand -hex 32>"
             - "GOIABADA_ADMINCONSOLE_SESSION_AUTHENTICATION_KEY_PREVIOUS=<its value before>"
             - "GOIABADA_ADMINCONSOLE_SESSION_ENCRYPTION_KEY_PREVIOUS=<its value before>"
       ```

       Then restart:

       ```bash
       docker compose up -d
       ```

       Compose stops a changed service's container before it starts the new one, so two containers of one service never run together, and one restart does it.
     </TabItem>
     <TabItem label="Native binaries">
       In the env file, give each server's current pair to its previous pair, and new keys to the current pair:

       ```bash
       GOIABADA_AUTHSERVER_SESSION_AUTHENTICATION_KEY="<new, openssl rand -hex 64>"
       GOIABADA_AUTHSERVER_SESSION_ENCRYPTION_KEY="<new, openssl rand -hex 32>"
       GOIABADA_AUTHSERVER_SESSION_AUTHENTICATION_KEY_PREVIOUS="<its value before>"
       GOIABADA_AUTHSERVER_SESSION_ENCRYPTION_KEY_PREVIOUS="<its value before>"

       GOIABADA_ADMINCONSOLE_SESSION_AUTHENTICATION_KEY="<new, openssl rand -hex 64>"
       GOIABADA_ADMINCONSOLE_SESSION_ENCRYPTION_KEY="<new, openssl rand -hex 32>"
       GOIABADA_ADMINCONSOLE_SESSION_AUTHENTICATION_KEY_PREVIOUS="<its value before>"
       GOIABADA_ADMINCONSOLE_SESSION_ENCRYPTION_KEY_PREVIOUS="<its value before>"
       ```

       Then restart both servers:

       ```bash
       sudo systemctl restart goiabada-authserver goiabada-adminconsole
       ```

       Each server runs as one process, which a restart stops before it starts the new one, so one restart does it.
     </TabItem>
     <TabItem label="Kubernetes">
       A rollout runs old and new pods side by side, and each must open what the other seals. So the new pairs go in first as the previous pairs, and the two are then swapped, in two rollouts.

       **Add the new pairs as the previous pairs.** Every pod still seals under the current pair, and can now open the new one, which nothing uses yet:

       ```bash
       kubectl patch secret goiabada-secrets -n goiabada --type=merge --patch-file=/dev/stdin <<EOF
       {"stringData": {
         "auth-session-auth-key-previous": "$(openssl rand -hex 64)",
         "auth-session-enc-key-previous": "$(openssl rand -hex 32)",
         "admin-session-auth-key-previous": "$(openssl rand -hex 64)",
         "admin-session-enc-key-previous": "$(openssl rand -hex 32)"
       }}
       EOF
       kubectl rollout restart deployment/goiabada-authserver deployment/goiabada-adminconsole -n goiabada
       kubectl rollout status deployment/goiabada-authserver deployment/goiabada-adminconsole -n goiabada
       ```

       The patch reads the new keys from a here-document, so they never reach the process list, and adds both halves of each pair at once. The restarted pods read them through the manifest's optional references: the auth server as `GOIABADA_AUTHSERVER_SESSION_AUTHENTICATION_KEY_PREVIOUS` and `GOIABADA_AUTHSERVER_SESSION_ENCRYPTION_KEY_PREVIOUS`, the admin console as `GOIABADA_ADMINCONSOLE_SESSION_AUTHENTICATION_KEY_PREVIOUS` and `GOIABADA_ADMINCONSOLE_SESSION_ENCRYPTION_KEY_PREVIOUS`.

       When this ends, `goiabada-secrets` holds the current pairs under their usual keys and the new pairs under the four `-previous` keys.

       **Swap the pairs,** so that the new one is current and the old one previous, and restart:

       ```bash
       key() { kubectl get secret goiabada-secrets -n goiabada -o "jsonpath={.data.$1}"; }
       kubectl patch secret goiabada-secrets -n goiabada --type=merge --patch-file=/dev/stdin <<EOF
       {"data": {
         "auth-session-auth-key": "$(key auth-session-auth-key-previous)",
         "auth-session-enc-key": "$(key auth-session-enc-key-previous)",
         "admin-session-auth-key": "$(key admin-session-auth-key-previous)",
         "admin-session-enc-key": "$(key admin-session-enc-key-previous)",
         "auth-session-auth-key-previous": "$(key auth-session-auth-key)",
         "auth-session-enc-key-previous": "$(key auth-session-enc-key)",
         "admin-session-auth-key-previous": "$(key admin-session-auth-key)",
         "admin-session-enc-key-previous": "$(key admin-session-enc-key)"
       }}
       EOF
       kubectl rollout restart deployment/goiabada-authserver deployment/goiabada-adminconsole -n goiabada
       kubectl rollout status deployment/goiabada-authserver deployment/goiabada-adminconsole -n goiabada
       ```

       Every value is read before the patch is sent, so the swap is whole. During this rollout a new pod seals under the new pair and opens the old, and an old pod seals under the old pair and opens the new, so either opens every session.

       When this ends, the usual keys hold the new pairs and the `-previous` keys the old ones; the Secret must hold that before the restart.
     </TabItem>
   </Tabs>

2. **Wait for the maximum session lifetime** since the new pairs became current. It's under **Admin**, **Sessions** in the admin console, 24 hours unless you changed it, and it bounds both servers' sessions. A session is sealed under the new pair the next time it's saved, and none outlives that lifetime, so by then every signed-in session is under the new pair.

3. **Remove the previous pairs, and restart both servers,** so that nothing opens sessions under the old pair any more.

   <Tabs syncKey="platform">
     <TabItem label="Docker Compose">
       Delete the four `_PREVIOUS` lines from `docker-compose.override.yml`, then:

       ```bash
       docker compose up -d
       ```
     </TabItem>
     <TabItem label="Native binaries">
       Delete the four `_PREVIOUS` lines from the env file, then:

       ```bash
       sudo systemctl restart goiabada-authserver goiabada-adminconsole
       ```
     </TabItem>
     <TabItem label="Kubernetes">
       ```bash
       kubectl patch secret goiabada-secrets -n goiabada --type=json -p='[
         {"op": "remove", "path": "/data/auth-session-auth-key-previous"},
         {"op": "remove", "path": "/data/auth-session-enc-key-previous"},
         {"op": "remove", "path": "/data/admin-session-auth-key-previous"},
         {"op": "remove", "path": "/data/admin-session-enc-key-previous"}
       ]'
       kubectl rollout restart deployment/goiabada-authserver deployment/goiabada-adminconsole -n goiabada
       kubectl rollout status deployment/goiabada-authserver deployment/goiabada-adminconsole -n goiabada
       ```

       When this ends, `goiabada-secrets` holds its seven keys again, the session keys being the new pairs.
     </TabItem>
   </Tabs>

</Steps>

A sign-in still in progress, one not yet signed in, can still be under the old pair, so removing it may restart that sign-in, at the cost of the form being filled in. Replacing the keys in one step instead, with no previous pair, signs everybody out once.

A previous pair is read whole or not at all: a server refuses to start with one half of it set, so add and remove its two keys together.

A new auth server session authentication key also replaces the [DPoP](/concepts/dpop/) nonces the auth server hands out, and the previous key doesn't keep the old ones. Once it's current, each DPoP client's next token request is answered `use_dpop_nonce`, which its DPoP library retries with the new nonce.

## The AES key

The auth server seals what it stores with `GOIABADA_AES_ENCRYPTION_KEY`, and opens it with that key and then, when it's set, `GOIABADA_AES_ENCRYPTION_KEY_PREVIOUS`. So you make the new key current and keep the old one as the previous key, then run `goiabada-authserver reencrypt`, which moves every stored secret to the new key while the auth server goes on serving. Done this way, nothing waits for the re-encryption: on Kubernetes the rollouts keep the auth server serving throughout, and on Compose and native binaries, which run one auth server, it stops only for each restart.

Before you begin, finish any [upgrade](/deploy/upgrade-goiabada/), so every auth server runs a release with the `reencrypt` command. An older one opens stored secrets with one key alone, and can't open what a newer one seals under another.

<Steps>

1. **Back up the database, and the current key,** as [Back up the AES key](/deploy/secrets/#back-up-the-aes-key) says.

2. **Make a new key current, and the old one previous, then restart the auth server.**

   <Tabs syncKey="platform">
     <TabItem label="Docker Compose">
       Generate a new key with `openssl rand -hex 32`, and back it up as [Back up the AES key](/deploy/secrets/#back-up-the-aes-key) says: from the restart on, what the auth server seals is under it. Then, under `goiabada-authserver` in `docker-compose.override.yml`, set `GOIABADA_AES_ENCRYPTION_KEY` to it, and add the key it held before:

       ```yaml
         goiabada-authserver:
           environment:
             # ...the other entries stay as they are
             - "GOIABADA_AES_ENCRYPTION_KEY=<new, openssl rand -hex 32>"
             - "GOIABADA_AES_ENCRYPTION_KEY_PREVIOUS=<its value before>"
       ```

       Then restart:

       ```bash
       docker compose up -d --wait goiabada-authserver
       ```

       Compose stops the old container before it starts the new one, so two auth servers never run together, and one restart does it.
     </TabItem>
     <TabItem label="Native binaries">
       Generate a new key with `openssl rand -hex 32`, and back it up as [Back up the AES key](/deploy/secrets/#back-up-the-aes-key) says: from the restart on, what the auth server seals is under it. Then, in the env file, set `GOIABADA_AES_ENCRYPTION_KEY` to it, and add the key it held before:

       ```bash
       GOIABADA_AES_ENCRYPTION_KEY="<new, openssl rand -hex 32>"
       GOIABADA_AES_ENCRYPTION_KEY_PREVIOUS="<its value before>"
       ```

       Then restart:

       ```bash
       sudo systemctl restart goiabada-authserver
       ```

       The auth server runs as one process, which a restart stops before it starts the new one, so one restart does it.
     </TabItem>
     <TabItem label="Kubernetes">
       A rollout runs old and new pods side by side, and each must open what the other seals. So the new key goes in first as the previous key, and the two are then swapped, in two rollouts.

       **Add a new key as the previous key.** Every pod still seals under the current key, and can now open the new one, which nothing uses yet:

       ```bash
       kubectl patch secret goiabada-encryption-key -n goiabada --type=merge --patch-file=/dev/stdin <<EOF
       {"stringData": {"aes-encryption-key-previous": "$(openssl rand -hex 32)"}}
       EOF
       old=$(kubectl get pods -n goiabada -l app=goiabada-authserver -o name)
       kubectl rollout restart deployment/goiabada-authserver -n goiabada
       kubectl rollout status deployment/goiabada-authserver -n goiabada
       kubectl wait -n goiabada $old --for=delete --timeout=2m
       ```

       The patch reads the new key from a here-document, so it never reaches the process list. The restarted pods read it as `GOIABADA_AES_ENCRYPTION_KEY_PREVIOUS` through the manifest's optional reference.

       `rollout status` ends once the new pods are ready, while the old ones can still be finishing their requests and handed-off work. The `wait` ends once every pod listed before the restart has stopped, so no pod without the new key is left when the swap begins.

       **Back up the new key now,** as [Back up the AES key](/deploy/secrets/#back-up-the-aes-key) says: from the swap on, what the auth server seals is under it. Read it out of the cluster with:

       ```bash
       kubectl get secret goiabada-encryption-key -n goiabada -o jsonpath='{.data.aes-encryption-key-previous}' | base64 -d
       ```

       **Swap the keys,** so that the new one is current and the old one previous, and restart:

       ```bash
       aes() { kubectl get secret goiabada-encryption-key -n goiabada -o "jsonpath={.data.$1}"; }
       kubectl patch secret goiabada-encryption-key -n goiabada --type=merge --patch-file=/dev/stdin <<EOF
       {"data": {
         "aes-encryption-key": "$(aes aes-encryption-key-previous)",
         "aes-encryption-key-previous": "$(aes aes-encryption-key)"
       }}
       EOF
       old=$(kubectl get pods -n goiabada -l app=goiabada-authserver -o name)
       kubectl rollout restart deployment/goiabada-authserver -n goiabada
       kubectl rollout status deployment/goiabada-authserver -n goiabada
       kubectl wait -n goiabada $old --for=delete --timeout=2m
       ```

       Every value is read before the patch is sent, so the swap is whole. During this rollout a new pod seals under the new key and opens the old, and an old pod seals under the old key and opens the new, so either opens every stored secret.

       When the `wait` ends, every pod runs with the swapped keys: `aes-encryption-key` holds the new key, and `aes-encryption-key-previous` the key you backed up in step 1.
     </TabItem>
   </Tabs>

   Until step 3 ends, each start of the auth server logs a warning that the stored data is still under the previous key. That's expected.

3. **Run `reencrypt`,** once every auth server runs with the swapped keys. One still on the earlier keys could seal a value under the old key after `reencrypt` has passed it.

   <Tabs syncKey="platform">
     <TabItem label="Docker Compose">
       ```bash
       docker compose run --rm -T goiabada-authserver reencrypt
       ```

       It runs in a container of its own, with the auth server's configuration and both keys.
     </TabItem>
     <TabItem label="Native binaries">
       ```bash
       sudo -u goiabada sh -c 'cd /var/lib/goiabada && set -a && . /etc/goiabada/goiabada.env && set +a && exec /opt/goiabada/goiabada-authserver reencrypt'
       ```

       It runs as the service's user, from its working directory and with its `goiabada.env`, as the unit on [Native binaries](/deploy/native-binaries/#set-it-up) does, so it reaches the database the service uses, with the keys it holds.
     </TabItem>
     <TabItem label="Kubernetes">
       ```bash
       kubectl exec -n goiabada deployment/goiabada-authserver -- /app/goiabada-authserver reencrypt
       ```

       It runs in a pod of the Deployment, which holds the swapped keys once step 2's `wait` has ended.
     </TabItem>
   </Tabs>

   `reencrypt` moves the stored secrets one at a time, beside the running auth servers, and prints how many it re-encrypted. It exits 0 once every stored secret is under the current key, and 1 otherwise, naming on stderr each value neither key opens. A stop, such as Ctrl-C, ends it between two values: run it again to carry on.

4. **Remove the previous key, and restart the auth server,** only once `reencrypt` exits 0. Until then, some stored secrets may still be under the previous key, and nothing without it can open them.

   <Tabs syncKey="platform">
     <TabItem label="Docker Compose">
       Delete the `GOIABADA_AES_ENCRYPTION_KEY_PREVIOUS` line from `docker-compose.override.yml`, then:

       ```bash
       docker compose up -d --wait goiabada-authserver
       ```
     </TabItem>
     <TabItem label="Native binaries">
       Delete the `GOIABADA_AES_ENCRYPTION_KEY_PREVIOUS` line from the env file, then:

       ```bash
       sudo systemctl restart goiabada-authserver
       ```
     </TabItem>
     <TabItem label="Kubernetes">
       ```bash
       kubectl patch secret goiabada-encryption-key -n goiabada --type=json \
         -p='[{"op": "remove", "path": "/data/aes-encryption-key-previous"}]'
       kubectl rollout restart deployment/goiabada-authserver -n goiabada
       kubectl rollout status deployment/goiabada-authserver -n goiabada
       ```

       The restart takes the old key out of the pods' environment. When this ends, `goiabada-encryption-key` holds the new key alone.
     </TabItem>
   </Tabs>

   To check, run `reencrypt` again as in step 3. With no previous key, it re-encrypts nothing, and exits 0 only when every stored secret opens under the current key alone. That run is the proof: a start checks only the current signing key, which `reencrypt` moves last, and refuses to start when no key it holds opens it, so a previous key removed before `reencrypt` reached its end is caught at the next start, but a value elsewhere that no key opens isn't.

</Steps>

Keep the old key as long as you keep a database backup taken under it, and both keys with a backup taken during the rotation: see [Back up the AES key](/deploy/secrets/#back-up-the-aes-key).

### Off the published sample key

The auth server refuses the sample key `00112233…eeff` from this repository's old Compose files as `GOIABADA_AES_ENCRYPTION_KEY`, so no auth server can run with it beside the new key as the previous key, and the ones still running under it open stored secrets with one key alone. So this rotation stops every auth server first, and begins at step 2, with the sample key as `GOIABADA_AES_ENCRYPTION_KEY_PREVIOUS`.

  </TabItem>
  <TabItem label="Native binaries">

  </TabItem>
  <TabItem label="Kubernetes">
    A rollout always overlaps old and new pods, at one replica too, since the generated `maxSurge: 1` starts the new pod before it stops the old one. So stop every auth server pod, then make a new key current and the sample key previous in one patch:

    ```bash
    kubectl scale deployment goiabada-authserver -n goiabada --replicas=0
    kubectl wait pod -n goiabada -l app=goiabada-authserver --for=delete --timeout=2m
    kubectl patch secret goiabada-encryption-key -n goiabada --type=merge --patch-file=/dev/stdin <<EOF
    {"data": {"aes-encryption-key-previous": "$(kubectl get secret goiabada-encryption-key -n goiabada -o jsonpath='{.data.aes-encryption-key}')"},
     "stringData": {"aes-encryption-key": "$(openssl rand -hex 32)"}}
    EOF
    ```

    Back up the new key, `aes-encryption-key`, as [Back up the AES key](/deploy/secrets/#back-up-the-aes-key) says. Then start the auth server with your replica count. If you're upgrading at the same time, apply the new release's manifest, as in [Update to a new release](/deploy/upgrade-goiabada/#update-to-a-new-release), which sets it; otherwise:

    ```bash
    kubectl scale deployment goiabada-authserver -n goiabada --replicas=<n>
    kubectl rollout status deployment/goiabada-authserver -n goiabada
    ```

    The auth server is down from the scale to zero until its pods are ready, and the admin console's requests to it fail meanwhile. A GitOps tool would put its replicas back, so suspend its sync first, as [Rotating Secrets something else owns](/deploy/kubernetes/secrets/#rotating-secrets-something-else-owns) says. Then run step 3 and step 4:

    ```bash
    kubectl exec -n goiabada deployment/goiabada-authserver -- /app/goiabada-authserver reencrypt
    ```
  </TabItem>
</Tabs>

### If the old key may have leaked

Anyone who read the database or one of its backups can decrypt everything the old key sealed, and the sample key is public. Once `reencrypt` has exited 0, replace what the old key sealed too:

- **Every client secret:** **Generate a new secret** on each confidential client's **Authentication** tab, then give your app the new one. For the admin console's client, see [the admin console's client secret](#the-admin-consoles-client-secret).
- **The SMTP password:** change it with your mail provider, then under **Admin**, **Email** in the admin console.
- **The Turnstile secret key:** rotate it on the widget in the Cloudflare dashboard, then save the new one under **Admin**, **Turnstile**.
- **The signing keys:** `/certs` publishes three, the next, the current and the previous one, and each press of **Rotate keys** under **Admin**, **Signing keys** deletes the oldest and creates a new one, so it takes three presses to replace them all. Tokens signed by the old keys stop verifying, refresh tokens included, and their users sign in again.
- **Every user's two-factor authentication:** rotating the key seals each user's authenticator secret again unchanged, so whoever read it can still compute their codes. For each user with two-factor authentication, an administrator clears **Enabled** under **Two-factor authentication** on the user's **Authentication** tab, and the user sets it up again under **Two-factor authentication** in their account, which draws a new secret. Ask users to wait 15 minutes after the key rotation first, so a set-up started under the old key has expired.

## The database password

`GOIABADA_DB_PASSWORD` is the password of the database user the auth server signs in as, `GOIABADA_DB_USERNAME`. The database checks a password only when a connection opens, so a running auth server keeps the connections it holds through a change, and opens every new one with the password it started with. What a rotation costs depends on whether the database accepts two passwords for one user at once: MySQL 8.0.14 and later do, PostgreSQL and SQL Server don't.

<Aside title="On Docker Compose">
The generated Compose file has the auth server sign in as the database service's administrator: `root` on MySQL, `postgres` on PostgreSQL, `sa` on SQL Server. The override holds the password twice, as `GOIABADA_DB_PASSWORD` under `goiabada-authserver` and as the database service's own variable, `MYSQL_ROOT_PASSWORD`, `POSTGRES_PASSWORD` or `MSSQL_SA_PASSWORD`. The image reads that variable only to set up an empty volume, so changing it changes nothing in the database: the steps change the password in the database, and keep both variables matching it.
</Aside>

### On MySQL

<Steps>

1. **Give the user its new password, keeping the current one** as a second password that's still accepted. `openssl rand -hex 32` makes one.

   <Tabs syncKey="platform">
     <TabItem label="Docker Compose">
       The image creates `root` twice: for connections from other containers (`%`), which is the auth server's, and from inside its own (`localhost`). In `docker compose exec mysql-server mysql -uroot -p`:

       ```sql
       ALTER USER 'root'@'%' IDENTIFIED BY '<new password>' RETAIN CURRENT PASSWORD;
       ALTER USER 'root'@'localhost' IDENTIFIED BY '<new password>' RETAIN CURRENT PASSWORD;
       ```
     </TabItem>
     <TabItem label="Native binaries">
       Name the user and host your deployment signs in as:

       ```sql
       ALTER USER 'goiabada'@'%' IDENTIFIED BY '<new password>' RETAIN CURRENT PASSWORD;
       ```

       Run it as an account with the `CREATE USER` privilege; the user itself can run it on its own account only with `APPLICATION_PASSWORD_ADMIN`.
     </TabItem>
     <TabItem label="Kubernetes">
       Name the user and host your deployment signs in as, the `GOIABADA_DB_USERNAME` of `goiabada-authserver-config`:

       ```sql
       ALTER USER 'goiabada'@'%' IDENTIFIED BY '<new password>' RETAIN CURRENT PASSWORD;
       ```

       Run it as an account with the `CREATE USER` privilege; the user itself can run it on its own account only with `APPLICATION_PASSWORD_ADMIN`.
     </TabItem>
   </Tabs>

2. **Store the new password where the auth server reads it, and restart the auth server.** During the restart the old password and the new one are both accepted, so nothing fails.

   <Tabs syncKey="platform">
     <TabItem label="Docker Compose">
       In `docker-compose.override.yml`, set `GOIABADA_DB_PASSWORD` and `MYSQL_ROOT_PASSWORD` to the new password, then restart the auth server alone:

       ```bash
       docker compose up -d --no-deps goiabada-authserver
       ```

       Without `--no-deps`, Compose would also recreate the database's container, whose variable changed, restarting the database under the auth server. That container takes the new value the next time it's recreated, which changes nothing in the database.
     </TabItem>
     <TabItem label="Native binaries">
       Set `GOIABADA_DB_PASSWORD` to the new password in the env file, then:

       ```bash
       sudo systemctl restart goiabada-authserver
       ```
     </TabItem>
     <TabItem label="Kubernetes">
       ```bash
       read -rsp 'New database password: ' DB_PASSWORD; echo
       kubectl patch secret goiabada-secrets -n goiabada --type=merge --patch-file=/dev/stdin <<EOF
       {"data": {"db-password": "$(printf %s "$DB_PASSWORD" | base64 | tr -d '\n')"}}
       EOF
       unset DB_PASSWORD
       kubectl rollout restart deployment/goiabada-authserver -n goiabada
       kubectl rollout status deployment/goiabada-authserver -n goiabada
       ```

       The value goes in base64, under `data`, so no character of the password needs escaping. During the rollout old pods sign in with the old password and new pods with the new. When this ends, `db-password` holds the new password.
     </TabItem>
   </Tabs>

3. **Discard the old password** once the auth server is back.

   <Tabs syncKey="platform">
     <TabItem label="Docker Compose">
       ```sql
       ALTER USER 'root'@'%' DISCARD OLD PASSWORD;
       ALTER USER 'root'@'localhost' DISCARD OLD PASSWORD;
       ```
     </TabItem>
     <TabItem label="Native binaries">
       ```sql
       ALTER USER 'goiabada'@'%' DISCARD OLD PASSWORD;
       ```
     </TabItem>
     <TabItem label="Kubernetes">
       ```sql
       ALTER USER 'goiabada'@'%' DISCARD OLD PASSWORD;
       ```
     </TabItem>
   </Tabs>

</Steps>

### On PostgreSQL and SQL Server

These hold one password per user, which a change replaces at once, so the auth server has to restart right after it.

<Steps>

1. **Store the new password where the auth server reads it, without restarting anything.** No running server reads it, and it's now stored before the database depends on it. On PostgreSQL, `openssl rand -hex 32` makes one; SQL Server's password policy asks for three of upper case, lower case, digits and symbols, which a hex string lacks.

   <Tabs syncKey="platform">
     <TabItem label="Docker Compose">
       In `docker-compose.override.yml`, set `GOIABADA_DB_PASSWORD` and `POSTGRES_PASSWORD` or `MSSQL_SA_PASSWORD` to the new password.
     </TabItem>
     <TabItem label="Native binaries">
       Set `GOIABADA_DB_PASSWORD` to the new password in the env file.
     </TabItem>
     <TabItem label="Kubernetes">
       Run the `kubectl patch` of the MySQL step 2, without the restart. A pod that starts before step 2 can't sign in, stops, and is restarted until step 2 is done. When this ends, `db-password` holds the new password.
     </TabItem>
   </Tabs>

2. **Change the user's password to the same value.** On PostgreSQL, `\password` asks for the new password twice without echoing it, and sends it hashed, so it reaches neither the server log nor `psql`'s history.

   <Tabs syncKey="platform">
     <TabItem label="Docker Compose">
       On PostgreSQL, run `docker compose exec postgres-server psql -U postgres`, then:

       ```sql
       \password postgres
       ```

       On SQL Server, in `docker compose exec mssql-server /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -C`, which asks for the current password:

       ```sql
       ALTER LOGIN sa WITH PASSWORD = '<new password>';
       GO
       ```
     </TabItem>
     <TabItem label="Native binaries">
       On PostgreSQL, in `psql`, as the user itself or a role allowed to change its password:

       ```sql
       \password goiabada
       ```

       On SQL Server, as a login with the `ALTER ANY LOGIN` permission, or as `goiabada` itself with `OLD_PASSWORD = '<current password>'` added:

       ```sql
       ALTER LOGIN goiabada WITH PASSWORD = '<new password>';
       ```
     </TabItem>
     <TabItem label="Kubernetes">
       On PostgreSQL, in `psql`, as the user itself or a role allowed to change its password:

       ```sql
       \password goiabada
       ```

       On SQL Server, as a login with the `ALTER ANY LOGIN` permission, or as `goiabada` itself with `OLD_PASSWORD = '<current password>'` added:

       ```sql
       ALTER LOGIN goiabada WITH PASSWORD = '<new password>';
       ```
     </TabItem>
   </Tabs>

3. **Restart the auth server at once.**

   <Tabs syncKey="platform">
     <TabItem label="Docker Compose">
       ```bash
       docker compose up -d --no-deps goiabada-authserver
       ```

       Without `--no-deps`, Compose would also recreate the database's container, whose variable changed, restarting the database under the auth server. On SQL Server that container's healthcheck signs in with the value it holds, so it reports unhealthy until it's recreated: recreate it with `docker compose up -d` when a short database restart suits.
     </TabItem>
     <TabItem label="Native binaries">
       ```bash
       sudo systemctl restart goiabada-authserver
       ```
     </TabItem>
     <TabItem label="Kubernetes">
       ```bash
       kubectl rollout restart deployment/goiabada-authserver -n goiabada
       kubectl rollout status deployment/goiabada-authserver -n goiabada
       ```
     </TabItem>
   </Tabs>

</Steps>

Between steps 2 and 3, a running auth server keeps the connections it holds, but each one it opens is refused, and the request that needed it fails with a 500. It opens connections as its traffic grows, and replaces each after 5 idle minutes (`GOIABADA_DB_CONN_MAX_IDLE_TIME`) or 30 minutes of life (`GOIABADA_DB_CONN_MAX_LIFETIME`), so the shorter the gap, the fewer requests fail.

If the auth server then stops with `Access denied`, `password authentication failed` or `Login failed` in its log, the password you stored and the database's disagree: set the database user's password to the one you stored. On Kubernetes, read it back with `kubectl get secret goiabada-secrets -n goiabada -o jsonpath='{.data.db-password}' | base64 -d`.

## The admin console's client secret

`GOIABADA_ADMINCONSOLE_OAUTH_CLIENT_SECRET` is the secret of the admin console's client, `admin-console-client`, which the auth server keeps, encrypted, in its database. The auth server reads its own copy only at its first start, to create that client, so it needs no restart. The admin console presents the secret on every sign-in, on every refresh of an administrator's access token, and for the token it asks for to reach its own sessions. So a rotation changes the client's secret in the database and the admin console's copy, then restarts the admin console.

<Steps>

1. In the admin console, open **Clients**, then `admin-console-client`, then its **Authentication** tab. Click **Generate a new secret**, then **Copy**. Don't save yet.

2. **Store the copied secret where the admin console reads it.** Nothing reads it before a restart, and it's now stored before the database depends on it.

   <Tabs syncKey="platform">
     <TabItem label="Docker Compose">
       Paste it as `GOIABADA_ADMINCONSOLE_OAUTH_CLIENT_SECRET` under both services in `docker-compose.override.yml`. The auth server's copy is read only to set up an empty database, so it can take the new one at its next restart.
     </TabItem>
     <TabItem label="Native binaries">
       Paste it as `GOIABADA_ADMINCONSOLE_OAUTH_CLIENT_SECRET` in the env file.
     </TabItem>
     <TabItem label="Kubernetes">
       ```bash
       read -rsp 'New client secret: ' CLIENT_SECRET; echo
       kubectl patch secret goiabada-secrets -n goiabada --type=merge --patch-file=/dev/stdin <<EOF
       {"stringData": {"oauth-client-secret": "$CLIENT_SECRET"}}
       EOF
       unset CLIENT_SECRET
       ```

       A generated secret holds letters, digits, `-`, `_` and `.` alone, so it needs no escaping. An admin console pod that starts before step 3 stops at once, because the auth server refuses the new secret until then, and the earlier pods keep serving. When this ends, `oauth-client-secret` holds the new secret.
     </TabItem>
   </Tabs>

3. **Save** the page, and confirm with **Save**: the dialog warns that you're changing the client secret, and that this is the admin console's own client. The database now holds the new secret.

4. **Restart the admin console at once,** then check by signing in from a private window.

   <Tabs syncKey="platform">
     <TabItem label="Docker Compose">
       ```bash
       docker compose up -d --no-deps goiabada-adminconsole
       ```

       Without `--no-deps`, Compose would also recreate the auth server, whose copy changed, stopping sign-in while it restarts.
     </TabItem>
     <TabItem label="Native binaries">
       ```bash
       sudo systemctl restart goiabada-adminconsole
       ```
     </TabItem>
     <TabItem label="Kubernetes">
       ```bash
       kubectl rollout restart deployment/goiabada-adminconsole -n goiabada
       kubectl rollout status deployment/goiabada-adminconsole -n goiabada
       ```

       The rollout completes only once the auth server accepts the secret the new pods hold: a pod it refuses stops before it listens, and the rollout waits with the earlier pods still serving. Sign in from the private window all the same.
     </TabItem>
   </Tabs>

</Steps>

Between steps 3 and 4, the auth server refuses the old secret, which the running admin console presents. A sign-in fails at its last step, an administrator whose access token falls due is signed out, and once the token the admin console holds for its sessions expires, within the access token lifetime, 5 minutes unless you changed it, every page behind the sign-in answers 500. Administrators signed in before step 3 stay signed in through the restart. The auth server and every other client work throughout.

If the admin console can no longer sign you in, because the database holds a secret its copy doesn't, [Locked out of the admin console](/troubleshooting/locked-out-of-the-admin-console/#the-admin-consoles-client-secret-changed) sets a secret you know through the admin API. Have the client it needs before you rotate: once the admin console is locked out, it's the only way back in.

## The admin password

`GOIABADA_ADMIN_PASSWORD` is read only by the first start, which creates the administrator. Change the administrator's password in the admin console; changing the variable changes nothing.
