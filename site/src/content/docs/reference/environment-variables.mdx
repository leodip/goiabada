Goiabada consists of two applications, each with its own configuration:

- **Auth server** (`goiabada-authserver`) - Handles authentication, OAuth2/OIDC endpoints, and database access
- **Admin console** (`goiabada-adminconsole`) - Provides the administrative interface

Configuration can be set via **environment variables** or **command-line flags**. When both are set, flags take precedence. Each binary accepts only the flags it acts on; a flag belonging to the other application is rejected.

The four pool settings apply to PostgreSQL, MySQL and SQL Server. A value out of range stops the auth
server at start, on one line naming every bad value, exit code 2; a bare number of seconds such as
`1800` is refused, because a duration needs its unit. The values are checked on SQLite too, but
otherwise ignored there: SQLite always runs on one connection. Every start writes one
`database connection pool` record with the pool it opened. The `migrate` subcommand reads the same
settings. With several replicas, every pod opens its own pool against one database: see
[Kubernetes](/deploy/kubernetes/#scale-replicas) for sizing it against
`max_connections`.

<Aside type="tip">
For SQLite with a file, use: `file:/path/to/goiabada.db?_pragma=busy_timeout=5000&_pragma=journal_mode=WAL`

- **busy_timeout=5000**: Waits up to 5 seconds when the database is locked by another connection, instead of failing immediately. Essential for handling concurrent requests.
- **journal_mode=WAL**: Enables Write-Ahead Logging, which allows concurrent reads while writing and improves performance. Without WAL, readers block writers and vice versa.
</Aside>

### Network configuration

The **base URL** is the public URL users see in their browser. The **internal base URL** is used by the admin console for server-to-server API calls. In containerized environments, internal URLs bypass external DNS/proxies for faster, more reliable communication (e.g., `http://goiabada-authserver:9090` instead of `https://auth.example.com`).

These variables are read by **both applications**: the auth server uses them for JWT issuer and seeding, while the admin console uses them to connect to the auth server.

### Listen addresses and IPv6

A listen host is an address on this machine, not the public URL: browsers and clients reach the server through `GOIABADA_AUTHSERVER_BASEURL` and `GOIABADA_ADMINCONSOLE_BASEURL`, and the listen hosts only decide which of this machine's addresses accept connections.

- **`0.0.0.0`, the default, already serves IPv6.** Goiabada opens one socket from it that accepts both IPv4 and IPv6 connections, and `::` means the same thing. On a host with IPv6 switched off it quietly serves IPv4 alone.
- **A specific address serves only its own family.** `127.0.0.1` accepts no IPv6 connection and `::1` no IPv4 one. A hostname such as `localhost` binds only the first address it resolves to, so prefer a literal address.
- **Write an IPv6 address bare, as `::1` or `2001:db8::10`.** Brackets are accepted too (`[::1]`) and mean the same address. A link-local address takes its zone: `fe80::1%eth0`.

<Aside type="tip" title="Rate limiting details">
When enabled, Goiabada applies rate limits to security-sensitive endpoints:

| Endpoint | Limit | Counts | Key |
|----------|-------|--------|-----|
| `POST /auth/pwd` (password login) | 10 / 15min | failed sign-ins | IP address (IPv6 grouped by /64) + email (lowercased) |
| `POST /auth/pwd` (password login) | 100 / 60min | failed sign-ins | email (lowercased) |
| `POST /auth/pwd` (password login) | 30 / min | every request | IP address (IPv6 grouped by /64) |
| `POST /auth/otp` (OTP verification) | 5 / 15min | failed codes | user ID |
| `POST /api/v1/account/email/verification` | 5 / 15min | failed codes | access token subject |
| `POST /api/v1/account/email/verification/send` | 5 / 60min | every request | access token subject |
| `PUT /api/v1/account/password` | 5 / 15min | failed passwords | access token subject, shared with `PUT /api/v1/account/otp` and `PUT /api/v1/account/email` |
| `PUT /api/v1/account/otp` | 5 / 15min | failed passwords | access token subject, shared with `PUT /api/v1/account/password` and `PUT /api/v1/account/email` |
| `PUT /api/v1/account/email` | 5 / 15min | failed passwords | access token subject, shared with `PUT /api/v1/account/password` and `PUT /api/v1/account/otp` |
| `POST /forgot-password` | 5 / 5min | every request | email (lowercased) |
| `POST /forgot-password` | 20 / 5min | every request | IP address (IPv6 grouped by /64) |
| `GET` and `POST /reset-password` | 30 / 5min | every request | IP address (IPv6 grouped by /64) |
| `POST /account/register` (self-registration) | 5 / 5min | every request | email (lowercased) |
| `POST /account/register` (self-registration) | 20 / 5min | every request | IP address (IPv6 grouped by /64) |
| `GET` and `POST /account/activate` | 30 / 5min | every request | IP address (IPv6 grouped by /64) |
| `POST /connect/register` (DCR) | 10 / min | every request | IP address (IPv6 grouped by /64) |
| `POST /auth/token` (ROPC grant) | 10 / 15min | failed sign-ins | IP address (IPv6 grouped by /64) + username (lowercased), shared with `POST /auth/pwd` |
| `POST /auth/token` (ROPC grant) | 100 / 60min | failed sign-ins | username (lowercased), shared with `POST /auth/pwd` |
| `POST /auth/token` (ROPC grant) | 30 / min | every request | IP address (IPv6 grouped by /64) |

A limit that counts failures is not spent by a successful sign-in, so signing in normally never uses it up.

Shared means one budget, not two of the same size: a wrong password counts the same whether it arrives at the login form or at the password grant, and the same whether it arrives at the password, OTP or email change.

**Shared across replicas.** On PostgreSQL, MySQL and SQL Server, the limits that count failures (failed sign-ins, failed codes and failed passwords in the table) are counted in the database, so every replica of the auth server spends one budget and a rollout does not refill it. On SQLite, which runs as a single replica, they are counted in the process. If the database cannot answer one of these checks within 5 seconds, the request is refused with a server error (500, in the endpoint's usual error format) rather than allowed through, and no rate-limit event is recorded.

**Per pod.** The limits that count every request are counted in each auth server process, on every database: a deployment running several replicas multiplies each of them by the replica count, and a rollout resets them. They bound floods and outbound mail rather than guessing. For a request limit that holds across the whole deployment, put one at your gateway, reverse proxy, CDN or cloud WAF, which also stops a flood before it reaches the auth server. The `rate_limit_exceeded` audit event is likewise recorded at most once per key and window by each replica.

**Keyed on IP addresses.** A limit keyed on an IP address is only as good as the client IP Goiabada resolves. Behind a reverse proxy it takes `TRUST_PROXY_HEADERS`. One hop, with `TRUSTED_PROXIES` empty, is sound behind a proxy that sets or appends `X-Forwarded-For`; a second proxy hop in front also takes `TRUSTED_PROXIES`. Either way, a caller that reaches Goiabada without passing the proxy can forge the address it is counted under. See [client IP resolution](/deploy/reverse-proxy/#client-ip-resolution-and-spoofing-protection).
</Aside>

### Bootstrap

There are two ways to bootstrap Goiabada:

**Recommended: Single-step bootstrap** using `GOIABADA_ADMINCONSOLE_OAUTH_CLIENT_SECRET`. Pre-generate credentials (e.g., using `goiabada-setup`) and provide them to both services. The auth server seeds the database and continues running normally.

**Legacy: Two-step bootstrap** using `GOIABADA_AUTHSERVER_BOOTSTRAP_ENV_OUTFILE`. The auth server generates credentials, writes them to a file, and exits. You then copy the credentials to your configuration and restart. This approach requires manual intervention between steps.

<Aside type="note" title="Understanding GOIABADA_ADMINCONSOLE_OAUTH_CLIENT_SECRET">
This variable serves different purposes depending on which application reads it:

**On auth server (seeding only):** When the auth server starts for the first time and seeds the database, it creates an OAuth client for the admin console. If this variable is set, the auth server uses its value as the client secret. After the initial database seed, this variable is no longer needed by the auth server and can be removed from its configuration.

**On admin console (runtime):** The admin console uses this secret to authenticate with the auth server via OAuth2. It needs this credential to obtain access tokens and make API calls to manage users, clients, and other resources. This variable must remain configured for the admin console to function.

**Both applications must have the same value** during initial setup. The setup wizard automatically generates a matching secret for both.
</Aside>

## Session keys

Both applications require session keys for cookie security in production.

### Generate keys

```bash
# Authentication key (64 bytes = 128 hex characters)
openssl rand -hex 64

# Encryption key (32 bytes = 64 hex characters)
openssl rand -hex 32
```

### Key purposes

- **Authentication key** (64 bytes): seals the cookie and stored session
- **Encryption key** (32 bytes): the same; both are needed

<Aside type="caution">
Never use plain text passwords or example keys. Always generate fresh cryptographic keys for each deployment.
</Aside>

### Rotating the session keys

To change the session keys, move each application's current pair into the four `_PREVIOUS` variables, set the four current variables to freshly generated keys, then restart both applications. Each seals new sessions with the new pair and still opens sessions sealed under the previous one, so nobody is signed out. Remove the `_PREVIOUS` variables once the maximum session lifetime has passed, after which every signed-in session is sealed under the new pair. A sign-in in progress is not, so removing them may restart one. Skip them entirely and everybody signs in again once.

## Data-at-rest encryption key

The **auth server** requires `GOIABADA_AES_ENCRYPTION_KEY`. It is a hex-encoded 32-byte key used to encrypt sensitive values before they are written to the database. The **admin console does not use it** (it has no direct database access and delegates to the auth server API), so set it on the auth server only.

### Generate the key

```bash
# 32 bytes = 64 hex characters
openssl rand -hex 32
```

### What it protects

The key encrypts secrets at rest, including:

- Client secrets
- SMTP and SMS provider credentials
- Email and phone verification codes
- OTP (2FA) seeds
- RSA signing keys used to sign tokens

<Aside type="danger" title="Back up this key separately from the database">
Store `GOIABADA_AES_ENCRYPTION_KEY` in a secure location that is **separate from your database backups**. If this key is lost, every encrypted secret and signing key becomes permanently unrecoverable. There is no way to decrypt the data without it.
</Aside>

### Rotating the key

**Rotating to a new key.** To change the key later, set `GOIABADA_AES_ENCRYPTION_KEY` to the new key and `GOIABADA_AES_ENCRYPTION_KEY_PREVIOUS` to the old key, then restart the auth server. At startup it detects that the data is still encrypted under the previous key and re-encrypts everything to the new key (a single transaction). The operation is idempotent, so it is safe to leave `GOIABADA_AES_ENCRYPTION_KEY_PREVIOUS` set across restarts, but you should remove it once the rotation is confirmed. If the data decrypts under neither key, the auth server refuses to start rather than risk corrupting it.

## Architecture note (v1.2+)

Since version 1.2, only the **auth server accesses the database directly**. The admin console communicates with the auth server via HTTP APIs using OAuth2 authentication.

This means:
- Database variables (`GOIABADA_DB_*`) are only used by the auth server
- The admin console requires OAuth credentials to authenticate with the auth server
- The admin console does not need database configuration
