This guide makes the pages your users see look and read like your product, in their language.

There are three levels, from a setting in the admin console to your own copy of the pages. Start with the first: most deployments need nothing more.

## Brand the pages

<Steps>

1. In the admin console, open **Admin**, **General** and set **App name**, up to 30 characters. It's shown at the top of the sign-in pages and ends their titles, as in "Sign in – Acme". It also signs every email, and it's the name authenticator apps list your users' accounts under.

2. Open **Admin**, **Theme** and choose a **Color theme**. It applies to the sign-in pages and the admin console alike. A new install starts on **Automatic**, which follows each visitor's device. To use your own colors, see [Regenerate the CSS](#regenerate-the-css).

3. Give each client a display name and a logo, so users see which app they're signing in to. See [Clients](/concepts/clients/#display-name-description-and-logo).

</Steps>

## Add a language

The pages come in English, Portuguese (Brazil), Spanish, French, Italian and German. To add another language, you translate one file of text and point both servers at it, with no rebuild.

<Steps>

1. Get the English text of the release you run: `src/core/i18n/catalogs/active.en.toml` in [the source](https://github.com/leodip/goiabada) at that release's tag, such as `v1.7.0`. The release is in the image tag and in the `build information` line each server logs when it starts.

2. Copy it into a folder named `catalogs`, as `active.<language>.toml`, named with the language's [BCP 47](https://www.rfc-editor.org/info/bcp47) tag: `active.nl.toml` for Dutch. Translate the text on the right of each `=` and leave the keys on the left as they are:

   ```toml title="catalogs/active.nl.toml"
   "auth.pwd.title" = "Aanmelden"
   "auth.pwd.email_label" = "E-mailadres"
   "auth.pwd.password_label" = "Wachtwoord"
   "auth.pwd.button" = "Aanmelden"
   ```

   Keep a placeholder such as `{{.appName}}` exactly as it is: the server writes the value there. A key you leave out, or leave empty, shows in English.

3. Make the folder that holds `catalogs` readable by both servers, and set `GOIABADA_I18N_OVERRIDES_DIR` to it on the auth server and on the admin console. In a container, mount it read-only, as the [templates are mounted](#change-the-templates) below.

4. Restart both servers. Each reads the catalogs once, at start, and refuses to start when one doesn't parse, naming the file.

5. Users choose it as their **Page language** under **Account**, **Profile** in the admin console, and your app can ask for it on the sign-in pages with `ui_locales`. See [how the language is chosen](#how-the-language-is-chosen).

</Steps>

## Change a few words

To reword a page in a language Goiabada already has, override only the keys you change, in the same folder:

```toml title="catalogs/active.en.toml"
"auth.pwd.title" = "Sign in to Acme"
```

Every key you don't name keeps the built-in text. Set `GOIABADA_I18N_OVERRIDES_DIR` and restart, as in [Add a language](#add-a-language).

## Change the templates

To change the layout of a page, or an email's body, you give a server its own copy of the templates. The templates and static files are compiled into each server's binary, and the images hold the binary alone, so there's no `web` folder inside a container to copy out.

<Steps>

1. Copy the web files from the source of the release you run, since a template from another release may use data the server no longer passes to it:

   ```bash
   RELEASE=v1.7.0   # replace with the release you run
   git clone --depth 1 --branch "$RELEASE" https://github.com/leodip/goiabada.git goiabada-source

   mkdir authserver-web adminconsole-web
   cp -r goiabada-source/src/authserver/web/{template,static,tailwindcss} authserver-web/
   cp -r goiabada-source/src/adminconsole/web/{template,static,tailwindcss} adminconsole-web/
   ```

   `tailwindcss` isn't served: it's what [regenerating the CSS](#regenerate-the-css) reads.

2. Edit the templates. They're Go [`html/template`](https://pkg.go.dev/html/template) files. Keep the element IDs and the scripts the pages use, or the forms stop working. Put a script of your own in a file in the `static` directory and load it with `<script src="{{ asset "/static/your-file.js" }}" defer></script>`, since the servers' [`Content-Security-Policy`](/reference/security/#response-headers) makes the browser refuse an inline `<script>`, an `on…` attribute such as `onclick`, a `javascript:` URL and a `<base>` element (a `<script type="application/json">` data block is fine).

3. Make the files readable by the containers. Both images run as uid 10001 and gid 10001 (see [the user the images run as](/deploy/docker-compose/#the-user-the-images-run-as)), and a page whose template the server can't read fails with a 500:

   ```bash
   chmod -R a+rX authserver-web adminconsole-web
   ```

4. Mount each directory read-only and point its server at it, in `docker-compose.override.yml`, which a run of the setup wizard with `--keep-secrets` leaves as it is. Add the volumes and the variables to the two services already there, beside their secrets. They add to the volumes `docker-compose.yml` gives each service, and win over the empty values it lists:

   ```yaml
   goiabada-authserver:
     volumes:
       - ./authserver-web/template:/app/web/template:ro
       - ./authserver-web/static:/app/web/static:ro
     environment:
       - "GOIABADA_AUTHSERVER_STATICDIR=/app/web/static"
       - "GOIABADA_AUTHSERVER_TEMPLATEDIR=/app/web/template"

   goiabada-adminconsole:
     volumes:
       - ./adminconsole-web/template:/app/web/template:ro
       - ./adminconsole-web/static:/app/web/static:ro
     environment:
       - "GOIABADA_ADMINCONSOLE_STATICDIR=/app/web/static"
       - "GOIABADA_ADMINCONSOLE_TEMPLATEDIR=/app/web/template"
   ```

   Leave a server's pair empty if you haven't changed its files. Then run `docker compose up -d`. With the native binaries, set the same variables in the env file, naming directories the binaries' user can read.

5. Open every page you changed. A mistake in a template shows only when its page is rendered.

</Steps>

<Aside type="caution">
A directory replaces the built-in set **whole**, so it must hold every file of that set, not only the ones you change. When you upgrade Goiabada, copy the new release's files again and redo your changes on them.
</Aside>

## Regenerate the CSS

The pages are styled with [Tailwind CSS](https://tailwindcss.com/), and `main.css` holds only the classes the templates used when it was generated. A class you add to a template does nothing until you regenerate it.

The colors are tokens at the top of `tailwindcss/ui.css`: the light palette in its `@theme` block, and the dark one under `@variant dark` just below. Change them there and regenerate, keeping each text color readable on the background it's drawn on, in both palettes. Each server has its own copy of `ui.css`, so change both if you want the sign-in pages and the admin console to match.

<Steps>

1. Download the standalone Tailwind CLI for your platform from [Tailwind's releases](https://github.com/tailwindlabs/tailwindcss/releases), at the version the release you copied pins: `tools.tailwind` in `goiabada-source/src/authserver/versions.yaml`. Rename it to `tailwindcss` and make it executable.

2. Run it in each web directory whose templates or `ui.css` you changed. Add `--minify` for a smaller file:

   ```bash
   cd authserver-web
   tailwindcss -i ./tailwindcss/input.css -o ./static/main.css
   ```

   `input.css` looks for class names in `../template` and in the JavaScript in `../static`, so keep the three folders side by side.

3. The new `main.css` is in the static directory you mounted, so the server serves it at once. The pages link it by a fingerprint of its contents, so browsers fetch the new one on their next page load.

</Steps>

## How the language is chosen

On the auth server's pages and in the admin console, the language is the first of these that names one:

1. The user's **Page language**, which they choose under **Account**, **Profile** in the admin console. An administrator can set it too, on the user's **Profile** page.
2. A `ui_locales` parameter: one or more language tags in order of preference, separated by single spaces, such as `ui_locales=es pt-BR`. On the auth server, it's the authorization request's or the [sign-out](/reference/endpoints/logout/)'s. It's kept for the rest of that sign-in, and applies to the error page the auth server shows when it refuses the request outright. In the admin console, it's `?ui_locales=` in the page's address.
3. The browser's `Accept-Language` header.
4. English.

A user on **Automatic**, where everyone starts, skips the first. So does a page drawn for nobody Goiabada knows yet, which is why your app's `ui_locales` still matters:

- The admin console uses the page language once the user has signed in to it.
- The auth server uses it once the user has entered their password: on the one-time code, recovery code and consent pages, on signing out, and on every page shown to a browser that's signed in.
- A browser that isn't signed in gets the sign-in, forgot password, registration and activation pages in the language of the other sources, since the auth server doesn't know who's there. The email address typed on the sign-in page never picks the language, so the page can't reveal an account's language to whoever types it.
- The password reset page, opened from the email, is in the page language of the user the link is for.

The auth server reads the page language each time it draws a page, so a change shows on its next page. The admin console reads it when the user signs in to it. A change they save there shows on their next page, and one made elsewhere, such as by an administrator, reaches them when they next sign in or open their profile.

The **Page language** list holds the languages Goiabada has text for, yours included. A user whose language you later remove is back on **Automatic**.

For `ui_locales` and `Accept-Language`, the first of their languages Goiabada has text for wins, or English when it has none of them: `ui_locales=sv nl` shows Dutch when you've added Dutch but not Swedish, and `ui_locales=sv` alone shows English.

A value an admin console form won't take is refused by the auth server, in the console page's language, which is why both servers need your override catalogs.

An email to a user is written in their page language. On **Automatic**, it's the **Language and region** on their profile, or English when they haven't picked one. The activation link and the welcome email a user gets when they register are written in the language of the page they registered on, since their account has no language yet.

## Catalogs

The text of every page, message and email subject is in the built-in catalogs. A key with no text in the chosen language shows in English.

`GOIABADA_I18N_OVERRIDES_DIR` names a folder whose `catalogs` subfolder holds `active.<language>.toml` files. Nothing else in the folder is read: files put in the folder itself are ignored, and the server logs `override directory has no catalogs subdirectory, skipping it` when it starts. Each file is merged over the built-in catalog of its language, key by key, and the file wins. A value left empty removes the built-in text, so the key shows in English. Every value is a plain string: a `[table]` section stops the server at start.

The names of countries and phone country codes, and the country in each time zone's label, come from Unicode's CLDR data, in the page's language, and each language on the **Language and region** and **Page language** lists is named in itself and in English, so none of them needs translating.

The durations the admin console writes in words, under a duration field and in how long to wait before asking for another verification code, come from the browser's own CLDR data in the page's language, or in English where the browser has none, so they need no translating either.

## Email bodies

An email's subject is in the catalogs, and its body is a template under `emails/` in the auth server's templates. To translate a body, add a copy beside the English one named with the language, such as `emails/email_forgot_password.nl.html`, in your own [templates directory](#change-the-templates). A copy named for exactly the recipient's language wins. Otherwise the closest copy in their language does: `nl` serves a recipient reading `nl-BE`, and `pt-BR` serves one reading `pt`. A recipient with no copy in their language gets the English template.

## Templates and static files

A server reads a template each time it renders the page, so an edited template shows on the next request with no restart. Static files are served with `Cache-Control: public, max-age=300`. The four directory variables are on [Environment variables](/reference/environment-variables/#customization).
