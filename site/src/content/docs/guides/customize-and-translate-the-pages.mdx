This guide makes the pages your users see look and read like your product, in their language.

There are three levels, from a setting in the admin console to your own copy of the pages. Start with the first: most deployments need nothing more.

## Brand the pages

<Steps>

1. In the admin console, open **Admin**, **General** and set **App name**, up to 30 characters. It's shown at the top of the sign-in pages and ends their titles, as in "Sign in – Acme". It also signs every email, and it's the name authenticator apps list your users' accounts under.

2. Open **Admin**, **Branding**. A client's pages are drawn in the default brand, the one marked **Default**, until you give it one of its own. Open it, choose its **Appearance** and its **Theme**, add your logo, favicon, background image, font and corners if you like, and click **Save**. See [Brands and themes](#brands-and-themes) and [The brand kit](#the-brand-kit) for the choices, and a [custom palette](#custom-palettes) to use your own colors. Add [footer links and a support contact](#footer-links-and-support-contact) there too, to show them under the card, and [custom CSS](#custom-css) for anything the other choices don't cover. The emails your users get are drawn in the brand too: see [Branded emails](#branded-emails).

3. To give one client a look of its own, click **New brand** and create one, then choose it under **Brand** on the client's **Settings** tab. See [Clients](/concepts/clients/#brand) for the pages it draws.

4. Give each client a display name and a logo, so users see which app they're signing in to. See [Clients](/concepts/clients/#display-name-description-and-logo).

</Steps>

## Add a language

The pages come in English, Portuguese (Brazil), Spanish, French, Italian and German. To add another language, you translate one file of text and point both servers at it, with no rebuild.

<Steps>

1. Get the English text of the release you run: `src/core/i18n/catalogs/active.en.toml` in [the source](https://github.com/leodip/goiabada) at that release's tag, such as `v1.7.0`. The release is in the image tag and in the `build information` line each server logs when it starts.

2. Copy it into a folder named `catalogs`, as `active.<language>.toml`, named with the language's [BCP 47](https://www.rfc-editor.org/info/bcp47) tag: `active.nl.toml` for Dutch. Translate the text on the right of each `=` and leave the keys on the left as they are:

   ```toml title="catalogs/active.nl.toml"
   "auth.pwd.title" = "Aanmelden"
   "auth.pwd.email_label" = "E-mailadres"
   "auth.pwd.password_label" = "Wachtwoord"
   "auth.pwd.button" = "Aanmelden"
   ```

   Keep a placeholder such as `{{.appName}}` exactly as it is: the server writes the value there. A key you leave out, or leave empty, shows in English.

3. Make the folder that holds `catalogs` readable by both servers, and set `GOIABADA_I18N_OVERRIDES_DIR` to it on the auth server and on the admin console. In a container, mount it read-only, as the [templates are mounted](#change-the-templates) below.

4. Restart both servers. Each reads the catalogs once, at start, and refuses to start when one doesn't parse, naming the file.

5. Users choose it as their **Page language** under **Account**, **Profile** in the admin console, and your app can ask for it on the sign-in pages with `ui_locales`. See [how the language is chosen](#how-the-language-is-chosen).

</Steps>

## Change a few words

To reword a page in a language Goiabada already has, override only the keys you change, in the same folder:

```toml title="catalogs/active.en.toml"
"auth.pwd.title" = "Sign in to Acme"
```

Every key you don't name keeps the built-in text. Set `GOIABADA_I18N_OVERRIDES_DIR` and restart, as in [Add a language](#add-a-language).

## Change the templates

To change the layout of a page, or an email's body, you give a server its own copy of the templates. To restyle the pages, write a brand's [custom CSS](#custom-css) instead: it needs nothing redone when you upgrade. The templates and static files are compiled into each server's binary, and the images hold the binary alone, so there's no `web` folder inside a container to copy out.

<Steps>

1. Copy the web files from the source of the release you run, since a template from another release may use data the server no longer passes to it:

   ```bash
   RELEASE=v1.7.0   # replace with the release you run
   git clone --depth 1 --branch "$RELEASE" https://github.com/leodip/goiabada.git goiabada-source

   mkdir authserver-web adminconsole-web
   cp -r goiabada-source/src/authserver/web/{template,static,tailwindcss} authserver-web/
   cp -r goiabada-source/src/adminconsole/web/{template,static,tailwindcss} adminconsole-web/
   ```

   `tailwindcss` isn't served: it's what [regenerating the CSS](#regenerate-the-css) reads.

2. Edit the templates. They're Go [`html/template`](https://pkg.go.dev/html/template) files. Keep the element IDs and the scripts the pages use, or the forms stop working. In the layouts, keep the `data-theme` attribute, the brand's stylesheet link after `main.css`, its icon links, its logo and its footer after `main`, or the pages lose their brand's look. Keep each page's `data-page` template and the `data-page` attribute the layouts write on `<body>`, which CSS written to the [styling contract](/reference/styling-contract/) relies on. The servers' [`Content-Security-Policy`](/reference/security/#response-headers) makes the browser refuse an inline `<script>`, an `on…` attribute such as `onclick`, a `javascript:` URL, a `<style>` element, a `style` attribute and a `<base>` element. It also refuses a script, stylesheet, image or font from another site. A `<script type="application/json">` data block is fine. Put a script, stylesheet, image or font of your own in the `static` directory, and load it from there, a script with `<script src="{{ asset "/static/your-file.js" }}" defer></script>`. Anything your templates load needs its own consent: see [Personal data](/deploy/personal-data/#whats-yours-to-decide).

3. Make the files readable by the containers. Both images run as uid 10001 and gid 10001 (see [the user the images run as](/deploy/docker-compose/#the-user-the-images-run-as)), and a page whose template the server can't read fails with a 500:

   ```bash
   chmod -R a+rX authserver-web adminconsole-web
   ```

4. Mount each directory read-only and point its server at it, in `docker-compose.override.yml`, which a run of the setup wizard with `--keep-secrets` leaves as it is. Add the volumes and the variables to the two services already there, beside their secrets. They add to the volumes `docker-compose.yml` gives each service, and win over the empty values it lists:

   ```yaml
   goiabada-authserver:
     volumes:
       - ./authserver-web/template:/app/web/template:ro
       - ./authserver-web/static:/app/web/static:ro
     environment:
       - "GOIABADA_AUTHSERVER_STATICDIR=/app/web/static"
       - "GOIABADA_AUTHSERVER_TEMPLATEDIR=/app/web/template"

   goiabada-adminconsole:
     volumes:
       - ./adminconsole-web/template:/app/web/template:ro
       - ./adminconsole-web/static:/app/web/static:ro
     environment:
       - "GOIABADA_ADMINCONSOLE_STATICDIR=/app/web/static"
       - "GOIABADA_ADMINCONSOLE_TEMPLATEDIR=/app/web/template"
   ```

   Leave a server's pair empty if you haven't changed its files. Then run `docker compose up -d`. With the native binaries, set the same variables in the env file, naming directories the binaries' user can read.

5. Open every page you changed. A mistake in a template shows only when its page is rendered.

</Steps>

<Aside type="caution">
A directory replaces the built-in set **whole**, so it must hold every file of that set, not only the ones you change. When you upgrade Goiabada, copy the new release's files again and redo your changes on them.
</Aside>

## Regenerate the CSS

The pages are styled with [Tailwind CSS](https://tailwindcss.com/), and `main.css` holds only the classes the templates used when it was generated. A class you add to a template does nothing until you regenerate it.

The [styling contract](/reference/styling-contract/) lists the variables, page names and classes that stay the same from one release to the next. A rule written against them keeps matching after an upgrade.

The colors are tokens at the top of `tailwindcss/ui.css`: the light palette in its `@theme` block, and the dark one under `@variant dark` just below. They're the **Blueberry** theme, and every other theme draws its own colors over them. To draw the pages in your own colors, give a brand a [custom palette](#custom-palettes) rather than changing them here: it's checked for contrast, and it needs nothing redone when you upgrade.

<Steps>

1. Download the standalone Tailwind CLI for your platform from [Tailwind's releases](https://github.com/tailwindlabs/tailwindcss/releases), at the version the release you copied pins: `tools.tailwind` in `goiabada-source/src/authserver/versions.yaml`. Rename it to `tailwindcss` and make it executable.

2. Run it in each web directory whose templates or `ui.css` you changed. Add `--minify` for a smaller file:

   ```bash
   cd authserver-web
   tailwindcss -i ./tailwindcss/input.css -o ./static/main.css
   ```

   `input.css` looks for class names in `../template` and in the JavaScript in `../static`, so keep the three folders side by side.

3. The new `main.css` is in the static directory you mounted, so the server serves it at once. The pages link it by a fingerprint of its contents, so browsers fetch the new one on their next page load.

</Steps>

## Brands and themes

A brand is a look the pages are drawn in: a name, an appearance, a theme and [its kit](#the-brand-kit). A client's pages are drawn in the [brand chosen for it](/concepts/clients/#brand). The pages of a client with none, and the pages that belong to no client, are drawn in the default brand. A new install has one brand, **Default**, on **Automatic** and **Blueberry**.

The appearance is **Automatic**, **Light** or **Dark**. Automatic draws the pages light or dark, as each visitor's device prefers.

The theme is one of eight built-in themes: **Blueberry**, **Blackberry**, **Avocado**, **Plum**, **Tangerine**, **Guava**, **Coconut** and **High contrast**. Each has a light and a dark palette whose text and borders meet WCAG 2.2 AA contrast. High contrast's text meets 7:1. Or choose **Custom**, after them, to draw the brand in a [custom palette](#custom-palettes) of your own colors.

**New brand** adds a brand. Choose it for a client, or open it and click **Make default** to switch to it, in one step, every client with no brand of its own and every page that belongs to no client. The **Clients** column says how many clients use each brand.

Deleting a brand moves the clients that use it to the default brand. The default brand can't be deleted, so make another one the default first.

The Admin API manages the same brands, from [`GET /api/v1/admin/brands`](/reference/api/admin/operations/getbrands/), and [`GET /api/v1/admin/brand-themes`](/reference/api/admin/operations/getbrandthemes/) lists each built-in theme's colors. Every brand it answers carries `colors`, the colors the brand is drawn in, and `contrastWarnings`, its [failing pairs](#contrast-warnings). See [Custom palettes through the Admin API](#custom-palettes-through-the-admin-api) to write a palette.

### Custom palettes

A custom palette draws a brand's pages in colors you choose, light and dark.

<Steps>

1. Open the brand and choose **Custom** under **Theme**. The **Colors** section opens under the theme cards, holding the colors of the theme you had chosen, to start from.

2. Choose **Basic** or **Advanced**. In **Basic**, you set four colors for each mode: **Background**, **Card**, **Text** and **Brand color**. In **Advanced**, you set all 23.

3. Type each color as `#` and six hexadecimal digits, such as `#2456c4`, or pick it in the color well beside its field. The preview draws it as you type.

4. Read the list at the foot of the **Colors** section, and fix the pairs you can. See [Contrast warnings](#contrast-warnings).

5. Click **Save**.

</Steps>

Each color has a **Light** field and a **Dark** field, side by side. Under the **Automatic** appearance both are drawn. Under **Light**, only the light colors are, so the Dark column is hidden and its colors are kept, unused. **Dark** does the reverse. Every field still needs a color for the brand to save, so a hidden column shows again while one of its fields holds something else.

In **Basic**, Goiabada works out the other 19 colors from your four when you save, and stores them with the brand. It moves the colors it picks for text, borders and the focus ring until their contrast passes, where it can, and never changes your four. The status colors, for danger, positive, caution and note messages, are Blueberry's: its light ones for a mode whose text is darker than its card, and its dark ones otherwise. So a warning in Basic is nearly always about a color you entered or a status color, which you can set in Advanced.

Switching to **Advanced** fills the other 19 fields with the worked-out colors, ready to adjust. Switching back to **Basic** keeps your four, and the other 19, the status colors included, are worked out again when you save.

**Copy colors from** puts a built-in theme's colors in every field, light and dark. Choosing a built-in theme hides the **Colors** section and keeps what you typed until you save. Saving a brand on a built-in theme deletes its custom palette.

The preview beside the form has two views: **Sign-in**, and **Messages**, which draws notices, a hovered row, a selected item, a focused field and buttons. Between them they show all 23 colors.

**Advanced** shows the colors in four groups, **Page**, **Text**, **Brand** and **Status**, with each one's token name, which the Admin API uses:

| Color | Token |
|---|---|
| **Background** | `canvas` |
| **Card** | `surface` |
| **Subtle background** | `subtle` |
| **Border** | `line` |
| **Strong border** | `line-strong` |
| **Text** | `ink` |
| **Muted text** | `ink-muted` |
| **Brand color** | `brand` |
| **Strong brand color** | `brand-strong` |
| **Text on brand color** | `on-brand` |
| **Soft brand background** | `brand-soft` |
| **Focus ring** | `focus` |
| **Danger color** | `danger` |
| **Strong danger color** | `danger-strong` |
| **Text on danger color** | `on-danger` |
| **Soft danger background** | `danger-soft` |
| **Danger text** | `danger-ink` |
| **Soft positive background** | `positive-soft` |
| **Positive text** | `positive-ink` |
| **Soft caution background** | `caution-soft` |
| **Caution text** | `caution-ink` |
| **Soft note background** | `note-soft` |
| **Note text** | `note-ink` |

### Contrast warnings

Goiabada checks a brand's colors against the pairs its pages draw text, boundaries and focus rings in: 35 pairs in each mode, such as muted text on the card or the focus ring on the background. Each pair has a minimum contrast ratio from WCAG 2.2 level AA:

- 4.5:1 for text, from [1.4.3 Contrast (Minimum)](https://www.w3.org/TR/WCAG22/#contrast-minimum).
- 3:1 for a boundary or a focus ring, from [1.4.11 Non-text Contrast](https://www.w3.org/TR/WCAG22/#non-text-contrast).

Every built-in theme meets them. A pair below its minimum never stops a save. The editor lists each one at the foot of the **Colors** section, with its ratio, while you edit and again after you save, and the brand list marks a brand that has any. Text drawn in a failing pair doesn't meet WCAG 2.2 level AA contrast, and some of your users will find it hard to read.

Only the modes the brand's appearance draws are checked: both under **Automatic**, the light colors alone under **Light**, and the dark ones alone under **Dark**.

Passing every pair doesn't make your pages meet WCAG 2.2 AA. That's a claim about whole pages, against every one of its criteria, and your logo and background image aren't checked.

<Aside type="caution">
The admin console and its sign-in page are drawn in [the admin console's client's](/concepts/clients/#the-admin-consoles-client) brand. If that brand's colors make text unreadable, the console's text is unreadable too, the brand editor included. Check the preview before you save it. To get back, send the `brand` that [`GET /api/v1/admin/brands/{id}`](/reference/api/admin/operations/getbrand/) answers to [`PUT /api/v1/admin/brands/{id}`](/reference/api/admin/operations/updatebrand/), with a built-in `theme` and `palette` set to `null`.
</Aside>

### Custom palettes through the Admin API

A custom palette is the theme `custom` with a `palette` member, in [`POST /api/v1/admin/brands`](/reference/api/admin/operations/createbrand/) and [`PUT /api/v1/admin/brands/{id}`](/reference/api/admin/operations/updatebrand/). An update replaces the whole brand, so a member you leave out, such as a [kit](#the-brand-kit) slot or a [footer](#footer-links-and-support-contact) member, is emptied. `palette` holds `mode`, `basic` or `advanced`, and `light` and `dark`, each a map from a color's [token](#custom-palettes) to its value:

```bash
curl -X PUT https://auth.example.com/api/v1/admin/brands/3 \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Acme",
    "appearance": "auto",
    "theme": "custom",
    "corners": "rounded",
    "font": "system-ui",
    "backgroundFit": "cover",
    "palette": {
      "mode": "basic",
      "light": {"canvas": "#f3f6f4", "surface": "#ffffff", "ink": "#17211b", "brand": "#1e7a4c"},
      "dark": {"canvas": "#0f1512", "surface": "#17201b", "ink": "#e4ece7", "brand": "#5cc58f"}
    }
  }'
```

- In basic mode, each of `light` and `dark` holds exactly `canvas`, `surface`, `ink` and `brand`. In advanced mode, each holds all 23 tokens.
- Send both modes, whatever the brand's appearance.
- A color is `#` and six hexadecimal digits, in either case, and is answered in lower case.
- `palette` is required with `custom`. With a built-in theme, leave it out or send `null`.
- `custom` is reserved: [`GET /api/v1/admin/brand-themes`](/reference/api/admin/operations/getbrandthemes/) lists the built-in themes alone.

A brand answers `palette` as it was written, and as `null` on a built-in theme, so a brand you read and send back is saved unchanged. A basic palette is worked out again from its four colors each time it's saved.

Every brand answer also carries two read-only members, which a write ignores:

- `colors` holds `light` and `dark`, each with all 23 colors the brand is drawn in: a custom palette's stored colors, or a built-in theme's own.
- `contrastWarnings` lists each [failing pair](#contrast-warnings) of the modes the appearance draws, light before dark, and is `[]` when none fails. An item holds `mode`, `foreground` and `background`, which are token names, `ratio` and `minimum`. The ratio is cut to two decimals and never rounded up, so a pair at 4.496:1 reads `4.49`.

A refusal about the palette carries `error_field`, a JSON Pointer to the member it's about, such as `/palette/light/brand`.

## The brand kit

A brand's kit puts your logo, favicon, background image, font and corners on its pages. Each is optional: a brand you haven't changed is drawn in Goiabada's own look.

The auth server's pages and the admin console's **Account** pages, home and its other card pages are drawn with the whole kit. The admin console's admin pages take only its colors and logo, as [the admin console's client](/concepts/clients/#the-admin-consoles-client) explains.

### Logo and app name

**Logo** is drawn above the app name on the sign-in card, and before the app name in the admin console's header and sidebar. **Dark logo** takes its place in dark mode. Without one, the logo is drawn in both modes. A dark logo needs a logo.

Turn on **Hide the app name** for a logo that already shows the name. The logo then stands for the name, and screen readers announce it as the app name. A brand without a logo always shows the name. Page titles keep the app name either way.

A client's own [logo](/concepts/clients/#display-name-description-and-logo) still shows on its screens, below the brand's.

### Favicon

**Favicon** is the icon in the browser's tab. A page whose brand has one links it in place of Goiabada's icons and web manifest.

### Background image

**Background image** is drawn behind the sign-in card, over the theme's background color. It's drawn on card pages only: the auth server's pages and the admin console's home and card pages, not its **Account** pages. Choose how it fills the page:

- **Cover** fills the page and may crop the image.
- **Contain** shows the whole image, with the theme's background color around it.
- **Tile** repeats the image at its own size.

The card stays opaque over the image, so its text is as readable as on a page without one.

### Font

**Font** is one of six system families: **System UI**, **Humanist**, **Geometric**, **Serif**, **Neo-grotesque** and **Rounded**. Each is a list of fonts your visitors' devices already have, so nothing is downloaded and text looks a little different from one device to another. Apple devices draw **Rounded** rounded. Windows and Android have no rounded font installed and draw it as an ordinary sans.

To use your own typeface, upload it under **Font file** and choose **Uploaded font**. One file is used for every weight, so a variable font works as it should, and a static one gets the browser's own bold. Add a **Bold font file** too, and the font file draws the weights up to 500 and the bold one the heavier ones. Text shows in System UI while the font loads, and for any character it lacks. Code and other monospace text keep their own font.

Choosing another family keeps the files, so you can switch back without uploading them again.

### Corners

**Corners** are **Square**, **Rounded** or **Pill**. Rounded is Goiabada's own look. Pill rounds a button or a single-line field fully, and rounds the card and boxes of several lines only as far as their content stays clear of the curve.

### What you can upload

| Field | Type | Size | Largest file |
|---|---|---|---|
| **Logo**, **Dark logo** | PNG or JPEG | 10 to 512 pixels a side | 1 MiB |
| **Favicon** | PNG, square | 48 to 512 pixels a side | 1 MiB |
| **Background image** | PNG, JPEG or WebP | 10 to 3840 pixels a side | 2 MiB |
| **Font file**, **Bold font file** | WOFF2 | | 2 MiB |

Animated images are refused, since a looping animation on or behind the sign-in card has no way to pause it. GIF and SVG are refused too.

**Upload** sends a file as soon as you pick it, and the preview draws it at once. Nothing reaches a real page until you click **Save**, and **Remove** empties the field. A file no brand uses is deleted once it's a day old, so save the brand the same day you upload it.

A brand's files are public, as the pages that draw them are: anyone can download them from `/brand-assets/{id}` on the auth server.

### The kit through the Admin API

The Admin API sets the kit in two steps. Each upload leaves an `uploaded_brand_asset` entry in the [audit log](/concepts/audit-log/).

An update replaces the whole brand. `corners`, `font` and `backgroundFit` are required, `hideAppName` is false when you leave it out, and a slot you leave out or set to `null` is emptied. A `brand` you read with [`GET /api/v1/admin/brands/{id}`](/reference/api/admin/operations/getbrand/) and send back as it came is saved unchanged.

<Steps>

1. Upload each file as a brand asset of its kind, in the multipart field `file`, with [`POST /api/v1/admin/brand-assets/logo`](/reference/api/admin/operations/uploadbrandlogo/), [`/favicon`](/reference/api/admin/operations/uploadbrandfavicon/), [`/background`](/reference/api/admin/operations/uploadbrandbackground/) or [`/font`](/reference/api/admin/operations/uploadbrandfont/). A dark logo is uploaded as a logo, and both font files as a font. The answer holds the asset's `id`:

   ```bash
   curl -X POST https://auth.example.com/api/v1/admin/brand-assets/logo \
     -H "Authorization: Bearer $TOKEN" \
     -F "file=@logo.png"
   ```

2. Name the asset by its `id` in a slot of the brand, with [`POST /api/v1/admin/brands`](/reference/api/admin/operations/createbrand/) or [`PUT /api/v1/admin/brands/{id}`](/reference/api/admin/operations/updatebrand/). The slots are `logo`, `darkLogo`, `favicon`, `background`, `regularFont` and `boldFont`:

   ```bash
   curl -X PUT https://auth.example.com/api/v1/admin/brands/3 \
     -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" \
     -d '{
       "name": "Acme",
       "appearance": "auto",
       "theme": "blueberry",
       "corners": "rounded",
       "font": "uploaded",
       "backgroundFit": "cover",
       "hideAppName": true,
       "logo": {"id": 42},
       "regularFont": {"id": 43}
     }'
   ```

</Steps>

## Footer links and support contact

A brand can show up to three links under the card, such as your privacy policy, a status page or your company's site, and a way for a stuck user to reach your support. Both are optional.

<Steps>

1. Open **Admin**, **Branding**, and open the brand.

2. Under **Footer links**, give **Link 1** a **Label** and a **URL**, and fill in **Link 2** and **Link 3** if you want more. A row left empty is no link.

3. Open **Label in each language** under a link to give it a label in each language your users read.

4. Under **Support contact**, fill in any of **Email address**, **Support page URL** and **Phone number**.

5. Click **Save**.

</Steps>

The preview beside the form draws the footer as you type.

The footer is drawn under the card on every page of the auth server, and on the admin console's home and its other card pages. On the console's **Account** pages it follows the page's content. The console's admin pages draw no footer. It's small text on the page's background color, and on a brand with a [background image](#background-image) it sits on a panel in the card's color, so it stays readable whatever the image.

A brand shows only its own links and contact. A client whose brand has none shows no footer, even when the default brand's has one.

Everything in the footer is public, as the pages that draw it are.

### Footer links

The links are drawn in the order of their rows, and each one opens in a new tab, so a click during a sign-in leaves the sign-in page open.

- **Label** is required, up to 40 characters, without `<` or `>`.
- **URL** is required, up to 256 characters. It starts with `https:` and names a site, with no user name or password in it.
- **Label in each language** holds one optional label for each built-in language, with the same limits as **Label**.

A page shows each link's label in the language the page is written in. Where the link has none for that language, a language you [added](#add-a-language) included, it shows **Label**. Goiabada can't tell a screen reader which language that label is in, so fill in a label for each language your users read.

### Support contact

The footer's contact line reads "Need help?", followed by each value you set: the email address and the phone number as themselves, so they can be copied, and the URL as a link named "Support page", which opens in a new tab.

- **Email address** is up to 254 characters, in the shape any account's address takes.
- **Support page URL** follows the rule of a footer link's **URL**.
- **Phone number** is a `+`, the country code and the number, up to 15 digits in all, the first not 0. You can type it with spaces, hyphens, dots and parentheses, and they're removed when you save, so the page shows the digits alone, such as `+442079460958`.

### The footer through the Admin API

A brand carries the footer in four members, in [`POST /api/v1/admin/brands`](/reference/api/admin/operations/createbrand/), [`PUT /api/v1/admin/brands/{id}`](/reference/api/admin/operations/updatebrand/) and every brand they answer: `footerLinks`, the links in the order they're drawn, and `supportEmail`, `supportUrl` and `supportPhone`. As with the kit, an update replaces the whole brand, so a member you leave out or set to `null` is emptied. A link is an object with `url`, `label` and, optionally, `labels`, a label for each language by its tag, such as `"pt-BR"`:

```bash
curl -X PUT https://auth.example.com/api/v1/admin/brands/3 \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Acme",
    "appearance": "auto",
    "theme": "blueberry",
    "corners": "rounded",
    "font": "system-ui",
    "backgroundFit": "cover",
    "footerLinks": [
      {"url": "https://acme.example/privacy", "label": "Privacy", "labels": {"pt-BR": "Privacidade", "de": "Datenschutz"}},
      {"url": "https://status.acme.example", "label": "Status"}
    ],
    "supportEmail": "help@acme.example",
    "supportUrl": "https://acme.example/help",
    "supportPhone": "+44 20 7946 0958"
  }'
```

An answer always carries all four: `[]` for no links, `""` for a value not set, and `{}` as the `labels` of a link with none. A blank language label is dropped.

A refusal about a footer link carries `error_field`, a JSON Pointer to the member it's about, such as `/footerLinks/1/url` for the second link's URL. The pointer's index is counted from 0, while the message counts links from 1.

## Custom CSS

A brand's custom CSS restyles its pages beyond what its other choices do, such as a page's layout, a heading's size or a card's border.

<Steps>

1. Open **Admin**, **Branding**, and open the brand.

2. Under **Custom CSS**, write your rules. Write them against the [styling contract](/reference/styling-contract/): its variables, page names and classes stay the same from one release to the next, so your rules keep matching after an upgrade.

3. Click **Save**.

4. Open a page in the brand to see your rules. The preview beside the form doesn't draw custom CSS, so try new rules on a brand you've given to a test client, and sign in to that client. If a page becomes unusable, [safe mode](#safe-mode) draws it without your CSS.

</Steps>

```css
body[data-page="sign-in"] .auth-card {
  border: 2px solid var(--color-brand);
}
```

The CSS goes after the brand's own styles, so a rule of yours wins over a built-in one of the same [specificity](https://developer.mozilla.org/en-US/docs/Web/CSS/Specificity). It's on every page of the auth server, and on the admin console's Account pages, its home page, and its error and sign-out pages. It's never on the console's admin pages.

### What custom CSS can hold

Custom CSS can't make a browser load anything, so it can't send a visitor's data anywhere:

- It's up to 64 KB.
- It can't hold `@import`.
- It can't hold a URL, except a `data:` image in `url()`, such as `url("data:image/svg+xml,…")`. A URL to another site or to the auth server itself is refused. Upload a background, a logo or a font in the brand's [kit](#the-brand-kit) instead.
- It can't use `src()`, `image()` or `image-set()`, with or without a vendor prefix such as `-webkit-`. Write a `data:` image in `url()` instead.
- Every comment, string and `url()` must be closed.

The rules apply however you write a name: in capitals, or with a CSS escape such as `\69mport`.

### Custom CSS through the Admin API

A brand carries its custom CSS as one string, `customCss`, in [`POST /api/v1/admin/brands`](/reference/api/admin/operations/createbrand/), [`PUT /api/v1/admin/brands/{id}`](/reference/api/admin/operations/updatebrand/) and every brand they answer. As with the kit, an update replaces the whole brand, so leaving `customCss` out, or setting it to `null` or `""`, removes the brand's CSS:

```bash
curl -X PUT https://auth.example.com/api/v1/admin/brands/3 \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Acme",
    "appearance": "auto",
    "theme": "blueberry",
    "corners": "rounded",
    "font": "system-ui",
    "backgroundFit": "cover",
    "customCss": "body[data-page=\"sign-in\"] .auth-card {\n  border: 2px solid var(--color-brand);\n}\n"
  }'
```

An answer always carries `customCss` as it was saved, each line ending a line feed, or `""` for a brand with none. A refusal of the CSS carries `error_field` set to `/customCss`.

## Branded emails

Every email the auth server sends is drawn in a brand, the brand of the page it was sent from, so a password reset looks like the sign-in it came from.

### What an email takes from its brand

An email is a card on the brand's background color, with the brand's **Logo** above the app name, as on the [sign-in card](#logo-and-app-name). **Hide the app name** hides the name there too, and the logo then carries the app name as its alternative text, which a mail client that blocks images shows in its place. The card takes the brand's colors, its **Corners** and its **Font**. An **Uploaded font** is drawn in **System UI**, since an email can't load a font file.

The password reset, the activation link, a new user's setup email and the welcome email each have a button in the brand's color above their link, and every other link is in the brand's color too. The brand's [footer links and support contact](#footer-links-and-support-contact) are drawn under the card. The background image, the favicon and the custom CSS never reach an email.

An email doesn't follow the reader's light or dark mode, since many mail clients ignore it. A brand whose **Appearance** is **Dark** is drawn in its dark colors, with its **Dark logo** if it has one. **Light** and **Automatic** brands are drawn in their light colors.

Some mail clients, Outlook among them, redraw a light email in dark colors when the reader uses dark mode. They leave the logo as it is, so a logo in dark ink on a transparent background can be hard to read there. Give it a background of its own, or a light outline, and it reads in both.

Every email is sent as plain text too, for mail clients that show no HTML: its text, its links written out, and the footer.

### Which brand an email takes

An email takes the brand of the page it was sent from:

| Sent from | Drawn in | Emails |
|---|---|---|
| The pages of a sign-in to your app | The client's brand | When someone registers, the activation link, the welcome email and the notice that the address already has an account. The password reset link, and the notice that the password was reset. The notices that two-factor authentication was set up, that a recovery code was used, and that the authenticator was disabled after too many wrong codes. |
| The **Account** pages, or the Account API | The brand of the client the access token was issued to, which for the admin console's **Account** pages is the admin console's own client's brand | The verification code. The notices that the email address or the password was changed, that two-factor authentication was set up or turned off, that the recovery codes were replaced, that the account was deleted, and that the authenticator was disabled after too many wrong codes while confirming a deletion. |
| An administrator's action | The default brand | A new user's setup email. The notices that an administrator changed the password, turned off two-factor authentication or deleted the account. The test email from **Send test email**. |

A client with no brand of its own gives the default brand, as its pages do: see [Clients](/concepts/clients/#brand). So does the forgot password page opened on its own, outside a sign-in.

## Safe mode

Safe mode draws the pages without what can make a brand unusable: its custom CSS, a custom palette and an uploaded font. Use it to sign in and fix a brand whose pages you can't read or use.

<Steps>

1. Open an admin console address with `?goiabada_safe_mode=true` at the end, such as `https://admin.example.com/admin/settings/branding?goiabada_safe_mode=true`.

2. Sign in if you're asked to. The admin console's pages are now in safe mode, and its admin pages say so.

3. Fix the brand under **Admin**, **Branding**.

4. Sign out to leave safe mode, and check the pages.

</Steps>

A page in safe mode shows the built-in Blueberry colors in place of a custom palette, and System UI in place of an uploaded font. A built-in theme's colors, the corners, a system font family, the background image, the logo, the favicon and the footer stay. Nothing saved changes, so the brand editor still shows and saves the CSS, the palette and the font.

You can also turn it on:

- **For one sign-in to your app**, with `goiabada_safe_mode=true` on the [authorization request](/reference/endpoints/authorize/#parameters). Every page of that sign-in is drawn in safe mode.
- **For every page of both servers**, for everyone, with [`GOIABADA_AUTHSERVER_BRAND_SAFE_MODE`](/reference/environment-variables/#customization) set to `true` on the auth server. It lasts until you unset it and restart the auth server, and signing out doesn't end it.

An email follows safe mode too: one sent from the pages of a sign-in in safe mode, and every email while `GOIABADA_AUTHSERVER_BRAND_SAFE_MODE` is on, shows the Blueberry colors in place of its [brand's](#branded-emails) custom palette. The admin console's safe mode doesn't change the emails its **Account** pages send.

## How the language is chosen

On the auth server's pages and in the admin console, the language is the first of these that names one:

1. The user's **Page language**, which they choose under **Account**, **Profile** in the admin console. An administrator can set it too, on the user's **Profile** page.
2. A `ui_locales` parameter: one or more language tags in order of preference, separated by single spaces, such as `ui_locales=es pt-BR`. On the auth server, it's the authorization request's or the [sign-out](/reference/endpoints/logout/)'s. It's kept for the rest of that sign-in, and applies to the error page the auth server shows when it refuses the request outright. In the admin console, it's `?ui_locales=` in the page's address.
3. The browser's `Accept-Language` header.
4. English.

A user on **Automatic**, where everyone starts, skips the first. So does a page drawn for nobody Goiabada knows yet, which is why your app's `ui_locales` still matters:

- The admin console uses the page language once the user has signed in to it.
- The auth server uses it once the user has entered their password: on the one-time code, recovery code and consent pages, on signing out, and on every page shown to a browser that's signed in.
- A browser that isn't signed in gets the sign-in, forgot password, registration and activation pages in the language of the other sources, since the auth server doesn't know who's there. The email address typed on the sign-in page never picks the language, so the page can't reveal an account's language to whoever types it.
- The password reset page, opened from the email, is in the page language of the user the link is for.

The auth server reads the page language each time it draws a page, so a change shows on its next page. The admin console reads it when the user signs in to it. A change they save there shows on their next page, and one made elsewhere, such as by an administrator, reaches them when they next sign in or open their profile.

The **Page language** list holds the languages Goiabada has text for, yours included. A user whose language you later remove is back on **Automatic**.

For `ui_locales` and `Accept-Language`, the first of their languages Goiabada has text for wins, or English when it has none of them: `ui_locales=sv nl` shows Dutch when you've added Dutch but not Swedish, and `ui_locales=sv` alone shows English.

A value an admin console form won't take is refused by the auth server, in the console page's language, which is why both servers need your override catalogs.

An email to a user is written in their page language. On **Automatic**, it's the **Language and region** on their profile, or English when they haven't picked one. The activation link and the welcome email a user gets when they register are written in the language of the page they registered on, since their account has no language yet.

## Catalogs

The text of every page, message and email subject is in the built-in catalogs. A key with no text in the chosen language shows in English.

`GOIABADA_I18N_OVERRIDES_DIR` names a folder whose `catalogs` subfolder holds `active.<language>.toml` files. Nothing else in the folder is read: files put in the folder itself are ignored, and the server logs `override directory has no catalogs subdirectory, skipping it` when it starts. Each file is merged over the built-in catalog of its language, key by key, and the file wins. A value left empty removes the built-in text, so the key shows in English. Every value is a plain string: a `[table]` section stops the server at start.

The names of countries and phone country codes, and the country in each time zone's label, come from Unicode's CLDR data, in the page's language, and each language on the **Language and region** and **Page language** lists is named in itself and in English, so none of them needs translating.

The durations the admin console writes in words, under a duration field and in how long to wait before asking for another verification code, come from the browser's own CLDR data in the page's language, or in English where the browser has none, so they need no translating either.

## Email bodies

An email's subject is in the catalogs, and its body is a template under `emails/` in the auth server's templates. To translate a body, add a copy beside the English one named with the language, such as `emails/email_password_changed.nl.html`, in your own [templates directory](#change-the-templates). A copy named for exactly the recipient's language wins. Otherwise the closest copy in their language does: `nl` serves a recipient reading `nl-BE`, and `pt-BR` serves one reading `pt`. A recipient with no copy in their language gets the English template.

The password reset link, the activation link, the welcome email, the notice that an address already has an account, a new user's setup email, the verification code and the test email have no template and no catalog messages: their subjects, button labels and bodies are built into the auth server in the six built-in languages, and a recipient reading any other language gets them in English.

The test email from the **Send test email** tab under **Admin**, **Email** is in the language the administrator reads the admin console in, and goes out in the default brand.

## Templates and static files

A server reads a template each time it renders the page, so an edited template shows on the next request with no restart. The pages link a static file with a fingerprint of its contents in the URL, which changes when the file does, so an edited file shows on the next page too. Requested by that URL, a static file of up to 1 MiB is served with `Cache-Control: public, max-age=31536000, immutable`; a larger one, or one requested by any other URL, such as a favicon's, with `public, max-age=300`. The four directory variables are on [Environment variables](/reference/environment-variables/#customization).
