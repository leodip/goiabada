When a client sends an authorization request to `/auth/authorize`, Goiabada runs a series of checks before issuing a response. This page describes every check, the order they happen in, and how parameters like `prompt`, `max_age`, and `acr_values` interact.

## Overview

Every authorization request passes through these stages:

```
/auth/authorize
  │
  ├─ 1. Validate request (client, redirect_uri, scopes, PKCE, prompt, ...)
  │     └─ on failure: answer the client, or log in first and answer afterwards
  │
  ├─ 2. Route based on prompt and session state
  │     ├─ prompt=none  ──► Silent checks ──► Issue response or error
  │     ├─ prompt=login ──► Force login ──► /auth/pwd
  │     └─ Normal flow  ──► SSO or login
  │
  ├─ 3. Authenticate (password, optionally OTP)
  │
  ├─ 4. Post-auth checks (scope filtering, session mgmt, consent)
  │
  └─ 5. Issue authorization code ──► Redirect to client
```

<Aside>
This page focuses on the authorization code flow (`response_type=code`), which is the recommended flow. The [implicit flow](/legacy-flows/implicit/) is supported for legacy clients. When used, tokens are delivered directly in the URI fragment instead of an authorization code.
</Aside>

## Stage 1: Request validation

The checks run first, before the user sees anything. Which they are, the order they run in and the answer to each are on [Authorize](/reference/endpoints/authorize/#what-the-auth-server-checks). Goiabada never redirects to a `redirect_uri` that isn't registered on the client, and an error reaches the client only once the user has signed in, unless the request is silent or the browser already has a session: see [When an error reaches your app](/reference/endpoints/authorize/#when-an-error-reaches-your-app).

Scope *validation* (does it exist?) happens here; scope *authorization* (is this user allowed?) happens later in [post-authentication checks](#stage-4-post-authentication-checks).

## Stage 2: Routing

After validation, Goiabada chooses a path based on the `prompt` parameter and session state. The three branches are mutually exclusive.

### Branch A: prompt=none (silent authentication)

Goiabada attempts to fulfill the request without any user interaction. The checks it runs, in order, and the error each one answers are on [prompt](/concepts/prompt/#the-silent-checks).

If all checks pass, the response is issued silently (an authorization code for code flow, or tokens directly for implicit flow) and the user is redirected to the client. The session's `last_accessed` timestamp is updated to prevent idle timeout.

If any check fails, the error is redirected to the client and no UI is shown. Two things stop that: a client that [registered itself](/concepts/clients/#self-registered-clients) never receives an error redirect, and neither does one whose `redirect_uri` is no longer registered on it. The redirect is withheld, so the silent request gets no error back and simply never returns. See [Prompt parameter](/concepts/prompt/) for what a client should do about that.

### Branch B: prompt=login (force re-authentication)

Goiabada never uses an existing session to skip authentication here, so the user must enter their credentials again.

After authentication, the flow continues normally through post-authentication checks (including consent, if `prompt=login consent` was requested).

If the same user signs in, the session that was already in the browser is reused, as long as it is still valid; one that has idled out, reached its maximum lifetime, or fallen outside a requested `max_age` is simply replaced, with nothing revoked. If a **different** user signs in, that session is ended and replaced: it is deleted, and the refresh tokens and unredeemed authorization codes that came from it are revoked. See [Prompt parameter](/concepts/prompt/).

<Aside>
When the same user re-authenticates and their session is still valid, it is not invalidated. Other clients using it continue to work, and only this authorization request requires fresh credentials. A session that is no longer valid for this request is replaced by a new one instead, so that assurance does not apply to it.
</Aside>

### Branch C: Normal flow (no prompt, or prompt=consent only)

Goiabada checks for an existing session:

- **Valid session found**: the user is not prompted for credentials (SSO). The flow skips to the level 1 completion check, which decides if a level 2 step-up is needed.
- **No valid session, or session expired**: the user is directed to the login page.
- **Valid session but user account is disabled**: `access_denied` error redirected to client.

## Stage 3: Authentication

This stage only applies to Branch B and Branch C (not `prompt=none`, which has no UI).

### Level 1: Password

The user enters their email and password. If credentials are valid, the flow moves to the level 1 completion check.

### Level 1 completion: deciding if level 2 is needed

Goiabada compares the request's ACR level with the level the user's own session reached, and asks for a one-time code when the session falls short, or when the user's two-factor authentication changed since the session last went through the code step. Which level a request asks for, and what each level asks of a user with and without two-factor authentication, are on [ACR and AMR](/concepts/acr-and-amr/#which-level-a-request-asks-for).

### Level 2: OTP

An enrolment is stored only while the account's two-factor settings are still the ones the sign-in read. If they change while the user is enrolling, for example because the same account finished enrolling an authenticator in another tab or from its account page, the new secret is not stored and the sign-in ends on a page saying the account's two-factor settings changed during the sign-in. That sign-in cannot be continued: the user goes back to the application and signs in again, which starts from the account's current settings.

## Stage 4: Post-authentication checks

After authentication completes (or is skipped via SSO), the following checks run:

### 4.1 Session management

- **Existing valid session**: the session is "bumped" (`last_accessed` is updated, and the ACR level is upgraded if the new level is higher). ACR levels never downgrade within a session.
- **No valid session**: a new session is created, and old sessions from the same device are cleaned up.

### 4.2 User status

The user's account is checked again (it may have been disabled between login and this point). If disabled: `access_denied` error redirected to client.

### 4.3 Scope filtering

Goiabada filters the requested scopes based on the user's permissions:
- Standard OIDC scopes (`openid`, `profile`, `email`, `address`, `phone`, `groups`, `attributes`) are always kept.
- Custom scopes (`resource:permission`) are only kept if the user has the corresponding permission (directly or through a group).
- If no scopes remain after filtering: `access_denied` error redirected to client.

The filtered set ("effective scopes") is what appears in the resulting tokens. Consent is also evaluated against effective scopes, not the originally requested scopes.

### 4.4 Consent evaluation

Consent is checked if the client has consent enabled, `offline_access` is in the effective scopes, or `prompt=consent` was requested.

| Condition | Result |
|-----------|--------|
| `prompt=consent` is set | Always show the consent screen, even if all scopes were previously consented |
| Client requires consent and user has not consented to all effective scopes | Show consent screen |
| `offline_access` is requested | Show consent screen (to re-confirm refresh token grant) |
| Client does not require consent, no `offline_access`, no `prompt=consent` | Skip consent, proceed to code issuance |
| All effective scopes already consented, no `offline_access`, no `prompt=consent` | Skip consent, proceed to code issuance |

#### Declining

Choosing **Cancel** on the consent screen ends the authorization. What the user sees next depends on who registered the client:

| Client | What happens |
|--------|--------------|
| Created by an administrator | The browser is redirected to the client's redirect URI with `error=access_denied`, and the client shows its own message. If that URI has since been removed from the client, the page below is shown instead |
| [Self-registered](/concepts/clients/#self-registered-clients) | The browser stays on Goiabada. A page names the application and the address it asked to send the user to, and the request stops there |

The redirect is withheld because anyone can register a client and choose where it points: a user who has just refused an application they did not recognise should not then be delivered to it. The same page is shown whenever Goiabada refuses a self-registered client's authorization for any reason, `prompt=none` included, and the client receives nothing. See [dynamic client registration](/concepts/clients/#self-registered-clients) for the full rule and what it means if you build one.

## Stage 5: Code issuance

The ceremony may have waited on the consent screen, so before anything is issued it is checked again, for implicit requests too. It stops if:

- the client was disabled (an error page) or the flow was switched off for it (`unauthorized_client`);
- the user was disabled (`access_denied`);
- the user's credentials changed since they signed in (the sign-in starts again, or `login_required` for `prompt=none`).

The authorization code is generated and delivered to the client using the response mode:

| Response mode | Delivery |
|---------------|----------|
| `query` (default) | `redirect_uri?code=...&state=...` |
| `fragment` | `redirect_uri#code=...&state=...` |
| `form_post` | HTML auto-submitting form with `code` and `state` fields |

The code is then exchanged for tokens at the token endpoint.

The `auth_time` claim in the resulting ID token is the moment the user's last credential was verified, not the moment the code was issued. A session reused without re-authentication, including `prompt=none`, keeps the session's time.

## How parameters interact

### max_age vs prompt=login

Both can force re-authentication, but they work differently:

| Parameter | When user must re-authenticate |
|-----------|-------------------------------|
| `max_age=N` | Only if the user last signed in more than N seconds ago |
| `prompt=login` | Always, regardless of session age |
| Both present | `prompt=login` takes precedence (the session is never used to skip authentication) |

### max_age vs session idle timeout vs max lifetime

All three are time-based session checks, but they measure different things:

| Check | Measured from | Configured by |
|-------|---------------|---------------|
| Idle timeout | `last_accessed` (resets on activity) | Global setting: idle timeout in seconds |
| Max lifetime | `started` (never resets) | Global setting: max lifetime in seconds |
| `max_age` | `auth_time` (resets on each sign-in) | Per-request parameter |

A session is valid only if **all three** pass. The `max_age` parameter bounds the time since the user last signed in, not the session's age. See [User sessions](/concepts/sessions/) for details.

### acr_values vs client default ACR

See [ACR and AMR](/concepts/acr-and-amr/#which-level-a-request-asks-for).

## Quick reference

| Question | Determined by |
|----------|---------------|
| Does the user need to log in? | Session validity (idle timeout, max lifetime, `max_age`), `prompt=login` |
| Does the user need OTP? | Target ACR level (`acr_values`, client default), user's OTP enrollment status, OTP configuration changes |
| Does the user see a consent screen? | Client's consent setting, `offline_access` scope, `prompt=consent`, existing consent coverage |
| Can the request succeed silently? | `prompt=none` (all of the above must pass without interaction) |
| What scopes end up in the token? | Requested scopes filtered by user's permissions, then by user consent if applicable |
