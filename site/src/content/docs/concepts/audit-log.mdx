Goiabada records security-sensitive events as audit events. These include logins, token issuance, permission changes, and account modifications. They can be written to the console, persisted to the database, or both.

## Logging targets

Audit logging has two independent targets that can be enabled together or separately:

| Target | Default | Description |
|--------|---------|-------------|
| Console | Enabled | One log record per event, carrying the event name, its details as fields, and, for an event raised while serving a request, that request's id, picked up by your container or host log pipeline. |
| Database | Enabled | Events are persisted to the `audit_logs` table and can be browsed in the admin console. |

Disabling both effectively turns off audit logging.

That request id is whatever the client or proxy sent in `X-Request-Id`, or one Goiabada generated when none was sent, so it ties an event to a log line and is not proof of who sent the request.

<Aside type="caution">
Database persistence is only useful if you can guarantee the database stays available. For deployments where the database is the resource being audited, also enable console logging so events still reach an external log collector.
</Aside>

## Retention

When database persistence is enabled, a background worker periodically deletes audit logs older than the configured retention period.

| Setting | Default | Notes |
|---------|---------|-------|
| Retention (days) | 180 | Maximum 3650 (10 years). Use `0` for **infinite retention**, in which case no automatic cleanup happens. |

The worker runs every 12 hours and deletes in batches of 1000 (up to 100,000 per run). On a high volume deployment, expect cleanup to amortize over multiple runs after the retention threshold is first reached.

## Admin console

Two pages are available in the admin console under **Settings**:

- **Audit log settings**: toggle the console and database targets, and configure retention. Changing them needs `authserver:manage`: a token holding only `authserver:manage-settings` reads them but is refused a change, since switching a target off or shortening retention would hide what the other refusals record.
- **Audit log viewer**: browse persisted events with event type and request id filtering, and pagination. Each entry shows the event name, timestamp, request id, and a JSON details payload.

The viewer reads through the auth server's admin API, which serves the rows from the `audit_logs` table, so it only shows events captured while database persistence was enabled. The event type filter is filled from the auth server's catalog of event names, so it offers every event this server can write, including ones that have not occurred on this deployment yet.

## REST API

The same configuration and viewer are available via the admin REST API:

- `GET/PUT /api/v1/admin/settings/audit-logs`: read or update logging targets and retention.
- `GET /api/v1/admin/audit-logs`: paginated viewer endpoint with optional `auditEvent` and `requestId` filters.
- `GET /api/v1/admin/audit-logs/event-types`: the catalog of event identifiers the `auditEvent` filter accepts.

See [REST API › Audit log settings](/reference/rest-api/#audit-log-settings) for full details.

## Events to alert on

These events record who can administer Goiabada and who tried to reach past that, and they are the ones worth an alert rule or a saved filter in the viewer. Each is one event type, so a single filter on it sees every occurrence. See [administrators](/concepts/resources-and-permissions/#administrators) for the rule they are about, and [administrative scopes](/concepts/clients/#administrative-scopes) for which clients may request those scopes on a user's behalf.

| Event | Written when | Details |
|-------|--------------|---------|
| `administrator_change_refused` | An admin API request reached for something only `authserver:manage` may do, creating an administrator, changing one or changing what reaches one, and was refused `403 MANAGE_SCOPE_REQUIRED`. One entry per refused request, so an integration retrying leaves one per attempt. A route refusing a token without any of its scopes (`INSUFFICIENT_SCOPE`) writes none. | `loggedInUser` (the token's subject), `method`, `route` (the route pattern, such as `/api/v1/admin/users/{id}/permissions`), `ceiling` (`grant` for granting or revoking an administrative permission, directly or through a group, `target` for any other write on an administrator, for switching a client's administrative scopes allowance or for changing an administrative permission's description, `settings` for the email or audit-log settings), `targetKind` and `targetId` where the request has a target, and for a grant refusal or a description change `permissionIds`, the administrative permissions that caused it, and `groupIds` when it moved a user into or out of an administrative group |
| `administrative_permission_changed` | An administrative permission was granted to or revoked from a user, a group or a client, or a user joined or left a group holding one. Written beside the change's own entry (`added_user_permission`, `updated_client_permissions`, `user_added_to_group` and their siblings), never instead of it. Deleting an administrator or an administrative group writes its own deletion entry and not this one. | `change` (`granted` or `revoked`), `targetKind` and `targetId` (the user, group or client, the user for a membership change), `permissionIdentifiers` (such as `authserver:manage`), `groupId` for a membership change, and `loggedInUser` |
| `updated_client_administrative_scopes` | A client's allowance to request the administrative scopes on a user's behalf was switched, through `PUT /api/v1/admin/clients/{id}/administrative-scopes` or the client's **May request administrative scopes** switch in the admin console. An allowed client is an administrator client, so an alert on who is an administrator watches this beside `administrative_permission_changed`. Written once the switch is stored, once per switch, including a switch to the value already stored. | `clientId`, `clientIdentifier`, `allowed` (the new value) and `loggedInUser` |
| `administrative_scope_refused` | A client that is not allowed to request the administrative scopes asked for one on a user's behalf and was refused (see [the endpoints' answers](/reference/endpoints/#administrative-scopes)). Written once someone has authenticated: at the authorization endpoint when the browser holds a valid session, `prompt=none` included, which is a crafted link reaching a signed-in user; when the code or implicit tokens are about to be issued; and on the authorization code, refresh token and password grants once the client has authenticated. A refusal at the authorization endpoint with no valid session writes a Warn log record instead, because that endpoint is open to anyone and not rate limited. | `clientId`, `clientIdentifier`, `scopes` (the refused administrative scopes, such as `authserver:manage`), `checkpoint` (`"authorize"`, `"issue"`, `"authorization_code"`, `"refresh_token"` or `"password"`) and `userId` |
| `viewed_client_secret` | A client's secret was read, decrypted, through `GET /api/v1/admin/clients/{id}/secret`. The admin console reads it there each time its **Authentication** tab is opened for a confidential client. Reading a client that holds no secret writes nothing. | `clientId`, `clientIdentifier` and `loggedInUser` |

The `updated_client_permissions` entry names what a client permission save changed, in `grantedPermissionIds` and `revokedPermissionIds`, so a grant to a client can be traced to the permission it was.

## Event format

Every audit event has a stable string identifier (such as `token_issued_authorization_code_response`, `auth_success_pwd`, or `deleted_user_session_client`) and a JSON details payload describing the actors and parameters involved. The full set of event identifiers is defined in `src/authserver/internal/audit/events.go`.

In the database, each row of the `audit_logs` table stores:

- `id`: auto increment primary key
- `created_at`: timestamp the event was recorded
- `audit_event`: event identifier
- `details`: JSON payload as text
- `request_id`: id of the request that raised the event, empty if there was none
