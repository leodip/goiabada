In Goiabada, you can define both resources and permissions. Each resource can have multiple permissions associated with it.

You can assign these permissions to users, groups, or clients as needed.

## Scope format

When you pair a resource with a permission, it forms a **scope**, both in the authorization request and within the tokens.

**Format:** `resource-identifier:permission-identifier`, both halves case-sensitive

**Example:**

If you have:

- A resource with identifier: `product-api`
- A permission with identifier: `delete-product`

The resulting scope will be: `product-api:delete-product`

This scope can then be requested in authorization requests and will appear in access tokens, allowing fine-grained access control to your APIs and resources.

### Permission identifiers are scoped to their resource

A permission identifier only has meaning within the resource it belongs to. Two resources can each
define a permission called `read`, and those are **two distinct permissions**: granting one conveys
nothing about the other.

So if you have `product-api:read` and `reports-api:read`, a client or user granted
`product-api:read` cannot use `reports-api:read`. You must grant each one separately.

This is worth knowing because reusing short identifiers like `read`, `write` and `delete` across
resources is normal and expected, and it is what makes the resource half of the scope load-bearing
rather than decorative. It applies to the `authserver` resource too: a `manage` permission you
create on your own resource is unrelated to the built-in `authserver:manage`.

## System-level resource

The `authserver` resource is a **system-level resource** used internally by Goiabada. It has special protections:

- Its **resource identifier cannot be changed** (renaming is blocked)
- It **cannot be deleted**
- Its **description can be modified**
- New permissions **can be added** to it
- Its **built-in permission identifiers cannot be renamed or deleted**
- The **descriptions of its six administrative permissions** are changed only by `authserver:manage` (see [Administrators](#administrators))

The built-in permissions under the `authserver` resource, with the description each is seeded with:

| Permission identifier | Description | Administrative |
|----------------------|-------------|----------------|
| `manage-account` | View and update user account data for the current user | No |
| `manage` | Full administration, including administrators and administrative permissions | Yes |
| `admin-read` | Read-only access to all admin API endpoints | Yes |
| `manage-users` | Manage users and groups that are not administrators, and their non-administrative permissions | Yes |
| `manage-clients` | Manage OAuth2 clients that are not administrators | Yes |
| `manage-settings` | Manage system settings, except email and audit logging, and signing keys | Yes |
| `browser-sessions` | Read and write admin console browser sessions | Yes |

You can create additional custom permissions on the `authserver` resource if needed, but the built-in ones listed above are protected.

An installation upgraded from an earlier version gets these descriptions too, except where an operator had already edited one: an edited description is kept as it is.

### Administrators

The six permissions marked **Administrative** confer power over this server. A user, group or client holding any of them is an **administrator**: a user directly or through any of its groups. The admin console's own client is always an administrator, whatever it holds, and so is any client an operator has allowed to request these six permissions as scopes on a signed-in user's behalf (see [Clients › Administrative scopes](/concepts/clients/#administrative-scopes)), since it can obtain a signed-in administrator's authority. `manage-account`, which every user receives at creation, and any custom permission you add to the `authserver` resource confer no power here and make nobody an administrator.

**Only `authserver:manage` creates an administrator, changes one, or changes what reaches one.** The granular scopes `manage-users`, `manage-clients` and `manage-settings` keep full control of everyone else, and every scope that reads still reads administrators, but none of them can:

- grant or revoke an administrative permission, add a user to or remove one from a group holding one, or delete such a group;
- write to an administrator, or read an administrator client's secret;
- change the description of an administrative permission, which is what an operator reads before granting it;
- change the email or the audit-log settings.

So `manage-users` can still grant and revoke `manage-account` and your own custom permissions, to anyone who is not an administrator, and `manage-settings` can still add custom permissions to the `authserver` resource and change the description of `manage-account` and of your own permissions. These rules judge the object a request writes: a change to an ordinary group or resource still reaches an administrator who is a member of the group or holds one of the resource's permissions, but it cannot make or unmake an administrator, because neither holds an administrative permission. A refused request changes nothing, answers `403` with the error code `MANAGE_SCOPE_REQUIRED`, and leaves an `administrator_change_refused` entry in the [audit log](/concepts/audit-log/#events-to-alert-on). See [Scopes](/reference/api/scopes/) for each scope in detail, and [Administrators](/reference/api/administrators/) for the whole rule.

Granting an administrative permission is how an administrator is made, so grant one as deliberately as you would hand out the admin console's password. Every grant or revocation of one, and every user joining or leaving a group that holds one, leaves an `administrative_permission_changed` entry an operator can alert on. Goiabada also refuses any change that would leave no enabled user holding `manage`: see [the last administrator](/concepts/users-and-groups/#the-last-administrator).

## How to use scopes

1. **Define resources** - In the admin console, create resources that represent your APIs or protected areas (e.g., `product-api`, `user-service`)

2. **Create permissions** - For each resource, define the actions users or clients can perform (e.g., `read`, `write`, `delete`)

3. **Assign permissions** - Grant these permissions to:
   - Individual users
   - Groups (all members inherit the permissions)
   - Clients (for server-to-server access)

4. **Request scopes** - When initiating an authorization request, include the scopes your application needs:
   ```
   scope=openid product-api:read product-api:write
   ```

5. **Validate access** - In your API, check the access token for the required scopes before allowing access to resources
