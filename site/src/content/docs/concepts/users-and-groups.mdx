## User management

As an administrator of Goiabada, you can create users and configure their properties:

- Profile information (name, nickname, etc.)
- Address
- Phone
- Email

You also have the capability to:

- Modify user credentials
- Terminate active user sessions
- Revoke consents

## Password recovery

A user who forgot their password can ask for a reset link from the login form. The link is sent only when the account is **enabled** and its email address is **verified**. For any other account (one whose address was never verified, or one an administrator disabled) nothing is sent and no code is stored, and the page says exactly what it says for an address with no account, so it cannot be used to find out which addresses are registered.

A reset link stops working as soon as its account is disabled, or as soon as the account's email address is changed, by the user or by an administrator, since the link belongs to the address it was mailed to: following it, opening the form and submitting it are each refused with the same "invalid or expired" message any other dead link gets. Correcting a mistyped address after sending a new user the email to set a password therefore retires the link sent to the mistyped address; send the email again. Sending a reset link also needs SMTP to be configured in the admin console.

<Aside type="caution">
On the default settings, self-registration does not require email verification, and a user an administrator creates starts with the address unverified. Those users cannot recover a password on their own until they verify their address while signed in (offered in the account pages whenever SMTP is configured), or until an administrator marks the address verified or sets a new password for them.
</Aside>

## Permissions and attributes

You can assign permissions and attributes to individual users.

**Attributes** are key-value pairs of arbitrary information that can be included in the access token or ID token. When creating an attribute, you can choose to include it either in the access token or the ID token.

## Groups

To facilitate user management, you can create groups of users.

When you give a permission to a group, it's given to all group members. The same applies to attributes - group attributes will be included for all group members.

Groups are useful for:

- Role-based access control (e.g., `admins`, `editors`, `viewers`)
- Department-based permissions
- Feature flags for specific user segments

A group holding one of the [administrative permissions](/concepts/resources-and-permissions/#administrators) makes every member an administrator. Adding a user to such a group, removing one from it, or deleting it therefore needs `authserver:manage`, just as granting the permission directly does.

## The last administrator

Goiabada refuses a change that would leave nobody able to administer it. An administrator remains while at least one **enabled** user holds `authserver:manage`, directly or through a group. Six changes can end that, and each is refused when it would bring the number of such users to zero:

- revoking `manage` from a user;
- revoking `manage` from a group;
- removing a user from a group that gives them `manage`, from the group's members or from the user's groups;
- deleting a group that gives `manage`;
- disabling a user;
- deleting a user.

The refusal changes nothing and answers `409` with the error code `LAST_ADMINISTRATOR`, and the admin console shows its sentence on the page you made the change from: "This change would leave no enabled user holding authserver:manage. Grant it to another user first." Grant `manage` to another user, then repeat the change. Removing one of several administrators works as before.

A client holding `manage` does not count, because what has to survive is a person who can sign in to the admin console and repair things; neither does a disabled user. The check reads permissions, not whether the person can still sign in: a sole administrator who has lost their authenticator, forgotten their password with no SMTP configured, or lost their mailbox still counts, and nothing in Goiabada gives them their access back. Keep `manage` on at least two people you trust, so that one can always restore the other.

## User self-registration

When the **User self-registration** setting is activated, end-users gain the ability to independently register their user accounts using a link on the login form.

If this setting is disabled, only administrators can create new user accounts through the admin console.

### Email verification

For user self-registrations, there's an option to require email verification for new accounts.

With it enabled, and SMTP configured, the registration form asks for the email address only, and every well-formed address gets the same "check your email" page, whether or not it already has an account. What happens next travels in the mail. A new address is sent a link, valid for 5 minutes. Following it opens a form where the person who received the message chooses the account's password, and the account is created, with its address marked verified, only when that form is submitted. Opening the link alone creates nothing, so a mail scanner or link previewer that fetches it cannot complete a registration, and someone who registers an address that is not theirs never chooses the password the account gets.

An address that already has an account is sent a notice instead, saying that no new account was created and pointing at the forgot-password page, if the account is enabled and its address verified (the rule [password recovery](#password-recovery) applies). Any other account is sent nothing, and so is an address whose registration is still pending. Each such request leaves one `requested_registration` entry in the audit log, recording what it led to, with the address digested rather than stored.

If the address has meanwhile gained an account, for instance because an administrator created one, following the link is refused and the pending registration is discarded.

Without email verification, the registration form asks for the password too, and the account is created at once, with its address unverified.

<Aside type="caution">
Only registration with email verification hides whether an address has an account. Without it, the form tells the visitor when an address is already registered: the account it creates is usable at once, so answering a taken address the same way would hide nothing, since signing in with the chosen password would fail. Enable email verification if the list of registered addresses should not be discoverable from the registration form.
</Aside>

<Aside>
To use email verification, be sure to configure your SMTP settings in the admin console.
</Aside>

<Aside type="tip">
This is different from [dynamic client registration](/concepts/clients/#dynamic-client-registration-rfc-7591), which allows applications (not users) to self-register as OAuth clients.
</Aside>
